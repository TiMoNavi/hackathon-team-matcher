# GitHub 用户画像候选源码对比

核对日期：2026-11-11。依据为以下固定提交的本地源码和许可证文件；本报告是静态核对，没有完成第三方程序运行验证。

## 结论

目前拉取的三个项目中，没有一个可以直接作为已经成熟的活动交友画像后端。建议先试 `github-profiler` 的公开数据采集，再评估简历合并与确认入库；`skill-mining` 的证据组织值得参考，但不能直接使用其角色结论。

| 候选 | 技术组成 | 与任务相关的能力 | 限制 | 许可证文件 |
| --- | --- | --- | --- | --- |
| github-profiler | Bash、Python、Claude Code Skills | 主页、仓库、README、贡献与按作者筛选提交；开发者分析提示词 | 偏脚本工作流，没有业务画像编辑和确认入库闭环 | MIT |
| skill-mining | Python、PyGithub、LangChain / LangGraph、Groq | 收集器、跨仓库信号、可引用证据索引 | 角色 agent 把 fork 当贡献；收集证据与最终推断质量不一致 | 本次提交未找到 LICENSE / LICENCE / COPYING 文件 |
| ai-recruiter-assistance | FastAPI、LiteLLM / Mistral、ChromaDB、SQLite | 简历文本与 GitHub 分析合并成 CandidateProfile | 偏招聘，字段和采集范围有限；仓库包含大量 node_modules | Apache-2.0 |

未找到许可证文件不能解释为已明确授权商用改造或再分发。本次仅下载并阅读 `skill-mining` 供调研。

## 1. github-profiler：优先试采集部分

- 上游：<https://github.com/therain2020/github-profiler>
- 固定提交：`ac3904fb0085be41a964237a249ae0e7aa63709b`
- 本地：[源码](../repos/github-profiler/) · [采集器](../repos/github-profiler/scripts/fetch-github-data.sh) · [分析提示词](../repos/github-profiler/templates/analysis-prompt.md) · [persona 提示词](../repos/github-profiler/templates/distill-prompt.md)

采集器使用 REST / GraphQL，保留 fork 等仓库属性；深入采集包含 README、按 `author=username` 筛选的提交及作者相关活动。是否拿到完整数据受访问权限、限流和采样范围影响，不能仅凭脚本存在就认定采集完整。

可复用价值是来源采集和中间数据。分析提示词中的维度评分、沟通风格和开发者 persona 属于模型判断，不是已证实的人格或能力事实。本人的提交记录也只能支持对应范围内的贡献，不能证明整个仓库由本人完成。

另有 [save-score.sh](../repos/github-profiler/scripts/save-score.sh) 用于向 Supabase 排行榜上传分数。本次未运行；后续试验应单独选择采集步骤，不直接执行整套工作流，也不启用私有仓库采集。

## 2. skill-mining：证据设计有价值，角色结论不可靠

- 上游：<https://github.com/krittikasardar/skill-mining>
- 固定提交：`528d7135cdca30a723b13d92f3487959de8d32d8`
- 本地：[源码](../repos/skill-mining/) · [仓库收集器](../repos/skill-mining/collectors/repo_collector.py) · [证据 schema](../repos/skill-mining/transformers_local/schema_builder.py) · [agents](../repos/skill-mining/data/agents/agents.py)

`schema_builder.py` 组织 `repositories`、`aggregate_signals`、`evidence_index`，便于让结论回到具体来源。收集器中的提交采样使用 `repo.get_commits(author=author_login)`，比只看语言占比更贴近贡献归因。

但是 `role_analyzer_agent` 直接把 `is_fork` 分成 original / forked，并在给模型的文本里称后者为 `Forked repos (contributed to others)`。fork 本身只说明复制了一个仓库，不说明向原项目贡献过代码；非 fork 也不能证明全部代码由本人原创。这个输入错误会污染角色画像。

技能 agent 还将部分仓库元数据包装为 “pseudo-evidence”。因此，存在证据 schema 不等于每个 agent 都真正使用充分、可归因的证据。不能照搬输出中的 creator / contributor / maintainer 等身份结论。

## 3. ai-recruiter-assistance：有简历合并流程，深度不足

- 上游：<https://github.com/alexcfv/ai-recruiter-assistance>
- 固定提交：`8b6000573f1e2ffd7e8ad698d1eeaec5c17a981d`
- 本地：[源码](../repos/ai-recruiter-assistance/) · [采集器](../repos/ai-recruiter-assistance/github/collector.py) · [画像 schema](../repos/ai-recruiter-assistance/models/schemas.py) · [合并服务](../repos/ai-recruiter-assistance/services/profile_builder.py)

`ProfileBuilder.build_profile` 把简历文本块与 GitHub 分析拼入提示词，调用模型生成 JSON。`CandidateProfile` 包含 summary、skills、experience、education、projects、github_analysis。这证明源码中存在合并入口，尚不能证明输出质量、逐字段证据和业务入库闭环满足本项目要求。

采集器只取响应中的前 3 个仓库，每库取目录树中前 5 个指定扩展名代码文件，README 截取 2000 字符，代码片段各截取 1500 字符。这里的采样不能当作完整代码审查，也不足以直接证明用户技术深度。

当前 schema 中履历只有 role / company / description，教育只有 degree / institution，项目只有 name / description；没有完整覆盖所需联系字段、奖项记录、贡献归因、字段证据、可见性和确认版本。文档中的 PDF 路径也不能解释为已验证支持用户的 DOCX。

该固定提交包含 64,843 个跟踪文件，其中 64,686 个位于 `node_modules/`。依赖产物被提交说明工程维护需要进一步检查；本次没有执行这些依赖或仓库脚本。
