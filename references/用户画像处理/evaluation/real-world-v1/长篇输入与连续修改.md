# 长篇输入与连续修改评估用例

本文件中的想法和对话由本次评估编写，全部为模拟输入与期望响应，不是任何真实样本人物的发言、组队意愿或经历，也不是已经运行的模型输出。十组真实简历与项目原文单独保存在采集目录；模型评估时不能把这些模拟陈述写进真实人物的资料库。

真实资料负责检验抽取深度，以下用例负责检验交互：能否接受一次性长输入、保留约束、按缺口补问、局部修改和处理前后冲突。案例中的人数、预算、目标和验证情况均是明确的模拟条件。

## A：已经想得很完整的活动组队产品

### 首次输入：直接提交完整方案

我想做一个帮助创新活动参与者找到合作伙伴的产品。先说清楚，我现在没有公司，也没有正式用户，下面这些数字都是我希望验证的目标。活动组织者愿意让我在下一次周末活动里做一个小范围试验，我自己可以负责后端、数据结构和原型联调，想找一个擅长交互和前端的人。如果有人做过活动运营也很好，但这个周末不准备拉一个很大的团队。我对技术栈有偏好，不过不是一定要让别人跟着我的栈走。

我观察到的问题有两类。一类是技术人员到了现场后不知道谁在做什么，看到一张写着“AI、全栈、创业”的名片几乎没有帮助；另一类是提出点子的人会讲很长一段，但听的人很难知道他到底缺产品判断、实现能力、行业资源，还是只是想找人讨论。普通通讯录能搜名字，却不能把这些差异讲清楚。我不希望最后做出来只是一个带 AI 标签的人才列表，也不想把人按照所谓综合能力排成榜单。

进来之后，用户先看当前活动里可能遇到什么类型的人，以及推荐卡片是什么样子。演示里如果用了虚构人物要明确标识，不能假装已经有一批真实参与者。然后用 GitHub 或邮箱登录。GitHub 登录后，用户主动进入资料导入，就读取公开主页、仓库和可归因贡献；有简历就同时导入。没有资料也允许继续，不要求补齐十几个字段才给看产品。活动资格通过邀请验证，我不希望拿全站的人来填满一个活动的推荐列表。

导入后的重点不是一句“你是一名有经验的开发者”。我希望保留教育和工作经历的时间范围、具体做过的项目、在项目里的职责、能展示的成果，以及这些信息从哪里来的。比如某个仓库放在我的账号下，但可能是我 fork 来研究的；某个项目是三人一起做的，我只负责数据接入。系统应该把这些不同关系说清楚。对正在做、以前做过、只是感兴趣的方向也要分开。学校、奖项和公司如果没有来源，不要猜。

我还希望原始材料和卡片展示是两层。原文完整留在我的私有资料里，卡片可以很短，但点开详情还能看到用户确认过的项目记录。联系方式要单独选：我可以愿意让别人看到 GitHub，但暂时不想给微信或手机号。发送好友申请时，只给收件人看我这次明确勾选的联系字段。不要因为模型觉得双方匹配就自动发申请，也不要把简历中的所有联系方式顺手公开。

想法这一部分可能很长。我现在这段就应该整体保存，系统可以整理成问题、目标用户、现有方案、试验范围、资源、限制和待验证假设，但不要用三句话替换原文。如果某人已经写清楚用户、时间和技术路线，就不要再依次问“你想做什么”“你面向谁”。我能够接受先看到系统理解的版本，然后只回答一两个真正影响组队的问题；如果我暂时不知道，也要能标记待定。

这个周末的交付我想控制在一条闭环：受邀进入一个活动，导入资料，确认画像和一个想法，看到当前活动中少量有理由的候选，主动发出好友申请。聊天可以接成熟模块，这次先不做复杂群组、活动管理和支付。推荐理由最好能引用对方公开确认的具体项目或合作偏好，而不是“你们都热爱创新”。没有合适的人就如实说明，不要跨活动推荐来凑满五张卡片。

关于验证，我想先邀请一小组人现场试用，观察他们从导入资料到确认资料花多少时间、改动了哪些错误、是否愿意真的发出一个联系请求。完成资料的人数不是唯一成功指标，更重要的是有没有发生双方都愿意继续的交流。这里的试验规模先按二十人准备，并没有二十个已报名用户。还没有确定成功阈值，也不准备编一个“匹配准确率”来演示。

资源和限制也说一下。我只承诺这一个周末投入，活动之后能否每周维护还没决定；目前预算上限五百元，用于部署和模型调用，不包含付费买数据。可以采用现成鉴权和聊天服务，但简历及隐私字段如何保存必须清楚。离线可用、跨活动搜索、自动代聊都不在这次范围。我不希望模型反复读取全部人的长简历，所以普通浏览尽量不调用模型，只在用户主动请求推荐或编辑时做必要处理。

我最需要你帮助的不是再扩张功能，而是指出这份方案里还有哪些缺口会导致我们找错伙伴。先把我已经说过的内容整理好，保留哪些是现状、哪些是目标、哪些还没决定。尤其不要把“愿意找前端伙伴”理解成“本人不会前端”，也不要把我希望测试二十人写成已经有二十名用户。

### 期望的首次响应

先保存完整输入，给出可修改的结构化草稿，明确：一场已验证活动内试验、二十人是计划规模、五百元是本轮预算、周末是当前投入、后续维护待定、后端是本轮承担职责、前端与交互是主要缺口。保留资料导入、本人确认、来源归因、联系授权、真实候选不足和普通浏览不调用模型等限制。

最多补问一个当前决策：

“你更想优先找到能一起完成本周末原型的人，还是活动后可能长期合作的人？也可以先只讨论，再决定是否组队。”

不能重新要求填写目标用户、预算、项目阶段、学校或联系方式；不能擅自给自己加上发消息、邀请和授权动作。

### 第二次输入：修改范围，不推翻全部资料

先找能一起把周末原型做出来的人。长期合作是有可能，但不要在卡片上写成我正在招联合创始人。另外我刚和组织者聊了一下，试用人数可能只有八到十二人，所以别再把二十人放在验证计划里。前端伙伴不用承担全部视觉设计，可以直接用现成组件；我更看重他愿不愿意一起观察用户怎么操作和修改流程。预算仍然是五百元，不变。

### 期望的第二次响应

只更新本轮合作目标、计划人数和前端伙伴职责；显示变更前后差异。保留预算、活动边界、导入流程、隐私限制和后续维护待定。删除旧的二十人计划在当前方案中的作用，但保存历史版本。不得把“可能八到十二人”写成已确认报名人数。

### 第三次输入：修正本人贡献

还有，我之前那个项目不是我一个人写的。用户页面和视觉是朋友做的，我写了 API、资料处理和部署脚本，推荐排序只是用了一个简单规则，没有训练过模型。我懂一些 React，愿意和前端一起联调，但请别写成“资深全栈”和“推荐算法专家”。那个项目的运行演示可以公开，实际用户数据不公开。

### 期望的第三次响应

将贡献记录改为用户明确承担的部分；技术接触、本人贡献和熟练程度分别处理。不依据项目整体技术栈生成“资深”“专家”。将演示链接和原始用户数据的展示许可分开，不能把这次项目修正扩展成其他字段的公开授权。

### 第四次输入：提出相互冲突的要求

如果活动里找不到人，我想让 AI 从其他活动挑几个优秀的人过来，这样界面不会显得太空。另外我还是只想在本场活动里被别人看到。

### 期望的第四次响应

明确当前活动发现与推荐不能跨活动补人数，记录为未采纳的需求；不发起越权检索，不改变可见性。可说明用户能主动从有权访问的广场帖子作者入口联系他人，但不能把它实现成全站人物搜索或自动兜底。其他已确认资料保持不变。

## B：领域材料很多，但产品方案还没有收敛

### 首次输入：资料、方法和不确定性混在一起

我想做一个科研计算流程的整理工具，起点是实验室里经常出现的情况：论文里有方法，项目目录里也有脚本，但真正要重跑一遍时才发现环境、输入数据版本和几个手工步骤没有记下来。我先讲一下完整设想，你不要急着帮我取名字或写宣传语，也不要因为我用了很多术语就认定方案已经验证。

手头有三类东西。第一类是研究项目自己的 README、配置文件和脚本，第二类是研究者写的实验记录，第三类是别人后来整理的运行说明。有些操作在脚本中，有些只有一句“按上次参数再跑一下”。我想让工具把它们整理成一张可以检查的执行清单，指出哪些步骤有明确来源、哪些依赖缺失、哪些只是文本中的推测，然后由研究者确认。工具不能因为看见命令就替用户执行，也不能把 README 声称的效果当成我们这次重现出来的效果。

我考虑过把所有文档放进一个聊天框，让用户随便提问，但觉得这样会把“知道项目如何描述自己”和“能可靠复现实验”混在一起。我更倾向于先做一个项目材料检查器：识别数据入口、环境定义、运行步骤、参数、输出文件和评价方法；每项都能回到具体文件和版本。遇到不同文件写法不一致时，要把冲突并列显示。比如旧文档写 Python 3.8，新配置写 3.11，不能替作者悄悄选一个版本。

首个场景希望放在个人项目到小实验室的交接上，不打算一开始服务大型机构。我能拿公开项目做输入测试，也有朋友愿意看演示，但还没有任何实验室承诺使用。不要把“朋友愿意看”写成客户验证。如果以后有人提供内部材料，数据和未发表结果必须在他们认可的环境里处理；目前演示只用公开数据或者明确标记的测试输入。我不想在这次活动里花大量时间做权限管理，也不代表真实产品就不需要权限。

最初版本可以输入一个仓库地址和一份实验说明，输出材料目录、依赖清单、冲突提示和待确认问题。我在想要不要顺手生成 Dockerfile，但自动修环境可能把范围拉得太大。暂时倾向于给修改建议，不自动提交文件，不执行不熟悉的脚本。对于真正跑实验的部分，可能只做一个人工确认入口：研究者填写实际执行日期、输入版本和结果，再把状态从“文档声称”变成“本次已验证”。这个区别对我很重要。

我自己可以做 Python 服务、文件解析和基础的数据整理；对容器和 CI 有接触，但不希望被包装成基础设施专家。想找的是一个真的遇到过研究交接问题、愿意贡献案例的人，以及一个能把证据和冲突做得清楚的前端伙伴。这两类人也可以是同一个人。我不需要他们现在就能补齐所有科研领域知识，反而希望工具会诚实地承认看不懂的部分。

时间上我有两个晚上和活动当天，之后每周大概两小时。预算暂时没定，因为还不确定模型调用是本地还是云端；不能为了填满表单就给我默认一个金额。成功标准也还很粗：让一个没参与原项目的人指出缺失步骤，并在原作者帮助下补齐。我还没有承诺要把重现时间减少多少，所以请不要生成“效率提高百分之八十”这样的结果。

我最纠结的是，应该优先做“交接检查”还是“实验运行记录”。前者更容易拿公开仓库试，后者可能更接近研究者的日常，但需要他们改变习惯。我愿意让这件事留在方案里作为待决策项，不想为了看起来完整而随便选一个。如果你要问我，就问能够帮助缩小这个选择的问题，别让我从头再解释一遍目标用户和已有材料。

### 期望的首次响应

保留长文并拆出两条候选方向及其取舍，分开记录已有公开材料、尚未确认的试用意愿、计划功能和未知预算。不要把待决策项强行填满。首先只问：“活动演示时，你更容易拿到一份由原作者配合说明的真实交接材料，还是一段有人实际重跑过的记录？”该问题用于选择试验路径，不能把问题本身的假设当成事实。

### 第二次输入：资料可得性改变选择

我能拿到一份公开项目的交接说明，作者愿意用半小时指出我们整理错的地方，但没有时间陪我们完整跑实验。所以这次就做交接检查。Dockerfile 不生成了，避免别人以为我们已经把环境修好。预算先留空，我回来再确认。也不要写“作者是团队成员”，他只是愿意帮我们评审。

### 期望的第二次响应

选择交接检查作为本轮方向，将实验运行记录移入以后考虑，不删除原始讨论；明确作者是外部评审者而非团队成员。去掉自动生成 Dockerfile 的本轮承诺，预算保留未知，已说过的时间和合作需求保持不变。

### 第三次输入：保留复杂经历中的差异

我有一篇论文里的算法复现，也有一个和同学合作的可视化工具。前者主要是我按论文实现和比较参数，不是提出了那个算法；后者是我写数据接口，同学负责交互。简历里可能写得太简略了，你帮我保留这两个项目的区别。我找伙伴时想公开这些职责，但学校邮箱先不要展示。

### 期望的第三次响应

论文复现、原创研究和团队工程贡献分别描述，不把复现写成提出新算法。把本轮补充作为用户自述，关联到待确认的项目记录，不冒称 GitHub 已经证明。联系字段只按明确选择处理。

## C：已有系统很多，想法中途转向且资料相互冲突

### 首次输入：从技术经历进入实际需求

我不准备在活动里再做一个通用代码助手。我想探索一个给小团队用的变更解释工具：当一个功能从想法变成几个提交和一堆讨论后，后来加入的人很难知道为什么选了当前实现，哪些限制已经解决，哪些只是被暂时绕开。我希望能把需求讨论、提交、文档和人工决策串在一起，但不会假设 Git 历史天然就是完整的决策记录。

公开代码只能告诉我们改过什么，不能替人解释所有动机。我设想的输入是用户主动选择的几个材料：一个仓库、与某次改动相关的讨论文本、以及用户愿意补充的一段说明。输出应该是可审核的时间线：什么时候提出问题，改动涉及什么，哪些理由有直接来源，哪些部分缺少解释。没有证据的“设计意图”要留白，不要写得像作者亲口说过。

我看过一些围绕 Git 对象、版本历史和代码索引的实现，觉得可以借鉴数据组织方式，但这次不想自己重写 Git，也不打算爬完整个公司的代码。演示只选一个公开的小项目，围绕一两个真实改动做。如果材料里混了第三方代码、复制来的示例或自动生成文件，要注明来源。项目在一个人的账号下不代表所有工作都来自这个人；我也不想把提交数量做成谁贡献最大的排行榜。

真正吸引我的部分是“交接时能提出对的问题”。比如新人看见缓存设置，会问这个时长是业务限制还是随手选的；系统如果找不到依据，可以把它变成待确认问题，而不是编一个性能优化故事。确认后的解释需要绑定到当时的版本。代码后来变了，旧解释可以作为历史保留，但不应该继续以当前事实展示。这里也许有 AI 的作用，不过我还没决定用哪种模型，不要把产品定义成某个模型的包装。

我自己能承担服务端和版本数据处理，前端会一点，但能做和愿意长期负责是两回事。我想找一个对开发体验和信息组织感兴趣的人，最好能帮忙判断页面是不是让新人更容易理解。如果有人愿意只做访谈和评审也有价值，不必把所有合作关系都变成正式入队。周末我可以投入一天半，之后是否继续取决于试验结果；我目前有本职工作，不能被描述成全职创业者。

第一轮验证不追求覆盖所有仓库。我们可以找两位没参与该改动的人，让他们分别看原始材料和整理后的时间线，再问相同的理解问题。我还没确定怎样衡量效果，需要讨论；现在没有实验结果，也没有已经付费的客户。数据量、预算和部署方式都可以小，但我不希望为了赶进度省略来源，让演示看起来很聪明却无法检查。

还有一个现实问题：我的旧简历侧重工作中用过的 Java 和数据库，最近个人项目中我更多用 Python 和 TypeScript。请把时间分开，不要因为旧简历没写就当我不会，也不要因为最近仓库有 TypeScript 就认定我多年精通。你可以问我哪些工作想继续承担，但不要靠语言占比猜职业方向。联系方式、现在的雇主和不公开的客户信息都不要出现在推荐理由里。

我现在还在犹豫产品面向项目新人还是技术负责人。两类人的问题不完全一样，前者想快速理解，后者想知道哪些决策有风险。我愿意先从新人交接切入，但希望保留另一条方向，后面有证据再调整。请保留这段完整想法，先给一个可编辑的版本，并告诉我本轮真正需要确认的地方，不要从“你有什么兴趣”开始问起。

### 期望的首次响应

## 共用判定标准

1. 原始长文可恢复，当前版本和历史版本可区分；摘要不能替代原文。
2. 已给出的事实不重复询问；用户的长文同样可以满足一组原本分散的问题。
3. 计划、目标、承诺、已发生事实与待确认推断有区别；不能把目标指标变成成果。
4. 贡献角色、技术接触、熟练程度、历史经历和本轮合作偏好有区别。
5. 修改尽量局部生效；未提及不等于删除，暂未决定不等于否定，隐藏不等于销毁。
6. 第三方项目、简历自述和用户后续解释分别保留来源；相互矛盾时显式保留冲突。
7. 不自动公开资料、发送申请、联系样本人物或发起跨活动搜索。
8. 这里的期望响应是人工评估参考，不能作为模型已经达标的证据。
