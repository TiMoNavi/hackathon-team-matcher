## 1. 范围与交付顺序

推荐专项文档写在 `docs/推荐模块/`。2026-11-12 最新授权允许推荐公共规则接口、推荐自有选择表、P1 最小明确条目读取、原推荐前端与同源宿主接线；GitHub 登录/首次公开来源衔接单独实施。P1 增量记录归 `docs/用户画像收集/`，公共接口同步共享契约与 HumHub 实施合同。具体范围见文档24；不修改 HumHub 原版、P8、冻结稿，不通过跨域直读表或循环单人服务绕过。保留 R1 两个推荐目录精确白名单。先前文档17的会话接入范围与默认关闭策略保持；本批不启用 AI、不修改共享预览库或现有 worker。共享 recommendation-runs/AIJob 契约不被插件同步会话扩展替换。推荐专属旧材料见 [迁移记录](sources/document-relocation_2026-11-11.json)。

最终实现目标是两个 HumHub 插件。主模块已接通原生资格/关系、P1/P8 批量获准投影、请求专属索引与 SQL 召回，并完成显式装配的规则链测试。索引不跨请求复用；SQL 持久批次、获准重放与有界到期清理已接通，正式 API、生产调度与完整部署生命周期仍未完成；AI 包和内部人物链已完成本轮合成验证，生产 AIJob/预算及完整历史依赖仍待接通。

- 主模块 `backend/protected/modules/matcher-recommendation/`：完整的零模型规则发现、相似/互补/兼容评估、依据与未知项、受控召回及结果复核。
- 可选子扩展 `backend/protected/modules/matcher-recommendation-ai/`：需求解释、有限澄清、候选重排、模型协议适配；单向依赖主模块契约。

先让用户用结构化条件找同好和项目搭档，再接 AI。首个交付切片是人物规则匹配；项目需求可以作为查询上下文。想法卡片按独立 target_type 接通，不能用人物结果冒充想法推荐。三人组合求解、全活动分组、社交图排序和自动读取帖子不在首版范围。

普通资料、确认与隐私归 P1 `matcher-user-profile`；推荐不另建正式画像库，不依赖 P2 引导是否安装或完成，不直接发送好友申请、消息或授权联系人。无 AI 独立运行仍需真实业务授权能力。

用户端继续采用既有 React 方案；本计划不新增完整前端，不把 HumHub 示例 Widget 样式作为正式页面。原生设置入口只承担必要的策略配置。此 PHP 插件路线不自动修改全项目的 Next.js / FastAPI / PostgreSQL 目标设计。

## 3. 拟定结构与契约

```text
backend/protected/modules/
├── matcher-recommendation/
│   ├── module.json / config.php / Module.php
│   ├── domain/          QueryIntent、规则、分数、依据、未知项、版本
│   ├── contracts/       纯 PHP 端口和 DTO，不含 Yii/SDK 类型
│   ├── application/     DiscoverPeople、PrepareCandidates、RecordFeedback
│   ├── adapters/        P1、活动、社交、SQL、缓存、队列、配置存储
│   ├── controllers/     鉴权、输入转换、调用用例、响应映射
│   ├── migrations/      仅推荐拥有的表与索引
│   └── tests/           内存单元、契约、集成；独立运行配置
└── matcher-recommendation-ai/
    ├── module.json / config.php / Module.php
    ├── providers/       需求解释/候选重排的实现
    ├── adapters/        模型网关协议、结构化输出转换
    ├── prompts/         版本化提示模板
    └── tests/           假模型、预算、输出、注册与移除
```

类名为提案。R0 统一 01/04 中暂用的 Reranker 等命名，只发布一套契约。领域只依赖纯数据与规则；应用依赖领域和窄端口；适配器实现端口，Module 完成装配。主模块不得 import AI 子扩展具体类；普通请求不构造模型客户端。

| 端口/边界 | 输入输出与责任 |
|---|---|
| CurrentEventAccess | 服务端会话主体、当前活动、有效资格、状态/权限版本；不自行认定 Space ID 有效 |
| ProfileFieldCatalog | 稳定字段键、类型、枚举、作用域、目录版本/schema 指纹；P1 提供元数据，推荐存映射 |
| CandidateProjectionReader | 可信上下文+有界 IDs → 已确认 authenticated 最小投影及 attribute_id/版本；P1 负责授权 |
| ContactEligibilityReader | viewer+活动+批量 IDs → 入口相关资格、关系状态及版本；不输出完整关系图 |
| AuthorizedIdeaReader | current_idea_id+可信上下文 → 获准主题、明确缺口及版本，不推测成员容量 |
| IdeaCandidateProjectionReader | 可信上下文+有界想法 IDs → 当前活动允许发现的想法简介、主题、阶段、贡献缺口及版本；由想法业务提供，不借用 P1 人物投影 |
| CandidateRetriever | 类型化意图、硬条件、可信上下文、各路上限 → 有界 ID/排名/证据引用；不得绕开 P1 授权 |
| 策略/批次/任务存储 | viewer/event/query/policy/permission 绑定的版本化对象；R0 固定唯一所有者 |
| QueryInterpreter / CandidateReranker | 最小查询或获准摘要+预算 → 条件草案/池内排序与证据；主模块定义，AI 实现，主模块复核 |

推荐只保存自身策略、字段绑定、必要的可撤权派生索引、批次、曝光与反馈，不另建正式画像、联系人或好友申请事实库。run/job 的业务状态与 applicability 由主模块/统一任务域依既有契约管理，AI 扩展不另起冲突的状态系统。

- [x] **R2.4 互补规则**：需求匹配对方愿意提供的贡献，项目缺口匹配新增覆盖。领导协调/技术/商业是可多选贡献角色；会某技能不等于本次愿意承担，团队/容量/反向意愿未知就标未知。
- [x] **R2.5 兼容与约束**：实现明确协作/沟通偏好、可用时间及线上线下需求；区分系统限制、用户确认的硬条件、软偏好及未知；硬条件未知不能判为满足。
- [x] **R2.6 维度归并**：为 similarity、supply_demand、coverage_gain、explicit_preference、interval_overlap 固定版本化 0/0.5/1 语义及同维度聚合；同一事实不能重复加分。双向意愿有证据才表达，首版不改为几何平均等实验公式。
- [x] **R2.7 评分基线**：主题 .35、贡献 .35、时间 .15、协作 .15；按本次查询移除未提出维度再统一归一化，所有候选同权重。软项未知 .5，证据覆盖另记，不逐人删除未知项后重标满分。
- [x] **R2.8 召回融合**：沿用 `match_score=sum(weight*value)`、`rrf_score=sum(route_weight*61/(60+rank))`、`coarse_score=.8*match_score+.2*rrf_score`；rank 从1开始；路线权重 .4/.2/.4，关闭一路后统一归一化，未命中该路记0。
- [x] **R2.9 结果选择**：无硬冲突、至少一项明确主题/贡献依据且 match_score≥.35 才是明确匹配；同分稳定 ID 次序；分差≤.05 时按曝光/多样性政策选并固定批次结果。探索位最多1个且同样过门槛，不为凑角色引入无关人。
- [x] **R2.10 证据与理由**：输出规则ID、字段/想法引用、内容/权限版本、未知项与真实差异；用具体合作理由，不把排序分说成成功概率或人格评价。
- [x] **R2.11 不足与反馈**：区分无合法候选、硬条件不满足、无明确依据和依赖失败；只展示获准的概括原因，保留主动改条件/普通浏览，不跨活动补人、不自动降门槛；一次跳过不全局惩罚人。

验收：虚构案例可解释同主题、补项目缺口、时间冲突与未知人格的不同处理。全为未知而获得中性分的人不能冒充明确匹配。活跃度、发帖量、好友数、简历长度和 GitHub 提交量不进默认主分；不预置 MBTI 绝配矩阵，不从简历推人格。

## 9. R5 — 规模、理由与权限验收

依赖：合成回放可随R2完成，正式请求链与性能验收依赖R3/R4。R3 已有 SQLite 隔离规模及耗时观察，见文档 10；生产 MySQL、正式 API 性能与推荐准确率尚未验证，不能据此完成本阶段。

| 场景 | 验收断言 |
|---|---|
| 0/1个候选 | 真实0或1人，本人不推荐给自己，无无限重试/补人 |
| 35人仅2人有明确依据 | 明确匹配仅2人，不用未知中性分凑5人 |
| 30/40人，缺人格或时间软项 | 可选缺失标未知；其他证据仍可匹配；未知硬条件不过关 |
| 35人全部违反硬条件 | 真空匹配，不自动放宽；用户主动调整后重新查询 |
| 300/400人证据充足 | 路线及200粗排上限成立，无固定截断偏差；普通分页可到后续合法对象 |
| 多人兼任协调/技术/商业 | 按需求/意愿/缺口选择；重复角色不过度加分，不强凑每种角色 |

| 跨活动、邀请/申请/退出 | 全流程隔离，不跨活动凑数；广场联系例外不扩大推荐范围 |
