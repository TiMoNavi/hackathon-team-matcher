# 40 名虚构用户的真实 AI 推荐对话测试

> **产品验收结论：不通过。** 2026-11-12 用户明确否决本轮测试：缺少自然对话、真实工具进度、任务相关的深度需求、多轮持续上下文、当前名单讨论、换批边界和有依据的解释。本文保留原始技术观测，不能作为对话推荐功能验收通过的证据。改版要求见 [14 对话式找队友改版](14_对话式找队友改版与验收.md)。

## 2. 谁可以进入候选池

40 人中，36 人属于当前活动 7，另外 4 人属于活动 8。每组真实对话先排除另外活动的 4 人，再排除当前活动的 blocked、friend、pending_in、pending_out、ever_sent 各 1 人；31 人进入规则评估。private 与未确认特征不进入获准投影。

1032 的公开兴趣是音乐，私有资料另有项目相关内容。因此他可以出现在音乐交友结果里，但不能因为私有项目内容被推荐；不能把“存在 private 字段”误实现成整个人不可见。昵称来自演示专用虚构映射，不是已经接通的正式身份展示。

白露进入结果依赖 AI教育 的主题证据，不能据此声称她愿意做后端。需求当前是软偏好，模型可能返回部分满足者；若用户确认后端贡献为硬要求，应走确认后的结构化条件。金笙的时间冲突也没有被本次排除，因为本次没有提出具体时间约束。

## 5. 先澄清再寻找商业搭档

模拟用户：

> 我想找个合适的搭档，但还没想清楚该按什么条件找。

AI 原话：

> 你想优先按哪种方向筛选搭档？

模型提供的选项：互补的专业技能 / 共同感兴趣的话题 / 当前具体的合作需求。

模拟用户：

> 当前具体的合作需求。我想做AI教育项目，我来负责产品协调，想找愿意承担商业拓展的人，平时偏好异步沟通。

AI 实际生成的条件（全部是 soft 草稿）：

| 字段 | 操作 | 值 |
|---|---|---|
| topics | similarity | ["AI教育"] |
| needs | supply_demand | ["商业拓展"] |
| preferences | explicit_preference | ["异步沟通"] |

这段澄清是真实往返：先收到模型问题，再按该问题撰写模拟用户续答，没有预编模型提问。同一 run 完成澄清与条件生成，一次后端检索得到 18 名合格候选。

**最终失败。**首次精排和唯一修复都返回 finish_reason=length，JSON 不完整。服务返回 failed / invalid_model_output，没有展示部分 ID、没有重开 run 增加额度，也没有自动降级成规则成功。失败的 0 个展示结果与“没有合格候选”是不同情况。

## 7. 当前推荐逻辑如何工作

1. 服务端固定身份与活动，AI 无权改活动、扫描全库或直接申请好友。
2. 自然语言只生成白名单字段的软条件；不能把模型草稿冒充用户确认的硬条件。
3. 资格检查排除关系与历史不符合者，再依据共同主题、明确贡献、时间、协作偏好评分。角色互补使用需求 needs 对本次贡献 offers，不从技能或人格猜意愿。
4. 活跃查询维度的权重重新归一化；本策略原权重为主题 0.35、贡献 0.35、时间 0.15、协作 0.15。规则排序分为 0.8 × matchScore + 0.2 × rrfScore。它不是合作成功概率，也不是模型评分。
5. 缺信息作为未知，软条件评分可以是 0.5，但必须另外存在主题或贡献正向证据，未知本身不能支撑推荐。硬条件未知不算满足。
6. 模型只看最多 24 个、每个最多 768 UTF-8 字节的摘要。只返回池内 ID、证据 ID 与顺序；没有自由理由字段。
7. 主插件复核 ID、证据、活动和授权版本，再机械生成展示理由。rule_score 与 ai_rank 分开保留。

这些测试使用真实应用服务、规则、摘要构建与输出校验；底层检索为内存夹具，当前只使用上限 80 的 structured 路。未测试生产 SQL、多路语义召回、持久化平台预算、真实申请历史或正式 API。

## 9. 这次暴露的待修项

- 需求解释要区分“我能提供什么”和“我要找什么”，并校验字段值域；优先阻止角色进入 self_type。中文标准词项/别名应在运行前配置，不能看完输出后补映射凑命中。
- 解决中等候选池的结构化输出截断：先量化摘要、证据长度、网关输出配额的关系，再确定合规调整；保留总调用上限，不无限重试。
- 展示理由只强调本次正向匹配，明确未满足/未知项，不把同字段的所有获准事实都写成推荐优点。

本轮共 10 次真实生成，平台预留 10 次，上限 12；每个 run 仍受主插件 3/5 次及一次修复约束。网关报告 token 用量为 prompt=38703、completion=12320、total=51023。请求 max_tokens=1536，但部分返回 completion_tokens 超过此值，因此不能声称它是可靠账单硬上限。没有在成功/失败后另跑一轮挑选更好看的答案。

复核发现最初离线报告使用了较早的夹具摘要；已禁网按最终 40 人数据重跑 75 项并通过，现与 live 使用相同 corpus hash。真实会话没有重跑。手动脚本重复运行 live 时生成独立文件，保留之前的失败和费用记录。

子 agent 已反馈 41 项探针与问题清单；主代理归档该清单、复现评分对照并复核最终哈希。完成文件清单见 [完成记录](sources/dialogue-demo-completion_2026-11-12.json)。

本轮仅新增测试夹具、手动演示脚本和文档，没有修改推荐生产算法、其他插件或原版。上述语义缺口和输出截断尚未修复，不能据此把完整 R6/M2 勾为完成。
