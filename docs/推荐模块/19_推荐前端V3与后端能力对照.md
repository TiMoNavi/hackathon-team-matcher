# 推荐前端 V3 与后端能力对照

2026-11-12。范围为用户指定的本机 4203 推荐页面、该页面实际入口及现有 PHP 插件源码。本次理解与接口审查不推进实现任务，也不修改前后端代码或启用模型。

## 1. 实际看到了什么

通过独立浏览器打开当前页面，查看人物舞台，切换到许知夏，展开「经历与贡献」，查看五维分析并点击「问 AI：角色互补」。这些操作期间观察到的 fetch/XHR 请求为 0，页面错误为 0；仅证明本次原型交互，不代表后端联调。截图见 [人物舞台](sources/frontend-4203-stage_2026-11-12.png) 与 [五维分析](sources/frontend-4203-analysis_2026-11-12.png)。

实际入口 [app/page.tsx](../../frontend/推荐/app/page.tsx) 使用 [RecommendationExperience](../../frontend/推荐/components/recommendation-experience.tsx)，没有使用旧 Discovery 组件。人物来自本地 people，搜索通过定时器推进，助手依据关键词选择预写回复。详见 [前端 README](../../frontend/推荐/README.md)。

这个页面围绕同一位候选人，依次提供以下体验：

1. 在当前活动中取得一批人，逐人查看，明确刷新才重新找人。
2. 展示身份、标签，以及项目、贡献、想法、需求、时间、开场建议等资料切片。六张卡不是六份项目经历。
3. 下翻查看资料列表、作品浏览和经历与贡献。
4. 用贡献能力、项目方向、角色互补、投入时间、协作安排五个维度，分别表达事实依据、合作建议和待确认事项。动态图和表格是同一份解释数据的两种呈现。
5. 输入框和侧栏围绕当前人物继续讨论，也能提出新需求；切换人物不清空对话。
6. 收藏、阅读勾选、小版本清单目前都是页面内存状态。

## 3. 三个不能靠界面包装补齐的缺口

### 资料展示与推荐摘要不同

P8 的发现政策允许已确认的 project，完整概览可以返回按当前查看者授权的经历。因此不能说后端完全没有项目资料。但推荐 [P1SourcePurposePolicy](../../backend/protected/modules/matcher-recommendation/adapters/profile/P1SourcePurposePolicy.php) 的 project 当前只提取 tech_codes 用作贡献能力线索。当前 AI 摘要不等于完整项目讲解材料，页面能显示项目详情也不等于模型已经看过这些内容。

需要分别定义用于召回的特征、用于人物页面的获准资料、用于一次具体追问的最小证据。不能把整份简历或原始 README 送给推荐模型来填卡片；资料原文仍属于画像提取流程。详情对查看者可见的 friends 字段，也不能自动变成推荐 AI 输入。

### 合作分析需要双方依据

原型中「你做 AI，TA 把体验接起来」隐含当前用户能提供 AI 能力。正式结果必须基于本轮用户明确表达/选择的贡献，以及对方获准的活动需求；不能仅凭对方资料生成双向匹配断言。当前人物规则与对话已有需求文本，但完整本人 attribute_id 选择尚未接通，五维结构还需要补齐。

建议每一维单独保存事实依据、合作建议、待确认内容与适用版本。规则模式可以生成基础提示，AI 在同一合同内增强表述；无资料的维度明确未知。来源展示只引用获准字段，不公开内部授权指纹、原始来源正文或凭据。

### 讨论对象必须绑定到发送时的页面状态

建议后续合同允许提供 focus_target_id、batch_id/display_version，以及可选的资料片段引用；这些是尚未实施的提案。后端验证它们属于当前活动、本人会话和有效批次，不能相信客户端附带的画像正文。

用户在发送后切换人物时，晚到回复仍绑定发送时的人物，不随屏幕变化改写归属。需要比较两个人时显式传受限对象列表。对批次外普通浏览对象的咨询，另行定义获准入口，不能让 ID 参数绕开现有候选边界。

## 4. 首次进入、换人和重搜的语义

- 页面进入/刷新优先读取已有有效结果或普通发现；不沿用演示定时器自动启动一次付费 AI 推荐。用户已在引导明确发起的任务可以恢复读取。
- 上一位/下一位、展开项目、切换图表、轮换气泡只消费已获准数据，不调用模型。右侧卡片的视觉轮换也不代表重新推荐。
- 讨论当前批次使用 chat；用户明确首次找人使用 recommend；明确重新找人使用 refresh。更改硬条件仍经过完整需求确认入口，不能靠模型自称用户已确认。
- 四阶段动效可保留视觉，但完成时间、候选数和失败状态来自实际任务。无法提供细粒度实时进度时显示处理中，不制造百分比、工具调用或思维过程。
- 模型返回 0、1、2 人都必须有对应布局；不足、预算不足、依赖不可用和撤权分别处理。不得跨活动凑够三张或五张。
- 读取持久对话不等于有「列出我的会话」接口；恢复时还需协调会话 ID 的保存/发现和当前活动切换行为。

## 5. 接入顺序建议

1. 固定人物展示合同，复用现有普通发现、已确认身份、P8 概览及媒体能力，完成零模型真实页面。前端卡片映射可先放前端适配层；确有多接口一致性需求再加薄的服务端组装，不另建画像表。
2. 固定五维分析与当前人物上下文，先用规则证据和内存适配器验证；补项目解释的目的与授权，不把 profile 全对象扩成模型输入。
3. 复用独立 AI 子插件，补正式历史/平台预算依赖，接讨论、明确刷新、需求确认、真实错误与恢复。若要异步实时进度，再按共享 AIJob 协调，不拿画像专用 worker 直接冒充。
4. 最后按产品需要补收藏持久化、清单和曝光；纯视觉图表不新增模型工具或另一套 Agent 框架。

保持主推荐插件拥有规则、活动/授权、批次和会话，AI 子插件实现模型解释端口，画像与隐私插件保有正式资料。当前页面的设计方向可以在这套边界内实现，不需要修改 HumHub 原版来迎合卡片。

## 6. 本次结论与验证范围

现有后端能承接人物发现和对话的基础，但尚不能通过替换一个请求地址就完整还原 V3。最重要的增量是获准展示组装、五维解释、聚焦人物/项目的对话上下文和真实状态合同。

本次仅浏览本机前端和核对源码；没有连接业务数据库，没有真实模型请求，也没有重跑此前隔离套件。主模块 Module/config、AI Module 和对话 HTTP 输入与上轮回归指纹相同。此前隔离通过与生产缺口仍以 [18 验收报告](18_隔离后端接入验收.md) 为准；早期 task 中若有「未实现身份/普通分页」的历史描述，不能覆盖本次已查到的真实源码。未据此修改 task 勾选或宣称产品接入完成。
