# 推荐页真实运行方案

2026-11-12。用户要求同时修正前端与后端的运行方式。本文件给出建议采用的产品流程、交互边界和实施拆分，依据 [19 页面与后端对照](19_推荐前端V3与后端能力对照.md) 的实际浏览结果；不是已实现或已验收声明。本轮只规划，不改应用代码、共享契约或其他专项任务，不启动数据库、worker 和真实模型调用。

实施基座采用用户已批准的 HumHub 同源 React 插件整合，页面源码继续放在 frontend/推荐。对齐 [全站整合任务](../睡前全自动运行/task.md) 的 N02/N10/N11，不另建 FastAPI，不把本机 4203 演示服务直接当正式站点。产品规则与公共 API 仍以 [共享契约](../共享数据与接口契约.md) 为准；本文新增字段和用例须由 N02 单一集成人同步后才能实现为公共合同。

## 1. 页面要帮助用户完成什么

主线是「我想找怎样的搭档 → 看到一批有依据的人 → 看懂某个人 → 判断哪里可能合作、哪里还不知道 → 准备开场并自主联系」。保留现有人物舞台、作品展开和助手的表达方式，调整它们背后的真实含义。

本方案作出六项建议：

1. 页面有「本活动伙伴」与「按需求找搭档」两种来源。前者普通浏览，后者有明确的规则/AI推荐结果；视觉可以共享，来源标签不能混用。
2. 进入页面、换人、展开资料和查看分析不自动调用模型。恢复用户已发起的有效结果，也不重新收费。
3. AI 结果出现后，输入框默认讨论当前人物；修改需求与开始新一轮必须有明确动作。
4. 一个人的作品、经历、意愿与合作建议分开。六种资料切片是可选类型，不要求每个人凑齐六张。
5. 五维分析来自双方可用证据，分别展示「已有依据」「合作建议」「仍需确认」；不用一个匹配百分比替代解释。
6. 候选少、资料少、服务失败都允许诚实呈现；不靠循环同三个人或捏造内容维持舞台。

## 2. 首次进入和恢复

### 2.1 进入顺序

1. 从同源宿主取得登录状态，读取唯一 current-event 权威选择，核对活动有效性。未登录走普通登录；未选择/未加入有效活动提供选择或邀请入口，不发候选请求。
2. 读取普通发现与 AI 的真实能力状态。AI 缺历史、预算、提供者或策略时明确显示不可用原因；普通发现按自己的资格继续可用。
3. 若从引导带来已发起的 run/conversation 引用，或本人有当前活动的最后一次有效推荐，则重新授权后恢复名单、问题与输入上下文。引用存在不等于有效，不能直接恢复浏览器缓存里的画像。
4. 没有有效推荐时先展示「本活动伙伴」，默认按资料最近更新排序。页面提供「按需求找搭档」，不播放 AI 搜索成功动画。这里的 recent 是资料更新时间，不是在线状态或活跃程度。
5. 用户可以直接浏览，也可以写需求；填写不以画像十步全部完成为前提，普通资格仍由服务端判断。

现有接口能读取指定 conversation，但没有已核实的「本人当前活动最近会话查询」公共入口。完整跨刷新恢复需补这个窄查询/旅程引用，不能使用 localStorage 作为业务事实源；本地最多保存对象 ID 和 UI 偏好，返回页面后必须 GET 重验。

页面初始化还需要只读能力投影，分别说明普通浏览、开始推荐、当前批次讨论、刷新、收藏/联系是否可用及受限原因。它是拟补合同，不能把内部factory检查当作现成前端API。能力为true也不授予后续请求权限；真正提交时仍重验活动、版本、预算和资格。无需向浏览器暴露网关配置、内部异常或完整平台额度。

### 2.2 需求输入

输入框的轻量引导为「想做什么」「你能提供什么」「还缺什么帮助」，支持一句话，不强制填三张表。例如「我负责产品和用户访谈，想做一个活动报名工具，找周末能一起做的后端伙伴」。

旁边可以选择「使用我已确认的本次活动目标」，展示实际选中的本人条目与版本；可逐项移除。服务端校验 selected_self_fields 的 attribute_id、本人归属、版本和 Space。不得默认读取全套私有简介、来源原文或其他活动目标。没有这些字段时，用户本轮明确输入也可以成为需求依据。

处理需求时显示可编辑条件，区分「必须满足」与「尽量满足」。普通筛选的精确条件和 AI 推荐的软偏好不能使用同一未标明含义的控件。模型解释出的条件是草案；新增/修改硬条件必须由本人确认，已经确认的条件不反复弹窗，也不被后续模型覆盖。确认沿用完整快照和版本语义。

信息够用就开始检索；只有会改变人选的问题才追问，例如「周末都可参与，是必须两天还是有半天即可？」。不问与项目无关的兴趣来填轮数。澄清属于同一 run，最多 3 轮，保留同一预算；到上限提供明确的结构化修改入口，不能偷偷另起 run 继续问。

## 3. 每个按钮到底做什么

| 用户动作 | 页面行为 | 后端行为与模型开销 |
|---|---|---|
| 首次进入/浏览器刷新 | 恢复获准结果；否则普通浏览 | GET及授权，0次LLM |
| 上一位/下一位/点击人物头像 | 在当前名单移动，标明第几位 | 已有数据展示；需要下一页时用cursor，0次LLM |
| 展开作品、经历、分析图 | 展示当前人物的获准详情/已有分析 | 缺详情才按需GET，0次LLM；不抓GitHub、不重提画像 |
| 普通结构化筛选 | 明确筛选条件，清除旧cursor后重读 | 现有普通发现，0次LLM；同字段多值OR、不同字段AND，不能伪装软偏好 |
| 明确「按这些条件找搭档」 | 展示本轮条件和处理中状态 | 可信操作触发recommend；准备好结构化条件则不重复解释 |
| 回答AI澄清 | 在当前问题下保存回答 | 同run续答、版本/幂等检查；不重置调用数 |
| 「聊当前人」发送消息 | 消息标注对象/可选项目 | chat，只讨论已授权上下文，不搜索、不换名单；仍可能发生模型调用 |
| 「比较两人」 | 显示两个被选对象 | 同批次最多2人比较，不重排或替换原名单 |
| 「调整找人条件」 | 进入可编辑需求草案 | 保存草案不发模型；本人明确提交后产生新查询 |
| 「按原条件再找一批」 | 保留条件，说明优先展示未看过的人 | refresh产生新run，受累计预算约束，不保证有新人 |
| 暂时收起某人 | 从当前浏览位置移开，可撤销 | 不发申请、不全局降权；持久反馈待接时不能显示已同步 |
| 收藏 | 私有收藏状态，失败可恢复 | 复用普通收藏业务、幂等；0次LLM，不建立好友 |
| 「准备开场」 | 可编辑私有文本 | 规则模板0次LLM；明确请求AI润色才使用讨论额度 |
| 「发好友申请」 | 用户检查附言并明确提交 | 普通社交用例验证来源，成功才显示已发送；不是模型工具 |

普通浏览不是 AI 失败后的自动替代结果。AI 失败页面可以保留已授权的旧内容，并提供「去浏览本活动伙伴」，但只有本人选择才切换模式。

当前还没有正式随机批次公共入口；首版用稳定普通分页与明确的AI刷新，不把数组随机洗牌或循环取模叫「重新推荐」。随机浏览后续仍须0次LLM、固定批次和真实耗尽。

## 4. 人物舞台与详情的数据规则

### 4.1 左侧人物卡

显示本人确认的昵称/头像、可见简介、真实角色标签、本次寻求的帮助和获准活动安排。没有英文名就不显示英文名；城市未授权不补；不能把历史技能写成此次承诺。主卡上的「正在找伙伴」也需有本次意愿依据。

头像使用现有媒体引用转换；无头像用中性占位。项目没有图片时使用统一装饰图并明确其为示意，不当成作品截图或“AI读过了这个项目”的证明。卡片大小只代表阅读布局。

### 4.2 右侧内容

| 切片 | 内容来源 | 不能混淆的含义 |
|---|---|---|
| 做过的项目/经历 | 已确认项目的标题、角色、贡献、结果和链接 | 想做某项目不等于已经做过 |
| 能提供的帮助 | 技能/角色与本次contribution | 会某技术不等于本次愿意负责全部技术工作 |
| 正在探索的方向 | 本人确认的方向、兴趣、活动目标 | 兴趣不自动成为强匹配理由 |
| 本次希望的伙伴 | 当前活动seeking | 与自身技能/提供能力分开，不能反向解释 |
| 时间和协作方式 | 本次可用时段、协作方式及明确偏好 | 同城市不等于线下；时间部分重叠不等于全程可用 |
| 开场建议 | 规则或AI建议，单独标记 | 不贴“本人确认资料”标签，也不自动发送 |

根据真实资料呈现0到多个切片，首屏最多展示六个重点入口；更多项目在详情按需展开，不能截断用户完整正文。只有一条资料就展示一条，缺失提示不得指向隐藏/private字段的存在。无需为凑六张把同一事实改写六遍。

主舞台默认停在当前人物和选中切片。推荐取消5.6秒自动换走主要阅读卡的默认行为，保留可主动开启的轮播与轻微装饰动效；聚焦、输入、开详情或减少动效时停驻。装饰轮换不记录一次新推荐，也不重复累计人物曝光。

手机仍是一位人物和可展开的详情，AI打开为单面板；底部输入与侧栏共用同一草稿、发送锁和会话，不存在两套对话。键盘、触屏均可换人/展开，输入法确认不误发送，返回恢复原人物及阅读位置。

### 4.3 三种数据不能互相代替

- 展示资料：P1/P8按合法入口给当前查看者的投影，必要时可包含正常详情允许的friends字段。
- 推荐/讨论证据：只使用当前活动下明确允许的authenticated资料；不因为页面能看friends字段就送模型。
- 画像来源：原始简历/README、上传候选和问卷原答案属于本人编辑流程，不在推荐页读取或发送。

普通详情能展示的项目正文，可能超出推荐摘要的容量。先返回完整获准详情给用户阅读，再按其明确问题选择最小可引用片段；模型不知道的内容必须说不知道。实现仍需P1/P8正式端口供给，推荐不直读其私有表。

## 5. 五维合作分析应该怎样生成

五行可以固定，但每行允许“资料不足”，图上的未知节点用相同状态表达；图表只是数据呈现，不代表多个Agent正在工作。默认规则层就能生成基础对照，无需每看一个人调用一次模型。AI建议只在已有显式推荐/讨论调用中增强，不能为五行追加五次调用。

| 维度 | 实际比较 | 适合显示的内容 |
|---|---|---|
| 贡献能力 | 任务缺口对照可证实能力和本次贡献 | 能帮助哪一部分；经历只按资料原意描述 |
| 项目方向 | 双方明确的主题/问题/目标 | 相同问题或可迁移经验；推测标为建议 |
| 角色互补 | 我能提供与TA需要、TA能提供与我需要 | 双向有证据时说明互补；单向只有需求时保留待确认 |
| 投入时间 | 双方有时区的时段和投入要求 | 真实交集/不足；硬条件需要全覆盖时不得用部分重叠放行 |
| 协作安排 | 明确的远程/线下、沟通与分工偏好 | 已一致、可能冲突、需要商量的具体点 |

每行的建议合同是：dimension、status、evidence、suggestion、questions、explanation_source、basis_version。status建议为supported/partial/unknown/conflict，表达证据状态，不是人格分数。evidence应注明主体self/candidate、获准字段引用及版本；没有证据不能写supported。公共证据不含内部授权hash或原始材料。

显示标签区分「本人确认的资料」「按条件整理」「AI建议」。用户确认是资料来源，不代表平台核实其工作经历。无法支持的表达例如“领导力强”“一定合拍”“97%成功率”不能出现。

底层排序沿用可回放的相似、互补、兼容规则及明确门槛，不在本页重新发明评分。岗位角色不是性格；MBTI只可作本人明确选择的自述偏好，不做天生互补矩阵。活跃度不能替代项目依据；若以后引入，须另定真实行为来源和用途，不能把资料更新时间改名成活跃。

## 6. 对话、当前人物与需求变更

### 6.1 发送时冻结上下文

输入框上方明确显示「正在聊：林小满 / 旅行项目」，可以移除项目焦点或选择同批次第二人进行比较。每次发送绑定当时的活动选择版本、conversation/run、batch/display版本、focus_target_ids和可选focus_item_refs；这些是拟新增合同，现有turn接口不接受这些额外字段。

后端核对对象确实属于有效批次、片段属于该人、用途及版本仍获准；客户端只能传引用，不能附一份自称可靠的画像正文。用户发送后切到另一个人，晚到回复仍显示原对象标签，不改变新人物的卡片或分析。

后端已有ordered_ids可解释“第二位”，但不能知道屏幕当前焦点。昵称也不能当唯一键。作品引用要用稳定属性/项目引用，不能用标题字符串定位。

### 6.2 两种输入意图

有有效AI名单时默认「聊当前人」。例如“她具体做过什么”“我和第二位哪个地方互补”“怎么开口问时间”都属于讨论。讨论不得触发search_candidates、修改候选顺序或消耗新推荐run。

「调整找人条件」进入草案；本人点击「按新条件找人」才发refresh。若用户在讨论里说“我还是想找更懂硬件的”，助手可复述拟改条件并显示这一动作，不默默换名单。明确的“再找一批”也显示有清楚业务含义的刷新操作，不靠模型自行决定无限检索。

切换人保留本次对话，但模型仅接收与当前对象/批次相关的有限、重验过的历史。旧人旧批次的正文不能成为新人的事实依据。人格、经历、项目技术选型与合作意愿的归属问题仍需沿用文档15的失败样本验证。

### 6.3 普通浏览中的AI入口不能假接

首个接入版本只支持现有有效推荐批次内的AI人物讨论。普通浏览的人物可查看规则分析和开场模板；公共助手可帮助整理新的找人需求，不能把任意卡片ID塞入当前AI批次。

若要让“普通浏览中的任何一位”也可被AI讲解，需另增受当前活动与authenticated字段约束的单人咨询用例，并在N02协调其与AI人选历史排除政策的区别。它不能以咨询名义完成新推荐或联系动作。该扩展尚未实施，首版按钮应说明当前能力，不能收消息后答另一个人的资料。

## 7. 人数、换批与错误

### 7.1 小池和大池

30–40人或300–400人使用相同资格/硬条件。大池先后端有界召回与粗排，合并最多200、模型最多24个最小摘要、最终最多5人；普通发现可继续分页遍历合法集合，不受AI五卡和200粗排上限限制。

0人分开处理：没有可发现成员、条件未满足、没有足够推荐依据、依赖/服务失败。只有前面三项可以说明本次没有结果；服务失败不能写“没有合适的人”。1或2位就按真实数量展示；名单末尾显示结束，不用取模回到第一位伪装新人。

软偏好未满足但核心依据充分的备选可以进入结果，理由明确说明取舍。必须满足的条件、授权和活动边界不能为了凑数降低。用户可以主动移除条件或转普通浏览。

当前实现seen_ids按会话排除看过人；首版如实说明“本轮没有新的合格人选”，提供查看已有有效名单或本人明确改条件，不以新建会话清空限制。未来曝光优化是独立策略，不无限重搜同一批人。

### 7.2 结果与请求使用独立状态

建议把最后一次可展示的批次与正在执行的请求分开记录。当前源码refresh会清空current_batch，需要后端支持才能实现以下体验；不能仅靠前端缓存旧画像规避授权。

| 情况 | 应显示什么 | 必须避免 |
|---|---|---|
| 首次AI处理中 | 明确处理中、可读需求、现有普通浏览入口 | 把浏览列表标成AI结果 |
| 刷新处理中 | 旧批次经重验后可继续看，标“上次结果，新结果整理中”；同会话先禁重复AI提交 | 提前清空全部页面、或把旧结果标新结果 |
| 新结果成功 | 原子替换批次，焦点转到新名单，关联新版本 | 两个run的卡片/理由混合 |
| 新结果成功但0人 | 本轮真实不足；旧名单仅在“查看上次结果”中重新授权读取 | 用旧人填本轮空结果 |
| 刷新失败 | 保留获准旧结果与失败原因，用户决定下一步 | 自动换规则模式或自动收费重试 |
| 当前批次撤权/切活动 | 立即清除对应展示和派生解释，拒绝旧请求发布 | TTL期间继续展示、切回来复活旧会话 |
| 网络断开、结果未知 | 保留输入，按原幂等键/会话读状态，不创建新run | 把断开等同取消或成功 |
| 版本冲突 | 保留未发送文字，重新取状态并让用户选择是否基于新对象发送 | 自动覆盖条件或把旧问题发给新人 |
| 预算/提供者/历史不可用 | 具体可理解的失败状态，普通浏览由本人主动选择 | 用管理员绕过依赖或编造余额 |

撤权初期可以继续采用整批/整段保守失效；只有依赖能准确拆分并通过测试后才做局部保留，不能为了UI连续性弱化现有保护。已下载在用户端的信息无法追溯收回，要求是在服务端禁止后续读取/使用，前端获知失效后移除并停止再发送。

## 8. 进度、调用与恢复的真实口径

### 8.1 首版采用能兑现的同步交互

已有recommendation-conversations是同步扩展，首版接入可以继续使用。发送后显示“正在处理这次需求”，完成后展示真实工具记录及人数。拿不到运行中的阶段，就不逐秒播放“正在检索/已经读完/即将完成”；percent保持未知。搜索动效可以是不定进度，但不能把3.4秒动画当成功条件。

同步请求中不承诺离开后一定继续、可取消提供方请求或立即退款。可以关闭面板，后台请求的终态仍以服务端为准。遇到断网先按已有对象/幂等状态恢复；未接持久任务前不显示“后台一定会为你完成”。服务端需要读出processing/已失败/完成，崩溃且调用结果未知时不自动重发。

若正式产品要求可离开继续、持久排队、可恢复的阶段与取消，另接共享AIJob/worker：阶段事件持久化，GET进度0次模型，取消请求与供应商是否停止区分，迟到结果仍校验applicability。该项不由P1画像专用job仓储代替，也不为动画引入第二套任务系统。

### 8.2 调用边界

| 操作 | 模型额度口径 |
|---|---|
| 普通发现、规则分析、展开资料、切图、收藏 | 0 |
| 已有结构化条件的AI推荐 | 目标路径正常1次精排/表达；含修复最多2次，须验证实际装配不重复执行解释 |
| 自然语言首次找人 | 正常解释+精排2次；无澄清含修复最多3次 |
| 发生澄清的推荐run | 最多3轮问题，解释/精排/修复共享最多5次，没有第6次 |
| 当前批次讨论 | 正常1次，含修复每turn最多2次；平台预算继续累计 |
| 候选检索后为空 | 不运行精排；此前已经使用的解释调用仍记账 |

现有会话装配有20turn/40次模型尝试上限，只是当前显式配置，不是平台免费额度或可通过新建会话绕开的上限。推荐自有reservation不能替代宿主持久平台预算。model_calls_used当前保守计尝试，可能高于供应商实际调用，不直接展示为收费次数。

上表是沿用的操作预算，不是各公共路径已达到该调用数的测量结果；后续以实际出站日志、预留账本和run计数交叉核验。

召回和模型上限仍为200→24→5，单候选摘要序列化不超过768字节，完整请求含提示、schema、条件、历史和证据不超过24KiB。五维分析先由规则形成；AI只补与本轮问题相关的表达，不能为五个人的五个维度另起25次生成。

针对1–2人的项目追问，后端可以选择不同的最小获准事实包，但须保持同一字节上限及用途边界；长正文可以给用户阅读，不能绕到历史/工具结果字段偷偷扩大模型输入。超出时说明只分析了选中的证据，保留未知，不把截断当成无此经历。

### 9.1 现有入口与新增合同分开

| 普通名单 | GET /api/v1/events/{event_id}/discovery | 前端映射，来源/关系状态呈现；relevance目前是筛选命中数，不当成完整规则评分 |

| 创建/读对话 | POST活动下recommendation-conversations，GET /api/v1/recommendation-conversations/{id} | 本人最近有效会话/引导引用恢复；不产生假job_id |

| 五维解释 | 当前无等价公共接口 | 在推荐用例增加规则证据与五维视图，选择现有响应扩展或窄GET；N02确定唯一合同 |
| 收藏/申请/消息 | 共享契约已有设计，实际HumHub接入由对应专项验证 | 复用Save与社交适配，不在推荐插件建另一份社交事实 |

外壳提供同源会话、CSRF与普通API客户端；不把跨端口调通CORS、管理员REST密钥或浏览器直连模型当成最终整合。已有成功/错误信封及HTTP业务状态沿用当前合同，前端必须检查execution_status/applicability/error，不把HTTP200统一视为推荐成功。

### 9.2 建议的数据对象

以下名称是待实现的设计对象，不是现有DTO：

- PersonPresentation：目标ID、活动ID、获准身份、资料切片、来源类型和可见性/内容版本。尽量由现有公开数据适配，不长期复制一份画像。
- MatchAnalysis：查询版本、批次/目标ID、五维依据/建议/未知、规则或AI来源。相同事实在不同需求下可以产生不同解释，不能仅按target_id缓存。
- TurnContext：conversation版本、有效batch/display版本、焦点目标引用、可选资料引用。记录发送时状态，服务端验证。
- PageResume：本人+当前活动下可恢复的会话/批次引用及最小状态，不包含持久缓存的他人原始资料。

展示拼装放HTTP/前端适配层，领域用例输出事实、条件和解释对象，不输出React组件名、卡片尺寸或硬编码的六个数组位置。缺字段在DTO中有明确缺失状态，避免组件拿不存在的chapters[2][3]继续运行。

五个产品维度固定不等于原版字段固定。维度到画像字段的绑定由已审核目录/用途配置提供，资料schema或可用值变化时重新验证；UI读取可用条件，不硬编码HumHub表名。缺必要能力时给明确不可用/未知，不把空字段变成硬性拒绝全部用户。

### 9.3 插件边界

| 模块/层 | 负责 | 不接管 |
|---|---|---|
| P1/P8及画像AI | 本人来源提取、确认资料、字段目录、获准投影 | 推荐排名、推荐会话 |
| 推荐主插件 | 规则、活动/候选授权、检索、批次/会话、五维事实及结果复核 | 画像正式写入、好友/消息真相、模型SDK |
| 推荐AI子插件 | 解释需求、有限追问、池内排序与有证据的自然表达 | 任意数据库/网页读取、自动社交写入 |
| 同源React外壳 | 身份/当前活动导航、公共客户端、资源与深链 | 第二套用户或任务系统 |

## 12. 验收清单

以下是待执行的验收，不是本轮测试结果。先用内存适配器测试规则，再在专用隔离后端和同源浏览器验证，测试人物全部明确虚构；不复制共享预览或真实用户资料。

| 场景 | 应验证的结果 |
|---|---|
| 刷新页面、展开五维、切人20次 | 0次新增模型；不重抓来源；曝光去重 |
| 两个活动成员同时拥有身份 | 列表/详情/对话/旧cursor/晚到结果均绑定服务端当前活动 |
| 0、1、2、32、400人池 | 真实数量和分页；大池普通浏览能到200之后，AI仍200→24→5 |
| 资料极少/未授权 | 不填英文名、头像来源、六张项目、人格或时间；private存在本身也不泄漏 |
| 同主题但贡献重复；不同角色互补 | 理由对应任务缺口；角色差异不是天然加分，单纯兴趣不冒充项目能力 |
| 本人未提供技术能力 | 不出现“你负责AI”；允许请求用户明确或显示待确认 |
| 硬时段不满足/软技能偏好未满足 | 前者不能放行，后者仅有核心依据时明确取舍 |
| 问A的项目后切到B | 回复绑定A，不更新B分析；切人不追加检索 |
| 比较两人/重复昵称/前端篡改ID | 稳定ID与批次校验，池外拒绝，不依赖昵称 |
| 人物详情有friends字段 | 用户按普通详情可见；推荐模型和派生解释均不携带 |
| 当前人/未入选但曾被引用的人撤权 | 当前批次及历史派生正确失效；直接POST不绕过GET授权 |
| 重搜成功0人/失败/超预算 | 分清终态；旧有效结果只能标上次结果，不自动降级或新增收费调用 |
| 双击、断网、相同幂等键不同消息 | 只执行一次或冲突；不以新key盲重试 |
| 同会话另一个标签更改需求 | CAS冲突，不覆盖新条件/新批次 |
| 3轮澄清/修复/预算耗尽 | 同run累计≤5，绝无第6次修复；讨论另受turn及平台累计上限 |
| 400人读取与五维展开 | 记录真实SQL次数/扫描量、延迟和模型字节，不宣称缓存即证明提速 |
| 收藏/申请/开场 | 收藏本人可见；AI只准备文本；提交前无申请/消息，成功后由权威服务更新状态 |
| 移动端/键盘/中文输入法/减少动效 | 当前对象始终明确；返回不丢输入；关闭面板不伪装任务取消 |

真实模型验收还需逐句检查“意愿→经历”“会技术→项目用了该技术”“参与→主导”等已知语义错误。合法引用ID不等于表述正确，89项后端隔离检查通过不能替代这一质量验收。调用预算沿全站已批准的有限真实测试约定，本方案不追加付费调用额度。

## 13. 一段目标交互示例

以下全部为设计示例，不是实际对话或人物事实。

1. 用户进入页面看到本活动伙伴，说明可直接浏览或按需求找人。没有“AI已找到最合适的你”。
2. 用户输入“我做产品和访谈，想找后端一起做报名工具，周末能做最好”，点击找搭档。页面显示后端为主要需求，周末为软偏好；若用户要求周末必须全程，则明确确认硬条件。
3. 后端完成真实检索，最终仅两人有依据。助手说明“一位有接口开发经历且有周六时段，另一位经验相关但没有填写时间”，不强凑五人。
4. 用户选第二位问“她以前做过类似的吗？”发送时绑定该人和作品引用。若只有技术标签，回答“资料能支持她使用过这项技术，是否做过报名业务还需要确认”，并给具体问法。
5. 用户说“那我想再看看有上线经验的人”。页面给可编辑的新条件，用户点击按新条件找人；旧名单保留为上次结果，新run开始。
6. 本轮没有新人，显示真实不足。用户可以回看旧名单、修改条件或主动普通浏览，不将失败改写成“所有人都不适合你”。
7. 用户挑好一位，编辑开场并明确发申请，社交业务成功后显示申请已发送；AI从未代发。
