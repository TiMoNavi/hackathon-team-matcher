# 对话式找队友改版与验收

> 2026-11-12。依据用户对上一轮演示的明确否决重新定义交付。本文是改版规格与实施任务，不是已经实现的功能或新的真实模型测试。原始对话保留于文档 13；本轮不追加网关调用，不用润色后的示例冒充实际模型记录。

## 1. 上一轮为什么不通过

之前把模型限制为“条件 JSON 解析器 + 候选 ID 排序器”，提问又固定为选择题，最后用后端模板拼事实。内部协议可以这样校验，但不能直接成为用户看到的推荐体验。增加虚构用户和通过项没有解决这个缺口。

当前代码只有同一服务实例中的有限澄清、一次检索和一次重排，没有可持久恢复的找队友会话，没有推荐后的讨论入口，也没有自然推荐解释。InternalAiRun 的 15 分钟内存状态不等于持续上下文。因此本轮产品验收明确为不通过，原技术检查只保留原来的有限含义。

本次产品以项目协作为主。音乐、徒步仅在用户主动寻找兴趣伙伴、或项目确实相关时才参与，不能作为默认找队友的主要测试。测试需围绕要交付的东西、已有团队、真实缺口、时间投入、合作意愿和取舍。

## 2. 用户应该经历什么

对话分为需求理解、检索、解释、讨论、调整几个阶段，但用户不需要填写这些阶段名或知道字段代码。

### 2.1 先理解任务，问题要解决实际歧义

用户已经说明的信息不能重复问。先复述本次最关键的判断，再问一项真正会改变候选的缺口。允许自由回答，选择项只能辅助，不强制把所有人塞进“技能/兴趣/需求”三选一。

下面全部是**预期交互示意，尚非新模型实测记录**：

> 用户：我们有产品和前端，想在黑客松两天内做一个能用的校园问答工具。我能组织测试，但后端、资料处理还没有人负责。希望对方能一起落地，不只是聊点子。
>
> AI：可以再具体讲讲你们希望两天后做到哪一步吗？是能现场演示，还是需要真实用户试用？这会影响我优先找做过接口和部署的人，还是更偏模型实验的人。

这不是每次照抄的固定问题。若用户已经说明交付目标，下一问应围绕缺失的投入或协作方式；若信息足够，直接进入检索。用户说“先看看”时可按已知需求给出初步结果，同时明确未知项，不强行完成问卷。

“我能做产品”“我会后端”属于用户已有贡献；“希望别人做后端”“缺商业验证”属于对方需求。两类数据分开，不写入 self_type，也不自动修改正式画像。

### 2.2 显示真实动作与判断摘要

用户可以看到简短的判断依据和行动过程：

> AI：你们已有产品和前端，我先重点找愿意承担后端、能在这次活动投入时间的人。行业经历先作为加分项。
>
> 工具状态：正在查询本次活动中你有权查看的候选人。
>
> 工具结果：找到若干满足基本条件的人，正在比较交付经历与投入方式。

工具状态必须来自后端实际事件。只有检索成功后才能说“检索到 X 人”；数字由工具返回，不能让模型自由编造。内部调试可展开 search_candidates 的名称、条件摘要、耗时和计数；普通界面优先用可理解的动作名称。

显示的是可核验的判断摘要、工具动作和推荐依据，不展示或声称能提供模型内部逐字思维链。不能用“正在深度思考”或虚构工具调用制造工作感，也不能把未经验证的自由文本直接流式发布为候选事实。

### 2.3 推荐应同时交代适合与不足

每个人至少解释三件事：能补什么缺口、依据是什么、还需要核实什么。允许自然语言表达，证据和结果仍须通过主模块验证。

> AI：我会先和候选 A 聊。他明确愿意做后端，也有可核验的接口部署经历，比较贴近你们两天内做出可演示版本的目标。不过资料没说明他是否能负责检索效果评估，这一点最好先确认。
>
> 候选 B 有相关领域经验，但只承诺周日参与。如果周六联调是硬要求，我不会把他放进这次合格推荐。

以上人物与经历都是设计占位，不属于原 40 人实测结果。新验收必须用具有相应获准证据的合成人物，不能把这些经历临时添到旧结果中。

## 3. AI 怎么判断谁合适

评价基准是本次任务和团队缺口，不是某个人的总体好坏。先验证资格与用户明确确认的不可妥协条件，再比较下列证据。

| 判断 | 要回答的问题 | 不能直接推出什么 |
|---|---|---|
| 交付相关性 | 他的明确能力/经历能完成你们缺的任务吗？ | 标签相同不等于能独立交付；领域不同也不必然无用 |
| 贡献意愿 | 他本次活动明确愿意承担这件事吗？ | 会后端不等于愿意做后端；过去当负责人不等于这次愿意带队 |
| 可投入程度 | 时间、线上线下方式与本次安排能否兼容？ | 未填时间不能解释为全天有空；活跃也不等于有时间 |
| 团队增量 | 加入后解决了哪个已知缺口？ | 所有人都相似不等于团队更完整；差异本身不自动加分 |
| 协作方式 | 双方明确表达的分工、沟通与决策方式是否兼容？ | 不能凭 MBTI、内外向标签或措辞预测能否合作 |
| 不确定性 | 哪些判断有证据，哪些只是可迁移可能，哪些完全未知？ | 模型措辞流畅不等于结论可靠 |

活跃程度只在存在获准、定义清楚的信号时作为辅助参考，不能默认压过任务能力和合作意愿。当前也没有完成三人团队组合优化，不能把一份个人排序叫作完整组队方案。

同义词/可迁移经验不能只靠字符串完全一致。例如已确认的知识库部署经历，可能与校园问答的部署任务相关；这种相关性要标为“可迁移经验”，附来源并说明未证明教育行业经验。模型不能把“学过 Python”提升为“做过生产 RAG”，也不能把“参与过”提升为“独立负责”。

条件必须携带语义类型、允许值、归属主体、来源和用户确认情况。字段含义与可用词项由主模块目录/配置提供；新字段不自动参与，原版列名不成为硬约束。最终排序保留 rule_score 与 ai_rank，不能把任意两种分数相加或宣称合作成功率。

推荐解释需要逐项引用事实与需求的对应关系，而非引用一个 feature 后展开该字段的所有值。预计的解释结构包含 criterion、match_kind、evidence_refs、uncertainty；自由文案不能夹带这些结构未支持的能力、意愿、时间或人格判断。证据 ID 存在不代表一句自由文案必然成立，仍需语义约束与人工样本验收。

## 4. 找不到完全对应的人怎么办

| 实际情况 | 合理回答与行为 |
|---|---|
| 没有全中软偏好，但有人满足硬条件且有核心任务依据 | 可以在同一次有界检索中得到“核心满足/部分满足”分组；说明少了什么，再呈现有依据的备选，不要求用户把所有标签填得一模一样 |
| 只要放宽一项用户确认的硬要求才可能有人 | 先说明卡在哪一项，提出具体调整建议；未经用户明确改变要求，不把不合格者包装成推荐 |
| 没有任何任务相关正向依据 | 如实说明不足，帮助用户重述任务或选择调整，不凭空说后台找到合适的人，不跨活动补足 |
| 工具或模型失败 | 明确说这次查询/生成未完成；保留已确认需求和仍授权上下文，不能说成“没有人合适” |

预期语气可以是：

> 这次没找到同时有教育行业经历、又愿意承担后端的人。不过你说教育经历只是加分项，核心是先做出演示版本。工具返回的 A 能满足后端和投入时间，也有接口部署证据；他缺少教育领域经历，可以作为需要进一步沟通的备选。

这句话成立有前提：A 确实被工具检索到、满足全部硬条件、拥有对应获准事实，而且用户确实把教育经历设为软偏好。不能先写文案再编人或补证据。

近似匹配与精确匹配可以由一次受控 search_candidates 内的多路查询合并，仍总计最多 200、送模型最多 24、最终最多 5。不能先失败再由模型偷偷发第二次搜索来掩盖原条件；真正改变硬条件或重新找人，应进入显式的新推荐轮次。不同分组不能静默降低既有推荐门槛；需要调整门槛/配置时须明示版本并重新验收。

真正零候选时仍不精排。后端可以依据真实过滤摘要自然说明不足，不能为让模型“再想想”偷偷追加调用。若以后引入专门的空结果解释调用，必须先明确更新预算契约，不能借不同阶段名逃避计数。

## 5. 讨论当前名单与重新推荐的界限

| 用户当前意图 | 行为 | 是否新建推荐 run |
|---|---|---|
| “为什么推荐第二位？” | 绑定当前展示版本的第二位，重验权限，解释原依据 | 否 |
| “A 和 B 谁更适合我们两天做出 Demo？” | 对比当前获准事实、任务覆盖和未知项 | 否 |
| “有谁愿意做商业验证？这几个人怎么分工？” | 只讨论当前名单；资料未说明就承认未知 | 否 |
| “如果我们更重视部署，先联系谁？” | 在当前名单内讨论取舍；不静默改写原排序或批次 | 否 |
| “先别找新人，我们把这两位聊清楚” | 保持名单与查询，继续讨论 | 否 |
| “排除 A，再给我推荐另外几位” | 用户明确请求 AI 重新推荐；保留约束和排除项，执行新轮次 | 是 |
| “可以放宽周六线下要求，重新帮我找” | 记录用户对硬条件的明确修改并新建轮次 | 是 |
| “还有呢？” | 结合上下文判断；不明确时问是在讨论细节还是要换人 | 不自动创建 |
| 点击普通发现的“换一批” | 使用零模型 discovery-batches | 不创建 AI run |
| 刷新页面、轮询、重放消息 | 读已有状态并重验权限，不重新计费或搜索 | 否 |

不应让用户每说一句话都触发检索。反过来，明确要求新名单时也不能只把旧五人重新排序当作“新一批”。候选耗尽要说明；是否重新浏览已展示对象由用户选择，不能偷偷回填或扩大活动范围。

语义分类是模型的建议，不是执行授权。后端必须结合真实用户请求、当前状态、版本和允许操作决定是否执行；模型自己输出 refresh=true 不能重置预算。新需求若仍可在当前名单中讨论，先按用户实际问题回答，不把所有需求补充都升级成付费检索。

## 6. 持续上下文需要独立会话层

必须分清一次聊天、一次推荐和一条消息的生命周期。

| 对象（拟定内部概念） | 责任 |
|---|---|
| RecommendationConversation | 归属用户和当前活动，持久保存本次找队友需求、用户修订、待确认项、当前名单引用、已看/明确排除的候选及会话版本 |
| RecommendationRun | 一次实际推荐的查询快照、候选、排序、权限版本、次数账本和结果；创建新轮次不覆盖旧轮次 |
| ConversationTurn | 一次用户消息及获准响应、讨论/澄清/新推荐意图、幂等键、版本和实际调用账本 |

会话记住的是本次项目目标、团队已有贡献、对方缺口、硬条件、偏好、用户已说明的取舍以及正在讨论谁。它不能把模型猜测持久写成用户事实，也不能把用户转述的候选信息改写进 P1 正式画像。

发送给模型时使用经过版本校验的需求摘要、必要的近期消息，以及当前讨论对象的最小获准事实，不重送整段历史或几百人的画像。需求和候选共同遵守完整请求 24 KiB 上限；不得在压缩时悄悄丢掉硬要求、用户排除项或把猜测变为确认。

每次讨论前重验候选授权、活动和资料版本，不能因为聊天记录里以前出现过就继续发送失权字段。“第二位”绑定具体 display/batch 版本，不能在换批后指向另一个人。刷新页面恢复会话；旧批次过期或活动改变时保留用户允许保留的需求，但不复活已失效名单或沿用旧权限。

当前主包中的 InternalAiRun 无持久仓储、不能序列化，不能复用它冒充以上会话。生产持久化与共享 AIJob 尚未接通的事实继续保留。

## 7. 插件边界、调用与契约调整

主插件拥有会话状态、工具执行、授权、预算、记录和发布；AI 子插件实现需求理解、对话意图建议、重排与有据的自然语言表达。主插件不依赖 AI 子插件具体类，普通发现仍为零模型路径。继续采用项目 architecture-patterns 的领域/应用/适配器分层，不新增独立微服务。

拟增加的窄端口包括 ConversationStore、ConversationTurnInterpreter、CurrentCandidateContextReader、RecommendationExplanationProvider 和 ProgressEventSink，名称尚未发布为公共 API。工具只有后端批准的读能力，无社交写、任意 SQL、URL 或全站查人入口。

自然语言初次推荐通常仍用一次需求/条件生成、一次重排与解释。自然解释应尽量与重排合并，而不是偷偷多加一个无账本的润色调用。每轮一次 search_candidates、原 3/5 次上限和共享一次修复保持。工具进度来自服务事件，不额外调用模型制造进度。

推荐后的普通讨论目前没有共享契约。拟对显式用户讨论 turn 单独记账，并同时受会话/平台限额限制；需要确定硬上限、重试/修复及幂等后才能启用。不能用 discussion 名义补做旧 run 的失败精排，不能通过新 conversation/turn/run 重置耗尽的额度。讨论不改写已完成 run，也不成为免费的无限模型聊天。

**必须显式协调的现有文档差异：**

1. 发现推荐设计目前要求“优先封闭式问题、避免开放式问题”。用户的新要求取代这种产品体验；应改为先理解上下文、针对关键缺口自然询问、可自由回答，选项可选。问题及动作仍可在内部用结构化协议校验，JSON 不直接展示给用户。
2. 共享契约只有推荐 run、澄清和 refresh，没有推荐后持续讨论和会话存储。必须补 conversation/turn 的所有权、状态、并发、预算与恢复语义，不能在演示里假称已经具备。
3. 当前字段型证据别名不足以支撑精确自然理由，需补事实/需求对应和不确定性表达。既有最大字节、活动范围、历史资格、隐私与候选上限不因此放开。

本轮遵守推荐专项文档工作区，只在本目录记录这些变更要求，未静默改写共享契约或其他插件，也未部署新接口。

## 8. 新验收必须是持续场景

[可执行化验收用例草案](examples/conversational-teammate-acceptance_2026-11-12.json) 记录真实任务式输入、预期状态/工具行为和失败条件。状态是 not_executed，不是本轮模型测试结果。

至少包括：

- 一段 8 轮连续找队友对话：长需求、有效追问、真实检索、逐人解释、比较、需求修订、显式换人、继续讨论。
- 软偏好无法全中时，给出满足全部硬条件且有核心依据的备选，并具体说明缺失。
- 硬条件无人满足时真实不足；用户明确放宽后才创建新推荐轮次。
- “为什么 A”“先别再找”“还有呢”“换其他人”的不同动作，验证不会乱搜、乱收费或伪装新名单。
- 刷新与跨请求恢复、历史消息重放、称谓绑定、预算耗尽、切活动、撤权、旧结果晚到。
- 相同技能但不同意愿、跨领域可迁移经历、资料不足、技能自述与交付证据不一致，不只测试标签碰巧相同。

新测试要保留用户看到的自然对话、后端实际工具事件、引用依据、query/batch/run/turn 版本及调用次数。模型 JSON 和内部诊断放附录。人审必须能回答：AI 是否理解当前任务、推荐能补什么、哪里不合适、用户为何值得进一步联系。界面没有真实实现时只能验收服务事件/对话协议，不能声称已完成前端体验。

## 9. 实施顺序与当前状态

1. C0：将上一轮产品验收标为不通过，明确新场景与契约差异——本轮已完成文档修正。
2. C1：会话/turn 存储与意图路由；实现讨论当前名单、指代绑定及显式新轮次，先用内存验证，再做持久化。
3. C2：项目需求语义、本人贡献/对方需求分离、类型与值域验证，解决已发现的 self_type 错配。
4. C3：实际工具事件、有依据的自然解释、匹配/不足/未知的分离，以及同轮的可迁移备选规则。
5. C4：统一调用预算、当前名单重授权、跨请求并发与恢复；完成待调整的共享契约后装配生产端口。
6. C5：用新数据跑持续、多轮的真实模型验收，保留失败，不通过增加样本数或计数代替产品验收。

本轮未编写这些新生产能力，也未发起新的模型请求。不能将本文示例标为“真实 AI 已经这样回复”，不能将 C1–C5 勾选完成。
