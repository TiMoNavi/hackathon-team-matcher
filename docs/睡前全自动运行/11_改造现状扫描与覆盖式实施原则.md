# 改造现状扫描与覆盖式实施原则

2026-11-12（Asia/Shanghai）。依据用户本轮明确决定：取消“所有模块拿掉后仍须完美运行”，允许模块禁用和覆盖原框架逻辑。本文记录当前源码、已发布交付、隔离验收与运行部署的区别；历史回执不反向改写。本轮为只读源码扫描及现行规则更新，没有执行插件停用、数据库迁移、构建发布或删除操作。

## 1. 当前判断

项目已形成基于 HumHub 的产品定制层，不是每个插件各自携带全套页面的独立应用集合。现有领域用例、权限适配、数据复用和测试可继续保留。应取消为“任意拔除”和“双界面完整兼容”而新增的要求，让已设计的 frontend 页面接入统一产品体验。

新要求不等于把模块目录合并成一团，也不等于直接调用所有原生 disable。模块可以成为必需依赖；覆盖后的旧功能可以明确关闭，停用后的产品可以进入受控不可用状态，不要求自动恢复原生完整功能。

## 2. 状态来源与扫描范围

- 本分支基线为 `feat/overnight-integration-20261112`、`91b6d1f`，此前整合实现为 `99c84bc`。工作区存在画像、推荐和聊天团队的新成果，不能把 HEAD 当成整个工作区最新功能，也不能把工作区版本当成已部署版本。
- 扫描现行任务、模块 manifest/config/Module、构建入口、原生生命周期和各队最新回执；没有读取凭据、真实画像或消息。计数、报告通过项只引用相应来源，本轮不冒称重跑业务验收。
- 发现 15 个 `matcher-*` 源码模块；只有 `matcher-webapp` 与 `matcher-chat-ui` 带 `resources/app`。其他模块主要提供接口、用例、迁移和规则，并非缺少一个必须补建的独立前端。
- 发现一项整合风险：8113运行模块通过符号链接读取共享工作区源码。本轮只核验P1/P2/推荐/宿主链接元数据，四个均指向当前源码；没有读私有配置。并发PHP改动可能直接被运行实例加载，因此“没迁移/没重建前端”不能证明后端仍固定在上次验收版本。后续应以固定提交/不可变发布目录装配隔离实例，分别核对代码、schema与前端构建。
- 当次 Git 状态未发现 HumHub 核心、backend vendor、原生 mail 的待提交修改；这仅说明工作区差异，不证明整个仓库历史从未改过上游。

### 已经存在的原生接管

P8在请求前安装原生画像保护，聊天新源码已有live poll controllerMap替换、beforeAction及原生消息/文件写入门禁；这说明当前实现已经部分接管框架行为，并非仅在外围增加页面。依据：[P8装配](../../backend/protected/modules/matcher-profile-privacy/config.php)，聊天工作区 `backend/protected/modules/matcher-chat/config.php` 与 `Module.php`。这些钩子的安全职责继续保留，不能因为改成覆盖式便整体删除。

美术也已出现新的并行迭代：推荐原展示组件被改为可接真实数据，画像有紧凑编辑、范围与照片增量。原目录仍在，但“不迁移源码目录”不代表每个视觉文件不变，也不代表所有当前运行页已与美术一致；视觉回归与部署接收须按本轮各队版本继续验证。

## 4. 新旧原则的明确变化

| 事项 | 本次采用的原则 | 仍然保留的要求 |
| --- | --- | --- |
| 模块依赖 | 允许产品必需模块和依赖链，不再保证任意拔除后完整运行。 | 依赖明确，缺失时返回真实不可用状态，不伪造成功或放开权限。 |
| 原生页面与逻辑 | 可以覆盖、替换、重定向或关闭指定入口；不要求新旧UI双份完整。 | 原生HTML、API、文件、通知等实际可达入口均按“保留/转接/关闭”逐项验收。 |
| 核心改造 | 优先现有扩展点；扩展点不能完整落地时允许有据可查的最小核心/模块补丁。 | 单写者、上游基线、升级重放、数据迁移与针对性测试；不擅自改未交接并发文件。 |
| 前端组织 | 原美术页面保留来源目录；统一宿主或独立包按产品和运行需求选择。 | 同源身份、CSRF、主题、单导航、真实空/错态；原模板及美术验收要求不因覆盖式改造撤销。 |
| 停用与恢复 | 可只关功能/页面或使依赖功能进入维护；安全恢复不必回原生UI。 | 数据保留、必要权限继续有效；清楚区分暂停、卸载与删除。 |
| 验收目标 | 验证产品替代完整、旧入口关闭有效、保留入口正确、无关功能不受影响。 | 不再把“卸载后原框架所有业务完整”或“两个聊天UI都完整工作”作为必过项。 |

普通发现零模型、推荐/AI分包及预算边界、P8联系人独立投影、真实用户确认、事务与幂等仍有业务意义，不因取消可拆卸目标而删除。

## 5. 需要调整的工程重点

1. 统一产品路由和导航：将已批准的原美术页面作为正式呈现，集成壳只承担必要装配，避免额外维护一套简化产品页面。无需为了每包独立给每个后端模块新建前端。
2. 聊天按接管方案确定原生入口的转接/关闭清单。新读取和发送继续推进，不再等待原生完整聊天UI双轨可用；实际可达的消息、附件和通知入口仍必须安全。
3. 画像使用新私有工作流作为产品主线。旧五阶段流程可在完成迁移/引用检查后限制新建或退出正式入口，不必永久双流程并行；旧正式资料与在途状态不自动丢弃。
4. 活动成员写入收口：先登记原生邀请/加入/审批与插件兑换等真实写入口；决定转接或关闭，必要时评估受控唯一约束迁移。N05单模块锁不能代替跨入口唯一性，取消“零核心改动”后可以在正确位置修复，不先承诺删除锁/outbox。
5. 运行版本固定：整合实例从已交接的固定源码快照/独立工作树加载，不继续把活跃共享源码当稳定版本。先核对已有真实账号/来源保留，再验代码、schema与构建，不通过恢复旧空库解决版本漂移。
6. 将停用合同收敛为有业务意义的状态：产品启用、功能暂停、受控维护，以及经验证的版本恢复。减少无实际用途的兼容组合，保留数据、授权、队列不重复执行等必要边界。

## 6. 停用的实际代码含义

HumHub当前源码中的Module停用与卸载并非纯布尔开关，原生mail停用还包含消息删除路径。因此“允许禁用原框架逻辑”优先实现为不删数据的入口/能力接管；不能机械调用原生生命周期后宣称只是关闭功能。依据：[核心Module](../../backend/protected/humhub/components/Module.php)、本机已安装的 `backend/protected/modules/mail/Module.php` 与 `backend/protected/modules/mail/migrations/uninstall.php`（原生依赖文件，不随本次文档提交）。

P1/P8及聊天现有停用保护仍需要区分“防数据/权限损坏”和“为任意拔除保兼容”两种原因，前者保留，后者按本原则减负。已有隔离名单、凭据保护、原文冻结和单写者规则属于运行安全与协作边界，不是可拆卸成本。

## 7. 后续实施和交接

本次先发布原则与现状，不顺手改当前服务或覆盖各队成果。下一实施批次应产出逐入口清单，至少记录路径/后台入口、现有所有者、替代行为、保留依赖、旧入口关闭方式、数据影响和验证。按推荐原版回接、画像正式工作流、聊天入口接管分别接收，再由单一集成人更新宿主及隔离版本。

当前总任务、接入设计、HumHub合同及各专项任务顶部按此原则同步；聊天专项未跟踪于本分支，其提示只留在共享工作区供原团队接收，不混入本分支提交。旧测试和历史成功回执仍保留其原范围。覆盖式改造获准不表示已完成入口替换、主预览部署或整个业务闭环。
