## 2. 正确使用插件，而不是把所有东西塞进插件

### 2.1 安装结构与依赖

- 自有模块放在现有第三方模块目录，不直接写 `protected/humhub/modules`。模块至少有 `config.php`、`module.json` 和 `Module.php`；控制器、资源与迁移按职责增加。
- `config.php` 注册稳定的 id、namespace、class、事件和 URL 规则；它会被加载／缓存，不在其中执行请求相关业务。硬依赖使用当前支持的 `humhub.modules` 元数据并声明已验证的最低版本。以上依据 S1。
- “子插件”表示明确责任及依赖边界，可以成为必需依赖；不要求任意独立移除后产品仍完整。Yii子模块适合内部路由组织，模块是否独立安装/升级按实际部署需要决定，不为形式上的可拆卸新增包装。
- 可选推荐和 AI 不写成画像必需依赖。运行时由 capabilities 与服务端 provider/readiness 检查决定是否显示、是否可执行；缺失不返回伪造推荐。
- 现有依赖保持原样直到有针对性的迁移方案。例如 matcher-ideas 当前依赖 matcher-recommendation 和 mail，不能为了画一张“干净依赖图”擅自删除。

### 2.2 全局、Space 与权限

S2 区分全局 Module 与可按 Space／用户启用的 ContentContainerModule；容器启用有自己的生命周期。**在某 Space 启用了模块不等于任意请求获得该 Space 的数据权限**。

本产品活动仍是 HumHub Space。邀请加入、有效成员资格、当前活动选择、每次读写和异步结果授权分别处理。沿用现有 current-event 权威实现及 CurrentEventAccess 等接口，邀请适配器不得维护第二份互相冲突的当前活动。

全局画像与 Space 偏好分开；切活动不清除好友、私聊或全局画像。想法的全局身份与该想法在某活动的发布／讨论实例分开，不能跨活动复用讨论成员和消息。

### 2.3 主题不能代替业务 API

按 S4，主题和视图覆盖适合外观改动。登录、活动授权、资料确认、申请与消息是业务能力，不能靠主题模板或浏览器条件判断实现。小范围原生页面美化可以后补主题；新 React 页面使用独立文档和资产，不同时引入 Bootstrap、Clean Theme、jQuery/PJAX 壳。

## 3. 交付边界与领域所有权

| 组件 | 状态 | 拥有的职责 | 不允许承担 |
|---|---|---|---|
| HumHub user / space / friendship / mail | 已有 | 身份、原生成员／好友／会话／消息事实 | 被前端 localStorage 替代 |
| 现有 P1/P8、来源、引导、AI 模块 | 已有并扩展 | 私有来源、画像草稿、正式确认、逐项授权、领域进度 | 社交自动执行或任意全站检索 |
| matcher-recommendation / AI 扩展 | 已有并装配 | 活动约束、普通发现、对话／预算／排序 | 缺历史或预算时假装已就绪 |
| matcher-ideas | 已有并扩展 | 想法计划、确认、活动发布、讨论绑定 | 把关注、好友、讨论成员混成一种关系 |
| matcher-webapp（暂名） | 拟新增 | 同源独立 HTML、构建 manifest、导航与能力引导 | 保存第二套用户、业务事实或模型凭据 |
| 认证／邀请适配模块（拆分以契约为准） | 拟新增或扩展现有插件 | 邮箱验证码、原生登录桥接、邀请兑换 | 另建用户体系、伪造 OAuth 或跳过资格 |
| 社交用例适配模块（暂名） | 拟新增或扩展现有模块 | 来源验证、申请附言／历史、幂等、群邀请批准、消息写入编排 | 绕过 HumHub 权限或复制好友／消息真相 |

保持模块化单体；不拆微服务，不更换数据库。领域实体与规则不依赖 HTTP、ORM 或模型 SDK；应用用例通过 ports 访问原生服务、仓储、时钟、预算、队列和 provider；外层适配器实现这些接口。单元用例可使用内存适配器验证，但真实登录、消息和模型验收不能用内存适配器冒充。

## 4. React 同源插件：先证明一页，再推广

1. 保留六个用户指定源码目录及各自说明／截图归属。不复制 vendor、不改原版预览，也不先把六个工程搬家。共享 HTTP、DTO、导航与构建桥可放拟新增的 `frontend/integration/`，由单一任务负责。
2. 选择“真实登录后读取本人和当前活动”的纵向薄片。HumHub 模块控制器输出独立 HTML，注册 CSRF 元信息、经过授权的最小 bootstrap 数据及构建产物；内联 bootstrap 使用宿主要求的 nonce／安全编码，保持 CSP，不通过关闭安全头解决资产加载问题。
3. 沿用已验证的 Vite/React 模块实验方式做构建桥，但先盘点所选页面的 Next 专有依赖。路由、图片、字体和服务端组件分别适配；不能仅设置 `output: export` 就宣称六个工程可嵌入。
4. 业务组件仍留在原目录，增加小型入口或宿主适配接口；每个文档只装载一份相容的 React。不同 React/Next 版本不直接拼在一个运行时。保留原型预览作为对照，不自动升级所有依赖。
5. 按 S5 由实际前端宿主模块发布构建资源；可以统一宿主，也可使用独立UI模块，不要求每个业务插件各放一套前端。manifest 解析哈希 JS/CSS、字体、图片和动态 chunk。`backend/assets` 是发布缓存，不作为手工维护源码目录。
6. 路由前缀、深链刷新、返回/前进、会话失效、退出后返回、授权回跳及原生页面跳转均真实测试。构建产物不使用某台机器的绝对路径。
7. 样式基准继续为 Signalry；聊天布局沿用 Soho，画像沿用用户确认的 AffectUI 场景与持续角色。验证桌面、手机、日夜、减少动效及键盘操作，不只检查颜色或 HTTP 200。

首个薄片失败时在本路线内定位具体适配问题，不自行切换到常驻 Next.js 服务、iframe 拼装或整站重写；确有阻塞时记录并等待重大方案变更确认。

## 5. 认证与接口桥

- 复用同源 HumHub 会话、真实用户身份与 CSRF。请求走普通用户 API，不把管理员 REST 密钥、模型密钥或 OAuth secret 发到浏览器。
- GitHub 复用已安装 auth-github 的正式回调与账户关联能力；验证 state、合法回跳、重复登录、首次公开资料关联和失败恢复。只有首次真实登录授权才触发规定的本人公开来源导入，后续登录不重抓。
- 邮箱验证码必须是实际可投递、可校验的登录流程，不能拿邮箱密码、注册确认邮件或 2FA 模块充当验证码登录。存储散列、有效期、单次使用、限速和重复请求规则纳入同一认证契约；账户合并不能仅凭未验证邮箱。
- 先完成两种真实登录，再进入依赖它们的闭环联调；缺 secret、回调地址、SMTP 或需要本人 OAuth 操作时记录阻塞，不创建替代付费服务。凭据仅由主执行者在必要的授权连接时读取；子agent拿无敏感值的端口和测试配置。
- 使用 `/api/v1` 和现有统一错误结构；新接口先在共享契约增加“HumHub 实施映射／拟新增”条目。状态、分页和版本以服务端为准。
- 分页默认 24、最大 48、签名 cursor；不承诺随机跳页。写操作按对应合同使用 expected_version／幂等键，未返回成功不在 UI 显示“已保存／已发送”。
- 普通读取可按退避重试；登录投递、发消息、发申请、发布及授权不能因网络重试重复执行。

以上服务端权限原则以 S3 为底线；具体邮箱和会话设计是本项目拟实施合同，尚未验收。

## 6. 画像与十步旅程的适配

详见 [V4 差异报告](../用户画像收集/40_画像前端V4与后端能力对照.md)。不靠 UI 文案掩盖数据模型冲突：

- 第 3 步核对产生私有、已核对草稿快照；第 5 步明确确认才写正式展示画像。重编辑期间保留旧正式版本，不提前公开新草稿。
- 必填与展示范围是两个独立维度，不能因为必填就自动公开。沿用最新画像专项中新增确认条目默认 authenticated 的约定并明确预览，保留用户已有的明确范围；未确认来源／候选仍私有，联系方式独立读取。
- 扩展 P1 的可重复长文段落并复用 P8 逐段范围。保留每段 20,000 字及换行的产品要求，不把中文字符数当字节数；同时尊重请求、存储和 AI 输入上限。采用分对象保存／显式总限额与错误，不静默截断。
- 完整正文与匹配用结构化字段并存、带来源和版本引用；AI 提取结果是候选，不能覆盖本人确认内容。
- 画像工作流按最新N06私有核对/正式确认合同接入；旧五阶段可在完成存量引用和迁移检查后限制新建或退出正式入口，不要求永久双流程并行。轻量旅程记录只关联当前步骤、画像草稿／问题批次、想法、活动与推荐会话，不保存一份替代各领域事实的巨大前端 Draft。
- 第 8 步按对象报告已保存、冲突和待确认，只重试失败对象；第 5、8 步继续逐条可见性预览。
- 上传二进制接真实来源 API；先遵守能力合同的文件格式／大小，不让原型的 10 MiB 输入骗过后端现有 5 MiB 限制。普通浏览、切活动和改可见性不重新抓取或调用模型。
- 进度读取现有 progress 接口；percent=null 如实显示不定进度，不用定时器伪造处理阶段。普通编辑、跳过和保存退出不依赖 AI。
- 引导推荐是可选能力：插件不存在／未就绪时明确跳过，不能拖死画像流程；但本轮目标站点的真实推荐仍是独立必验任务，不能以“可选”偷减整体交付。

## 7. 好友、私聊、群聊与想法讨论

- 刷卡仅浏览／收起，明确确认才发好友申请。event_card 校验同活动资格；public_post 校验可访问帖子和作者入口，不能一律套同活动限制。
- 好友申请附言不等于私聊消息；发出为待接受，对方接受绑定 expected_version。持久发出历史供推荐排除已联系对象。
- 建群是明确用户动作；受邀者必须有真实接受动作才加入，未接受不能看到群消息或被算作讨论成员。邀请状态、批准权限、幂等与版本由普通用例维护。
- 想法发布、关注、讨论邀请／申请、接受、好友关系互相独立。一个发起人可以有多个想法，一个想法在不同活动的讨论分别绑定，不借同名群或旧会话串用成员。
- 保留既有永久会话绑定及 tombstone 规则；新增自动创建只由明确的“创建讨论”操作触发，并在事务／重试边界确保不会生成多群。
- 消息调用原生 Messenger 的授权写入路径；幂等处理断网重试。切活动后保留合法既有好友和私聊；对活动讨论按自己的资格规则重验。
- 世界广场与活动广场保持显式发布范围。活动内帖子不自动同步世界；公开帖作者入口不是全站人物搜索。

## 8. 推荐装配与有限真实调用

复用已有推荐会话与工厂，补真实申请历史、持久平台预算与 provider 装配，不绕过 readiness。普通发现／筛选／翻页／随机批次为 0 次 LLM；合并召回最多 200，送模型最多 24 个最小摘要，结果最多 5 个。候选不足如实显示，不跨活动填卡。

推荐每 run 的澄清最多 3 轮、模型调用含修复合计最多 5 次；平台预算不足明确报错，用户可自行选择普通发现，不静默降级。同步调用先如实显示“处理中”；若需求要求离开后继续、取消或细分阶段，先完成持久异步合同，不能冒用画像 job。

计划批准后的首轮真实 AI 验证仅用合成资料：一条画像 extract/questions/compose 链路加一个推荐 run，合计最多 8 次模型调用，重试也占此上限，并受已有更严平台预算约束。未有明确可用预算时不调用。不得自动补预算、换网关或无限修复；正常通过后停止额外试跑。该上限是本计划的保守执行限制，不是用户新授权采购金额。

## 9. 启停、升级、回退与原版改动

S2 和本地 Module.php 表明原生 disable 会走卸载迁移并清模块设置。现有画像模块已禁止直接 disable/remove；其维护模式保持权限保护继续加载。

| 操作 | 本项目要求 |
|---|---|
| 关闭新 UI/接管功能 | 入口明确不可用或恢复已验证版本；只在原生授权等价时选择恢复原生入口，不要求自动恢复完整原生功能；保留数据与保护 |
| 关闭可选 AI／推荐入口 | capabilities 与服务端一致；手填及适用的普通功能继续可用 |
| 维护画像／隐私 | 使用既有维护与拒绝访问机制；不能停掉授权层后暴露原始数据 |
| 真正卸载数据模块 | 另行审查迁移、数据归属和权限接管；不在无人值守默认执行范围 |
| 升级 | 隔离数据库验证首次／重复迁移与旧记录兼容，形成可重复证据 |
| 回退 | 优先撤回 UI／功能开关；涉及已写入新格式的数据，先验证兼容再回代码，不盲目 down migration |

用户已取消“去掉插件不影响原生完整功能”的目标。模块可以是产品必需依赖，暂停后相关功能可不可用；验收替代范围、旧入口关闭、数据保留及可用路径的授权，不再逐包证明任意移除后的功能等价。

修改优先采用可维护的路由/主题/服务替换和扩展点；必要时实施范围明确的核心或原模块补丁，记录上游基线、覆盖范围、数据影响和升级复验。用户已授权覆盖式改造，常规边界内实现不再因涉及原生逻辑而另行等待。更换技术路线、不可逆数据破坏或放宽权限仍不属于本次授权；不因取消可拆卸目标而整库重写。
