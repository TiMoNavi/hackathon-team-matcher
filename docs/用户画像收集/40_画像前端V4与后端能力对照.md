# 画像前端 V4 与后端能力对照

评估日期：2026-11-12。对象为 `frontend/用户画像收集——前端/app/guide`、该目录 V4 说明，以及当前 HumHub 用户画像相关插件源码。

本轮进行静态链路与接口核对，并参考既有验收记录；没有修改应用代码、数据库、部署配置或冻结稿，没有调用模型，也没有执行这套新前端连接真实后端的端到端测试。下文的补齐方案是建议，尚未实施。

## 1. 判断

**已有后端能够支撑原来的结构化画像填写主线，但尚不能完整承接这套 V4 十阶段前端。可以继续复用现有插件，主要工作是扩展资料模型、对齐确认时机、补齐完整引导编排与想法流程。**

已完成的 S1–S7.7 并没有失效。它们主要验证了资料导入、结构化字段、补问、画像合成、逐条权限、任务状态和普通发现。此前“剩余 S7.4/S7.5 前端工作”的判断适用于原任务范围，不能直接作为新版长文画像、想法对话及完整推荐社交链路的完成结论。

当前前端用本地 `Draft` 和 localStorage 保存状态，使用定时器推进模拟任务；人物与想法结果来自固定数组。文件选择仅保存文件名称等元信息，没有上传二进制。它已经表达了完整体验，但不是现有接口的真实客户端。依据：[前端状态模型](../../frontend/用户画像收集——前端/lib/onboarding/model.ts)、[本地保存与模拟任务](../../frontend/用户画像收集——前端/components/onboarding/use-guide.ts)、[文件入口](../../frontend/用户画像收集——前端/components/onboarding/profile-steps.tsx)。

## 2. 我理解的体验主线

1. 用户先提供简历、GitHub、个人网站或已有文字，允许直接手填。
2. 后端读取资料、提取候选；页面展示真实处理状态，部分失败不抹掉其他来源。
3. 用户阅读并修正初步资料，完整经历以长文保留。
4. 像 Plan 模式一样逐题补问，有选项、自由填写和跳过。
5. 汇成完整个人介绍，逐段修改、删除、设置展示范围，再确认保存。
6. 用户描述一个或多个想做的项目，或想加入的方向。
7. 每个想法独立补问，形成可以手改的完整计划。
8. 汇总画像、想法和本次 Space 的安排；分清各对象的保存状态与可见范围。
9. 用户明确发起当前活动内的寻找，页面跟随真实状态。
10. 阅读获准的人物／想法资料，选择联系、关注或申请讨论，各动作独立确认。

这条主线覆盖了画像、引导、想法、推荐和社交多个领域。十个页面不要求十个后端模块，也不意味着它们全都属于“用户画像插件”。

## 3. 逐阶段对照

| 前端阶段 | 当前可复用能力 | 距离这套前端还缺什么 |
|---|---|---|
| 1–2 提供资料、整理信息 | P3/P4/P5 的 GitHub、简历、网站／文字导入；私有来源与候选；P6 extract；来源和 AI 任务 progress | 新前端真实上传与来源关联；GitHub OAuth 配置与完整回跳验收；统一文件限额；如需退出后可靠继续导入，补后台执行与恢复合同 |
| 3 初步核对 | P1 草稿编辑、删除、稳定属性 ID、版本冲突与来源候选 | 任意长文段落模型；“仍为草稿”的页面承诺与后端 review_confirm 的确认语义对齐 |
| 4 补充偏好 | 规则／AI 的 3–8 题批次、选项、自由回答、跳过、答案和位置保存 | 前端改读真实问题 DTO；若第 3 步保持私有草稿，提问输入必须支持已核对草稿快照 |
| 5 生成并确认画像 | compose、逐条改动、独立 P8 范围与三种视角预览、显式确认、失效结果防覆盖 | 长文文档的存储／预览／确认；确认时点统一；来源与不确定提示映射到段落 |
| 6–7 想法与完善 | matcher-ideas 已有手动草稿、版本、确认、Space 发布关系和已有 Messenger 会话绑定 | 完整计划字段、build/join 语义、想法自身展示范围；每想法独立的对话、AI 任务、采纳和恢复 |
| 8 最后确认 | 全局／Space 分开保存；当前活动选择；普通发现开关；各领域已有部分版本校验 | 十阶段总会话、多个资源引用、部分保存结果与重试；完整画像／想法／活动设置的授权预览组装 |
| 9 本活动寻找 | 当前 Space 普通发现可用；推荐对话内核和同步 HTTP 已有实现及隔离接入证据 | 推荐生产依赖装配、与引导结果衔接；若要真实细分阶段与取消，需异步任务协议 |
| 10 遇见同伴 | 人物获准详情／概览；HumHub 原生好友与 Messenger 基础 | 人物与想法混合结果、匹配展示 DTO；正式申请附言／逐项发送回执；关注想法和讨论申请业务 |

普通发现不需要调用模型。推荐当前也不能概括为“完全没做”：源码主模块已为 0.3.0、AI 扩展为 0.2.0，另有独立推进的对话能力。其生产接入缺口需要依据当前源码与[推荐隔离接入报告](../推荐模块/18_隔离后端接入验收.md)判断，不能沿用画像专项早期记录里的推荐版本作全局结论。

## 4. 画像部分真正需要补齐的地方

### 4.1 长文资料需要正式的数据表达

V4 明确要求每段最多 20,000 字、继续添加段落、保留完整换行、逐段可见性；前端每段只是 `id / label / value / visibility / origin`，还能添加多个同类段落。[V4 说明](../../frontend/用户画像收集——前端/docs/10_长文资料与信息条推荐.md)

后端已有 37 类结构化资料：27 类全局字段、10 类 Space 字段。它有稳定 `attribute_id`、`display_label`、`record_group_id`、`sort_order`、逐条范围和版本，这些可以复用；但它只接受字段目录中的 key，值也必须符合对应类型。[字段目录](../../backend/protected/modules/matcher-user-profile/domain/FieldCatalog.php)、[草稿合并与校验](../../backend/protected/modules/matcher-user-profile/application/ProfileService.php)

几个会直接阻止接入的例子：

| 原型输入 | 后端现状 |
|---|---|
| 一段 20,000 字“关于我”，可继续增加同类段落 | `bio` 单值，上限 10,000 字 |
| 任意长的“作品与经历”正文 | `project` 是对象；title 必填，contribution/outcome 各最多 3,000 字 |
| “技能”“合作偏好”都作为普通字符串 | skill 要 code/label；偏好是 codes/free_text，相关自由文本一般上限 1,000 字 |
| 昵称只要非空，输入框最多 80 字 | 身份 nickname 为 2–32 字，走独立身份 API |
| 新增段落随机 field ID | 不能把随机 ID 直接当 FieldCatalog key；必须映射稳定属性 ID 与正式类型 |

**建议保留“完整展示正文”和“匹配用结构化字段”两种表达。** 完整段落保留用户原话；技能、角色、时间等继续用于查询和匹配。建立明确引用与版本关系，修改长文后让相关提取候选待核对，不让 AI 无声覆盖用户确认过的内容。

优先评估在 P1 现有属性／草稿存储中增加可重复的长文段落类型，并复用 P8；不必为每种段落创建插件或数据库列。必须同时核对字段长度、数据库列容量、草稿／历史快照、单请求总字节、条目数与预览。当前普通资料 API 单次 JSON 限 256 KiB，不能只把 `bio` 的长度改大就视为完成。

新增段落至少要有稳定 ID、类别、标题、正文、顺序、范围、版本与本人确认状态。来源引用保留在本人审核链路；对他人的投影只包含获准正文。联系方式仍走独立联系读取规则，不能因其显示成一段文字就并入无差别人物摘要。

### 4.2 第 3 步的确认时机有实际冲突

当前 [ReviewStep](../../frontend/用户画像收集——前端/components/onboarding/profile-steps.tsx) 显示“内容先留在你的草稿里”，且关闭隐私编辑；按钮只把页面带到第 4 步。直到第 5 步才把本地 `profileConfirmed` 设为 true。

后端 [OnboardingService](../../backend/protected/modules/matcher-onboarding/application/OnboardingService.php) 的 `review_confirm` 会调用 `confirmDrafts(input_drafts)`，写入正式画像，然后进入 questions；题目生成也依赖这个已确认状态。新增普通字段默认 authenticated，因此接入时若直接把按钮映射成 review_confirm，会产生与页面“草稿”承诺不一致的展示可能。当前原型没有接入，所以这不是已经发生的线上泄漏。

前端较早的[十阶段说明](../../frontend/用户画像收集——前端/docs/01_页面与十阶段说明.md)其实要求第 3 步明确提示新增确认条目的默认范围；它与目前实际页面也需要同步。

**按这版实际体验，建议第 3 步只记录“本人已核对的私有草稿快照”，供后续提问和合成；第 5 步显式确认才写入可展示画像。** 这需要改变用例输入与确认边界，不是单纯换按钮文案。返回编辑时保留既有正式版本，新的未确认修改保持私有。若产品最终决定第 3 步就正式确认，则必须先把范围提示与真实操作含义说明清楚，再接接口。

### 4.3 五阶段画像会话还不是十阶段总会话

P2 保存的是 `materials → review → questions → draft → privacy`，资源引用包括输入／输出草稿、问题批次、答案位置、资料版本和历史。它已有可靠的画像阶段保存恢复。缺的是上层完整旅程的关联：正在看哪个想法、各想法对话与任务 ID、第 8 步各对象保存结果、第 9 步推荐会话／结果批次等。[会话用例](../../backend/protected/modules/matcher-onboarding/application/OnboardingService.php)

十个界面可以映射到五个已有领域阶段，数量不同本身不是缺陷。为了跨设备、刷新和保存退出后恢复完整链路，建议增加轻量旅程记录／组合接口，引用已有领域对象；不要把前端整个 `Draft` 原样作为后端唯一业务状态，也不需要一个大事务包办全部对象。

第 8 步按对象返回保存成功、失败、版本冲突和待确认项，只重试失败对象。完成引导的标记与画像确认、想法发布、推荐执行分别处理。Space 改变时切换其专属安排并重新验证对应任务，全局资料不重填。前端隐藏“本人活动设置”不等于服务器已执行权限过滤：私有控制设置应只给本人，其他人看到的活动资料仍按各字段已确认范围投影。

### 4.4 AI 可以复用，但生成内容与长度要扩展

P6 已有 `extract / questions / compose` 三种操作：

- extract 从来源提取符合 FieldCatalog 的候选，带来源证据。
- questions 从允许的模板中选 3–8 题，允许选项、自由填写与跳过；AI 可调整问法和理由。
- compose 依据已确认资料与答案生成草稿；已有单值和同代码多值条目不能被自动覆盖，现有自然语言改写主要允许补缺失的 headline/bio。

所以第 4 步的“每次一个问题＋几个选项＋自己填写”已有基础，不需要重建聊天系统。前端当前写死三题，正式接入应根据真实批次渲染问题 ID、选项 code、scope、题数和已保存答案，而不是按界面显示文字反推字段。[P6 合同](../../backend/protected/modules/matcher-onboarding-ai/README.md)

但目前 P6 不会生成这套任意长文段落文档，也不承担想法对话。支持完整故事式介绍需要新增段落候选与证据映射、本人采纳、编辑后作废等约定。现行 AI 输入上限 128 KiB、结构化输出上限 64 KiB；多个 20,000 字中文段落不能直接整份塞入一次请求。正文保存可以完整，模型按需使用相关片段，使用范围与结果覆盖边界明确说明。[校验限额](../../backend/protected/modules/matcher-onboarding-ai/domain/OutputValidator.php)

### 4.5 阶段状态已做，需要接入和扩大覆盖

已提供三个紧凑读取入口：

- `GET /api/v1/onboarding/sessions/{id}/progress`
- `GET /api/v1/me/profile/ai-jobs/{id}/progress`
- `GET /api/v1/me/profile/sources/{id}/progress`

包含 state、phase、message、poll_after_ms、next_actions、updated_at；会话还有问题计数、阶段、任务摘要与版本标记。AI 任务区分 execution_status 与 applicability；superseded/revoked 不能继续当成有效成果。percent 当前为 null，表示没有可靠百分比，不是漏了接口。[ProfileProgress](../../backend/protected/modules/matcher-user-profile/application/ProfileProgress.php)、[SessionProgress](../../backend/protected/modules/matcher-onboarding/domain/SessionProgress.php)

这些足够驱动画像提取、补问准备、合成的等待状态。新前端需移除“每隔固定时间推进一个业务阶段”的模拟逻辑，不能把模型内部进展编成已完成的小步骤。打字、轮播、跳过动画仍可在前端完成。想法任务与推荐异步任务则需要各自接入真实状态，不能冒用画像 job ID。

### 4.6 来源导入有基础，部署与持久执行要区别看

- GitHub 本人关联检测、来源历史标记和首次引导自动导入的旧界面逻辑已有；真实 GitHub OAuth 配置与完整登录回跳尚未由本专项验收。新前端应复用 capabilities 和关联信息，不让已关联用户再次填写 GitHub 用户名。普通重新登录不重抓。
- 原型允许选择 10 MiB 文件，后端简历模块为 5 MiB、最多 30 页，接受 PDF/DOCX/MD/TXT。先以服务器能力合同限制输入，或另行扩容和验证。
- 来源导入先保存 running，再在同一 HTTP 请求里调用 reader，最终返回结果；这不是已实现的通用后台导入队列。与已存在的画像 AI worker 区别开。若要求上传后马上拿任务 ID、退出后继续、失败后恢复，需要补持久任务与执行回收。

依据：[简历 reader](../../backend/protected/modules/matcher-resume-import/application/ResumeSourceReader.php)、[来源用例](../../backend/protected/modules/matcher-user-profile/application/ProfileSourceService.php)、[旧界面首次 GitHub 导入](../../backend/protected/modules/matcher-onboarding/assets/flow/sources.js)、[S7.7 已验收范围](38_S77_AI组合验收报告.md)。

## 5. 完整十步中另两个领域的缺口

### 想法计划与引导

现有 matcher-ideas 不是空壳：有私有草稿、读取、修改、确认、正式想法、Space 关联和显式 Messenger 绑定。但正式字段只有 title 与 summary；title 最多 160 字，summary 最多 2,000 字。私有 raw_text 限制的是 **20,000 字节**，不能等同 20,000 个中文字符，也不能把完整计划藏入 raw_text 后就称为已经支持展示、权限和结构化编辑。[IdeaDraftService](../../backend/protected/modules/matcher-ideas/application/IdeaDraftService.php)

前端需要的是 build/join、问题描述、目标对象、第一步／最小尝试、阶段、所需帮助、完整正文与展示范围，加上独立的 messages、revision 和处理状态。建议先扩展无 AI 的想法草稿／计划模型，再加可选的想法辅助插件，单向依赖想法主模块。多个想法的任务、失败、重试、版本与采纳分别管理。

P8 的“本人参与某想法／活动的关系是否公开”与“想法计划本身公开给谁”是两个对象，不能互相代替。目前控制器还明确拒绝开启讨论流程并返回 `open_to_discussion=false`。关注想法、申请加入讨论、批准、会话成员变更仍需业务用例；已有会话关联不等于这一整套流程已经完成。[Ideas API](../../backend/protected/modules/matcher-ideas/controllers/ApiController.php)

### 推荐与联系

当前普通发现与获准人物概览可以复用。推荐对话有持久会话、条件确认、明确推荐／换批和同步 HTTP，并有真实 HumHub 隔离接入证据；完整申请历史、统一持久预算和共享异步队列协议仍是开放依赖，现有工厂会检查这些条件。[组合工厂](../../backend/protected/modules/matcher-recommendation/adapters/composition/NativeConversationFactory.php)、[接入报告](../推荐模块/18_隔离后端接入验收.md)

第 10 步人物／想法混合卡片尚不能直接照抄本地 `MATCHES`。推荐公共 item 当前主要是 id、reason、gaps、rule_score、ai_rank，人物详情要再通过获准投影组装；想法候选与其推荐展示也需独立定义。开场问题与可贡献事项只能根据获准且确实存在的数据生成，资料不足允许留空。[推荐输出](../../backend/protected/modules/matcher-recommendation/adapters/conversation/ConversationHttpView.php)

HumHub 原生有好友申请／接受与 Messenger 基础，不能说“完全没有好友或私聊”。但原生好友控制器并不是当前前端要求的“选单人／多人、预览首句话、正式提交、逐项返回结果、持久发出历史”的完整接口。应在普通业务用例中接上来源授权、幂等与版本校验，并区分申请附言、正式消息和好友接受。[原生好友入口](../../backend/protected/humhub/modules/friendship/controllers/RequestController.php)

“想认识名单”和“移出这一次列表”如果只需本机保存，可继续做前端状态；只有要求跨设备恢复时才需要服务端收藏记录。它们不自动建立好友或讨论关系。

## 6. 哪些只是适配，不应当成后端重做

| 差异 | 接入方式 |
|---|---|
| 前端 self、后端 owner | 预览参数映射；实际他人访问仍由 P8 授权 |
| 前端 website、后端 web | 来源类型映射 |
| 文本昵称放在 fields 中 | 使用独立身份 API；昵称不是任意可隐藏的普通段落 |
| 前端 role/time 字符串，后端 event_role/event_time_commitment 对象 | 定义确定性的输入与显示映射，或先保存为明确的叙述块；无 AI 时也能完成 |
| 当前活动 demo 字符串 | 读取服务端 current-event 与真实 Space 成员资格，不能只改本地 eventId |
| 真实昵称／头像／项目摘要与演示卡不同 | 使用当前身份、媒体和获准概览接口；没有真实图片时给占位 |
| Next.js 独立页面与 HumHub 会话 | 明确同源代理或可信 BFF、Cookie、CSRF、错误与幂等合同；普通用户 API 已存在 |
| 目录、宽正文、专注编辑、滚动、主题、角色动画、信息条轮换 | 前端实现，消费已获准数据；不需要重写后端 |

现有 [普通用户 API](../../backend/protected/modules/matcher-user-profile/controllers/ApiController.php) 已使用登录会话与 CSRF 校验。接入独立前端不意味着要改成管理员 REST 调用，也不能把权限过滤全部放在浏览器。

## 7. 建议的实施顺序与验收边界

这不是本轮已授权执行的任务清单，后续实施时可据此细化 task。
