# 原生数据库复用与字段落地规划

> 更新日期：2026-11-11。依据本地 HumHub v1.19.4 源码制定。S1 建立 31 个原生字段及四张核心表，S2/S3 补齐普通资料、联系方式、独立隐私和编辑器；S4 继续复用并新增三张问答/进度表。历史证据见 [S1](06_S1字段实现报告.md)、[S2](08_S2实现与验证报告.md)、[S3](10_S3实现与验证报告.md) 报告，S4 验收与部署状态见 [主报告](13_S4实现与验证报告.md)。

## 1. 本轮确定的存储方案

沿用当前 HumHub 数据库和用户身份，以原生 user/profile 保存适合它们的当前资料。S1 已新增 **4 个原生资料字段和 4 张插件核心表**；S2–S4 继续复用，承载基础信息、多条记录、确认版本、草稿和可选联系方式。S4 另以迁移加入 P1 的问题批次/答案和 P2 的进度会话，扩展表共 7 张，实际升级状态见 S4 主报告。P8 matcher-profile-privacy 独立负责隐私策略与投影，字段值和逐条范围仍由 P1 的现有表保存。

| 数据 | 当前权威存储 | 复用方式 |
|---|---|---|
| 账号、用户名、头像、时区 | 原生 User、头像资源与 user.time_zone | 通过现有用户关联和适配器读写 |
| 简介、城市、姓名等单值资料 | 原生 profile 对应列 | 当前值继续保存在原列 |
| 昵称、年龄段、MBTI、长期合作期待 | profile 新增 matcher_ 字段 | 使用原生 ProfileField / fieldType 注册 |
| 技能、方向、角色、经历、活动偏好 | matcher_profile_attribute | 每条拥有稳定 ID、结构化值和展示范围 |
| 资料版本与并发控制 | matcher_profile_state / revision | 维护当前版本号与不可变历史快照 |
| 编辑中的资料 | matcher_profile_draft | 普通资料页与引导共用 |
| 逐条可见性与获准展示 | attribute.visibility、state.permission_version；P8 策略服务 | 三种范围共用现有元数据，读取时验证当前入口与关系 |
| 保存的问题与答案 | matcher_profile_question_batch / question_answer | P1 保存固定问题、选项、单答案版本和批次版本 |
| 引导步骤与恢复 | matcher_onboarding_session | P2 保存资源引用及进度版本，资料和答案继续使用各自权威记录 |

同一个值只有一个当前编辑位置。版本快照用于历史读取、差异和确认记录；读取当前资料时，由统一服务组合原生值与扩展条目。

## 2. 已核实的原生机制

- `profile` 以 user_id 为主键，一位用户一行；`profile_field` 保存字段定义，`profile_field_category` 保存分类。资料值实际保存在 profile 的列中。
- 添加字段的原生顺序是保存 ProfileField，再保存对应 fieldType。字段类型负责创建真实列和刷新 schema 缓存。
- Text/Select 创建 VARCHAR(255)，TextArea 创建 TEXT；长度、枚举和必填由字段规则进一步约束。
- 原生显示名支持 displayNameCallback，头像通过用户资源关联提供；user.time_zone 是现成时区字段。
- CheckboxList 使用文本中的多行选项存储。逐条权限与多条经历采用稳定条目记录，便于独立编辑和匹配查询。

源码入口见文末。迁移采用插件管理的版本化脚本，现有运行库继续承载这些数据。

## 3. 冻结简介中的字段如何落地

| 原稿字段 | 逻辑键 | 计划存储 | 编辑与展示 |

| 昵称 | nickname | profile.matcher_nickname | 2–32 字符，作为本人确认的显示名 |
| 姓名 | real_name | profile.firstname + lastname | 复用原值，按一条真实姓名管理展示范围 |
| 年龄 | age_range | profile.matcher_age_range | 以可选年龄段填写；已有生日资料可在本人选择后提供派生年龄视图 |
| MBTI | mbti | profile.matcher_mbti | 本人选择，可留空 |
| 方向 | direction | 扩展条目，每条一个方向 | 稳定编码、名称与可选说明 |
| 学校 | education 的学校信息 | 扩展教育记录 | 学校概览引用本人选定的教育记录 |
| 技能 | skill | 扩展条目，每条一项技能 | 编码、名称、可选本人水平和说明 |
| 一句话自述 | headline | profile.title | 本项目将原生单行 Title 映射为一句话自述 |
| 在找 | seeking / event_seeking | 全局用 profile.matcher_seeking；活动用扩展条目 | 长期期待和此次需求分别填写 |
| 角色 | role / event_role | 扩展条目 | 能够贡献的角色与本次愿意承担的角色分别保存 |
| 获奖情况 | award | 扩展条目，可多条 | 名称、主办方、日期、描述 |
| 学业经历 | education | 扩展条目，可多条 | 学校、专业、学历、日期与说明 |
| 项目经历 | project | 扩展条目，可多条 | 标题、个人角色、贡献、技术、成果和链接 |

完整姓名模式将用户输入保存在 firstname、lastname 留空；已有拆分姓名保持原值，编辑时按该记录原有模式呈现。S1 已将姓名输入总长调整为 120 字符，并调整 firstname/lastname 的字段校验配置；原生初始配置分别为 20/30 字符，物理列继续复用。两列共享 real_name 的可见性策略。原生姓名必填配置已调整为可选，最小展示身份由 nickname 的业务规则校验。

headline 保留逻辑键，通过适配器映射至 title。原生初始校验长度为 50，S1 已调整为 160；数据库列仍沿用原生 VARCHAR(255)。角色依据 role/event_role 的确认条目读取。

## 6. 第一批 4 张核心扩展表

以下是 S1/S2 建立、S3/S4 继续复用的物理结构。逻辑契约仍使用 GlobalProfile、ProfileVersion、ProfileAttribute、EventProfileContext 和 ProfileDraft。P8 的首个迁移管理原生展示标志与旧资料审核，保持四张核心表和 31 个原生 ProfileField 的数量。S4 问答与会话的三张新增表见第 6.6 节。

新增表的 id/attribute_id/state_id/current_revision_id 统一使用 UUID 字符串（CHAR(36)）；user_id、space_id 按原生主键的实际整数类型建立外键。修订计数使用 BIGINT，scope_key/field_key/native_binding 使用 VARCHAR(64)，状态和可见性使用受控短字符串，结构化值与快照使用 JSON，时间使用 UTC DATETIME(6)。关联列保持相同字符集和排序规则。

### 6.1 matcher_profile_state

每位用户的每个资料范围一行。字段为 id、user_id、scope_key、space_id、revision、permission_version、current_revision_id、identity_version、confirmed_avatar_ref、created_at、updated_at，以及 S2 增加的 projection_pending。提交后缓存刷新失败时保留该标记，后续提交或重试可以恢复。

- scope_key 由服务端根据范围生成，使用非空的 `global` 或 `space:<id>`，`unique(user_id, scope_key)`；global 对应空 space_id，活动范围对应实际 space_id。
- 全局行对应 GlobalProfile；活动行对应 EventProfileContext。
- space_id 外键引用原生 Space；user_id 引用原生 User，整数类型与原表一致。
- identity_version 与 confirmed_avatar_ref 仅用于全局行，分别管理昵称/头像编辑版本和已确认头像资源引用；资料确认版本由 revision 管理。

### 6.2 matcher_profile_attribute

一条当前资料或策略记录一行。字段为 attribute_id、state_id、scope_key、field_key、storage_kind、native_binding、value_json、display_label、record_group_id、sort_order、visibility、confirmation、last_confirmed_at、schema_version。scope_key 是与所属 state 一致的约束键，通过复合外键保证一致，并在数据库层约束 native 条目仅属于 global。

| storage_kind | 当前值在哪里 | 表内保存什么 |
|---|---|---|
| native | 字段目录指定的 user/profile 列 | 稳定 ID、绑定名、策略与确认元数据；value_json 为空 |
| inline | 本行 value_json | 技能、经历、活动偏好等结构化值及策略 |

native_binding 采用字段目录中的稳定名称，例如 headline、real_name、timezone、primary_portfolio_link，由 FieldCatalog 唯一映射到原生列。native 条目归属 global state，活动条目采用 inline。`unique(state_id,native_binding)` 约束单值绑定；inline 条目的 native_binding 为空，同一个 field_key 可以有多条。

每个当前条目以 attribute_id 唯一标识。单值扩展条目的数量由字段目录校验；新记录得到新 ID，内容编辑保留原 ID。record_group_id 可组织需要分开设置可见性的经历子项。

昵称、头像的展示身份由身份用例管理。昵称值位于原生 profile，头像使用原生资源机制；数据库保存其已确认引用与身份版本。普通资料可见性用于其余资料条目。

昵称在条目表中另保存 native_binding=nickname 的身份确认元数据。显示名适配同时要求 global state 的 identity_version 大于 0，以及该身份条目的 authenticated、confirmed 和确认时间。这样昵称确认与单独确认头像可以分别判断。

### 6.3 matcher_profile_revision

保存主键 id、state_id、revision、snapshot_json、schema_version、confirmed_at、created_at，并以 `(state_id, revision)` 唯一。state.current_revision_id 指向本 state 的修订，使用复合外键约束并在写入时验证对应关系。

snapshot_json 记录该版本的条目值、稳定 ID、可见性与确认时间，并为后续来源引用保留扩展位置。内容或可见性确认均生成新的资料修订，范围变化同时推进 permission_version。S3 的仅范围、排序或分组变更保留原内容确认时间；实际内容修改及显式重新确认更新 last_confirmed_at。读取历史版本时使用该快照，当前读写使用原生值和当前条目，披露仍验证当前权限。

因此逻辑上的 `(version_id, attribute_id)` 唯一性由快照写入校验与版本仓储保证，历史快照存储适配器负责返回指定版本条目。

### 6.4 matcher_profile_draft

保存 id、state_id、draft_kind、base_revision、base_identity_version、draft_version、fields_json、origin、initiator_id、status、created_at、updated_at，以及 S2 增加的 confirmation_hash、confirmed_revision。draft_kind=profile 用于普通资料编辑、引导和处理建议；identity 承载头像/二维码候选元数据、身份变更记录与 HTTP 创建收据，由 origin 区分。origin 和 initiator_id 记录编辑来源及实际操作者。仓储按类型提供对应接口。

更新草稿比较 draft_version。资料确认同时锁定 state 与 draft，验证请求 expected_version 等于当前 draft_version，并验证 base_revision 等于 state.revision；身份确认比较 identity_version 与候选资源归属。新的字段和条目先保存在草稿中，再通过确认事务写入正式存储。

### 6.5 字段定义与后续表

原生简单字段继续使用 profile_field 与 profile_field_category。复合字段的值 schema、数量、必填场景、显示顺序和物理绑定由版本化 FieldCatalog 提供。当前 37 类普通字段的 required_when 均为空；普通编辑页面据此生成可选字段及记录内部的结构化输入。

P8 使用原生模块设置保留原 ProfileField 展示/检索标志和显示名格式，迁移将通用 visible、searchable、directory_filter 出口交给获准投影管理。原生字段内容继续保存在原列。

S4 已实现 question_batch、question_answer 和 onboarding_session 三类记录及对应迁移。S5 已实现来源、快照及读取任务三张表，片段和候选证据随私有快照 JSON 保存；S6 接入模型任务。这些记录继续保存在同一数据库。

参与的想法和活动采用只读关系摘要端口。Space 的名称、简介和正式成员关系可直接适配；Messenger 当前只有会话标题，后续通过想法业务的正式简介、message_id 与 space_id 关联生成摘要。S1 为这些关系准备接口，关系记录的建设与实际披露在对应业务阶段完成。

### 6.6 S4 三张工作流表

| 物理表 | 所属 | 主要字段与约束 |
|---|---|---|
| matcher_profile_question_batch | P1 | UUID id、owner_id、可空 space_id、version、profile_versions_json、questions_json、generation_mode、schema_version、policy_version、创建/更新时间 |
| matcher_profile_question_answer | P1 | UUID id、batch_id、question_id、单答案 version、answer_type、selected_options_json、free_text；unique(batch_id,question_id) |
| matcher_onboarding_session | P2 | UUID id、owner_id、scope_key、可空 space_id、version、stage、max_stage、status、resource_refs_json、创建/更新/完成时间 |

问题批次记录两种资料范围的确认修订和稳定问题。每个答案独立使用 expected_version，修改答案同时推进批次版本。会话只存草稿/批次引用、步骤和版本；本人手工资料仍写入现有 ProfileDraft。scope_key 使用 global 或 space:ID，外键引用原生 User/Space，答案外键引用问题批次。

S4 的 ProfileWorkflow 端口统一同库事务，按 global → Space 固定顺序锁定资料状态，再锁定会话和批次。最终确认在一个事务中完成两份范围草稿；任一范围写入失败时，资料、快照、草稿与完成进度一起回滚。已确认内容变化时旧综合返回冲突，由本人主动重新核对；旧草稿、问题与答案继续保留。

规则题库与模板通过 QuestionProvider/ProfileComposer 端口接入。当前仅使用 rules 提供者，全部跳过可以产生空操作草稿并完成。37 类普通字段保持可选；全局习惯复用，本次目标、角色、时间和安排依 Space 分开。完整 DTO 与 HTTP 动作见 [S4 实施约定](12_S4实施约定.md)。

## 7. 确认、原生编辑与查询

资料确认用例在同一个数据库事务中：验证用户与范围 → 锁定资料及草稿 → 检查草稿版本和基础资料修订 → 写原生单值及扩展条目 → 推进修订与适用的权限版本 → 写确认快照 → 更新草稿状态。提交后更新搜索与缓存投影。

昵称/头像编辑使用独立 identity_version。头像先上传到本人版本化候选资源，元数据通过 identity 草稿关联；PATCH /me 校验候选归属和身份版本后切换 confirmed_avatar_ref。资源文件在确认前就绪，事务提交后刷新原生头像投影；可通过原生 EVENT_INIT_PROFILE_IMAGE 适配资源读取。文件写入、数据库确认和投影更新分别具备重试及恢复步骤。

本人普通资料编辑、引导确认和导入确认统一进入该用例。管理员对授权字段提出修正时生成 origin=admin_proposal 的本人待确认草稿，实际采纳仍由资料所有者提交；管理操作保留操作者与时间记录。用户时区编辑通过同一字段适配登记相关变更。

昵称显示通过 displayNameCallback 读取已确认的 matcher_nickname。旧账号尚待确认昵称时，使用稳定的中性显示值 `成员·{user.guid 的末 8 个字符}`；本人确认后切换为正式昵称。需要最小展示身份的社交操作按 nickname 确认规则验证。

S3 资料投影每次验证当前可见性、有效好友关系、合法入口与 Space 资格，已接通原生个人页、头像卡、目录/搜索摘要和 REST 等适配。已启用模块、兼容文件及具体核验边界见 [原生出口登记](11_S3原生出口适配登记.md)。后续 MCP 可通过相同的资料服务和入口验证读取获准结果。

基础编辑器 /matcher-user-profile/editor/index 已复用资料用例，支持全局/Space 分区、多条记录、草稿恢复、分批确认与三种视角预览。页面预览只模拟本人当前资料或已保存草稿，实际对外读取使用已确认条目；联系方式具有独立读取用例与展示区。

S4 的 /matcher-onboarding/flow/index 通过同一资料用例完成输入、核对、补问、编辑和范围确认。P8 提供三种预览；onboarding 草稿和普通手工草稿分别保留，均在明确确认后写入同一普通资料。真实页面操作见 [网页验收](14_S4真实网页验收.md)，最终验收与部署见 [S4 主报告](13_S4实现与验证报告.md)。

匹配查询先取得当前活动候选用户，再读取其确认且获准的字段。第一批索引为：

- state 的 `(user_id, scope_key)` 唯一索引与 `(space_id, user_id)` 查询索引。
- attribute 的 `(state_id, field_key, sort_order)`，以及 native_binding 的单值唯一约束。
- 单编码条目从 value_json.code 派生 value_code 查询列，按 field_key、value_code、visibility、state_id 建索引；派生值随权威 JSON 更新。
- revision 的 `(state_id, revision)` 唯一索引；draft 的 `(state_id, status, updated_at)` 索引。

role_codes、skill_codes、codes 等多值字段按完整数组匹配；首期通过活动资格过滤后的受控 JSON 查询/规则比较处理，再按契约分页返回。时间段采用完整起止区间比较。使用 300–400 人活动样例记录实际查询耗时，再完善相应索引。

## 8. 迁移与已有资料

1. 只读记录实际表前缀、数据库版本、列类型、字段配置和匿名统计，保存迁移基线。
2. 用模块迁移创建分类、4 个新增原生字段、核心扩展表及索引。字段注册顺序包含 ProfileField 与 fieldType 两次保存。
3. 以稳定绑定为现有单值创建元数据，已有可核验的确认与展示选择按原语义映射；待核对资料进入本人可见的编辑草稿。
4. 为姓名模式、title 长度、昵称候选和时区关联提供转换与确认流程。已有存储值保持可追溯。
5. 接通普通资料用例和全部读取入口，完成兼容验收后开放用户编辑。

重复执行迁移按字段内部名、类型、绑定和版本检查。字段与用户资料的保留策略由插件生命周期管理，业务功能开关用于暂停处理。升级和恢复演练纳入独立验收。

S3 已实现的旧资料适配由 PrivacySchemaInstaller 与 LegacyProfileImporter 承担。有效原生候选以 origin=migration、visibility=private 进入本人审核草稿；已有编辑草稿时保留当前工作，候选继续供本人主动采纳。已有确认条目和范围沿用原值，用户确认后才形成正式资料。原生 profile 行缺失时，受管资料和昵称写入返回冲突并回滚。主预览升级与最终验收结论记录在 [S3 主报告](10_S3实现与验证报告.md)。
