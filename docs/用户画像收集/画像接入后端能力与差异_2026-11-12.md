# 画像接入后端能力与差异

静态核对日期：2026-11-12。本文以当前工作区源码、N06 合同和前端 V5 文档为准，记录供接入规划使用的后端能力和差异。没有修改应用代码、数据库、部署或冻结稿，没有连接服务、运行应用测试或调用模型。文中的新字段、新状态和流程都是**拟新增/拟调整**，不代表已经实现。

范围只覆盖身份与普通画像、来源、问题、合成、隐私投影和引导会话。想法、推荐、聊天及社交动作的实现分别交由对应团队；本文只指出它们与第 8 步的引用边界。

## 当前能力基线

静态读取到的插件版本为 P1 `matcher-user-profile` **0.10.1**、P2 `matcher-onboarding` **0.4.0**、P8 `matcher-profile-privacy` **0.2.0**、P6 `matcher-onboarding-ai` **0.1.0**。历史任务中记载的 P1 0.10.0 是之前验收基线，不能代替当前模块清单版本。阶段完成范围与未完成项以[专项任务入口](task.md)及[现有 V4 对照](40_画像前端V4与后端能力对照.md)为背景；40 是 V4 对照，不能视为已核对 V5。

| 领域 | 当前可复用能力 | 本次接入的边界 |
|---|---|---|
| 身份 | P1 独立昵称/头像读写、`identity_version` CAS；头像经本人上传，5 MiB、JPEG/PNG/WebP 校验，服务端生成 1024px 主图和 256px 缩略图，上传回执未确认，之后显式写 `avatar_ref`。 | V5 个人照片位对应身份 `avatar_ref`，不能复制到普通资料或自动取 GitHub 头像。上传后绑定身份仍需明确确认；不能把照片上传成功当作画像已确认。 |
| 普通画像 | P1 字段目录、逐属性稳定 `attribute_id`、版本化草稿、上/删操作、可见范围、排序与分组；新普通确认条目默认 `authenticated`。全局与 Space 属性分别存储。 | 字段目录仅接受已登记 key，属性不能在既有记录上改类型；目前没有 V5 自定义标题/任意长文段落的通用内容类型。 |
| 来源 | P1 私有来源与快照、进度、刷新/删除、候选采纳；P3/P4/P5 读取器按实际启用能力提供 GitHub、简历、网页/粘贴读取。5 MiB 简历上传已存在。 | 来源原文、未采纳候选和草稿属于本人私有资料；浏览、改范围、切 Space 不抓取或重跑。不得把来源候选或 AI 建议直接写成正式资料。 |
| 问题与合成 | P2 五阶段会话、规则题库、问题/答案批次、位置保存、规则合成与 P1 输出草稿；可选 P6 extract/questions/compose 任务及 progress。读状态本身不调用模型。 | 题目输入和合成当前依赖正式确认资料；不能直接满足第 3 步“私有核对后继续补问”。自由回答上限 1,000 Unicode 字符，不等于 V5 长文上限。 |
| 隐私与关系 | P8 提供本人视角预览、登录用户/好友模拟预览、联系方式单独读取，以及 Space 内 `activities` / `idea_groups` 逐对象共享设置。访问时依当前合法入口和真实授权重验。 | 预览是本人模拟，不授予访问权。第 8 步需按对象回执组合；不能把合并预览当成写入授权，也不能绕过 Space、成员身份或对象所有者校验。 |

## 第 3、5、8 步的确认边界

N06 合同明确：第 3 步仅本人私有核对，第 5 步才正式确认，第 8 步逐对象确认；重新编辑期间保留旧正式版本。[合同中的既有 `review_confirm` 风险与要求](../睡前全自动运行/04_HumHub实施合同.md#L104)是此处的实施依据。

当前 P2 的 `PUT /api/v1/onboarding/sessions/{id}`，`action=review_confirm` 会在 `OnboardingService::update()` 的对应分支中调用 `confirmDrafts()`，提交输入草稿并推进问题阶段。P2 的问题准备和 P6 questions/compose 也以已确认画像版本为输入。因此，将 V5 第 3 步直接绑定此 action 会提前提交正式画像；换页面文案无法解决这个状态语义冲突。原型尚未接入真实后端，本次没有观察到线上误确认。

建议 N06 为旧协议保留显式版本边界，并为新旅程增加私有核对引用：

| 步骤 | 拟采用状态语义 | 现有能力与缺口 |
|---|---|---|
| G03 私有核对 | 保存本人草稿，冻结一个供后续补问/合成使用的私有核对快照引用。引用需绑定草稿版本、来源/候选版本、全局及当前 Space 的正式基线版本和会话版本。修改任一输入即使快照失效。 | P1 草稿、版本和本人草稿预览可复用；P2 `review_confirm` 是正式确认，不能复用为私有核对。P8 可做视角预览，但其 draft preview 不是不可变的旅程快照。**拟新增**专用快照/回执与当前性检查。 |
| G04 补问 | 每题答案保存到当前问题批次；批次显式引用私有核对快照版本。答题、跳过和恢复均由服务端版本控制。 | P1/P2 已有问题批次、回答、位置与并发控制；需让问题生成与 P6 输入消费私有核对内容，而非要求先正式确认。长故事不能塞入现有 1,000 字回答字段，应保留为画像段落草稿。 |
| G05 正式确认 | 用户检查最终画像段落、身份与范围后，确认当前输出草稿；写入正式画像并生成可重试的确认回执。全局与 Space 分别检查 expected revision，不能由模型或客户端代确认。 | P1 `confirmDraft` 已支持 draft version、base revision、stable attribute IDs、选择性逐项确认和幂等回执；P2 `complete` 在既有工作流事务中确认其输出草稿。新实现应保留这一已有事务边界，补充段落类型和旅程回执；身份有独立 `identity_version`，不能把跨领域完成原子性当作现成能力。 |
| G08 逐对象确认 | 对每项资料、想法、活动设置分别显示保存/确认状态、版本冲突、拒绝或待处理回执；只重试失败对象。 | P1/P8 和其他领域有自己的写用例，应由轻量旅程状态保存对象引用、版本和结果。不要接受客户端任意写 `resource_refs`，不要让画像会话复制想法/活动事实，也不要把引导结束等同于发布或发起推荐。 |

建议的**拟新增**私有快照概念字段可含 `review_snapshot_id`、`review_snapshot_version`、`input_draft_versions`、`source_refs`、`base_profile_versions`、`created_at` 与 `status`。实际命名和持久化格式需在 N06 设计/迁移中定稿；客户端不能提交可信的确认状态或覆盖领域引用。继续保留旧五阶段协议的兼容行为，不静默重解释已有 `review_confirm`。

第 8 步旅程记录建议仅保存当前已验证的 Space 标识及各领域对象引用、expected version、每对象回执和恢复位置。当前活动仍以服务端已验证选择及授权为准；不允许旧 Space 请求、客户端伪造资源 ID 或 A→B→A 后的旧写请求越过检查。更换 Space 时加载其专属资料并重新验证；全局资料不重复创建。想法/讨论/消息与推荐结果由各自团队提供可引用合同，画像插件不创建社交关系或代发消息。

## V5 数据与存储差异

V5 文档范围切换与紧凑填写（工作区路径 `frontend/用户画像收集——前端/docs/11_范围切换与紧凑填写.md`，待所属团队发布）及添加条目与个人照片（工作区路径 `frontend/用户画像收集——前端/docs/12_添加条目与个人照片.md`，待所属团队发布）定义重复条目、可编辑标题/分类、完整正文和本机照片。当前源码接口并不等于已接入这些交互。

- **任意长文段落：** P1 `bio` 单值上限 10,000 字；项目贡献/结果、工作摘要、奖项描述最多 3,000 字；其他自由文本字段多数 1,000 字。虽然值校验按 UTF-8/Unicode 字符计数且不因换行删除正文，但这些固定类型不能表达 V5 任意段落与重复“关于我”。单个 `attribute_id` 已固定 `key`，V5 的自定义标题、分类调整与“技能/经历/联系方式”重复实例也不能自然映射到现有 `FieldCatalog`。
- **建议模型：** 在 P1 普通属性草稿/修订体系内增加受限的 `narrative_segment`（名称拟定）类型，逐段稳定 ID、类别、标题、正文、顺序、逐段可见性和版本；同类可多条，明确最大条数和总储存量。正文与结构化字段共存：完整原话供本人展示，受控结构化事实供匹配；抽取出的结构化候选要指回段落/来源版本并由本人采纳。类型和安全 scope 迁移应有显式版本化操作，不能改写旧属性 ID 的类型。展示分类可作为正文 schema 内的受限枚举更新，不能与 global/Space 安全 scope 混为一谈。V5 的“联系方式”段落必须有独立的联系人类型/用途投影，不得因为换了标题、选择“基本介绍”或进入通用 narrative 就落入普通人物摘要；其 schema 与 P8 的 detail/contacts 分类一起扩展。
- **长度合同：** 每段正文上限 20,000 Unicode 字符，保留原始换行；服务端验证 UTF-8、字符数及 JSON 字节数。20,000 字并不等于 20,000 字节：20,000 个常用汉字的未转义 UTF-8 正文约 60,000 字节，四字节字符约 80,000 字节，JSON 转义与元数据另计。当前普通 JSON API 请求总量最多 256 KiB，多段批量更新会触顶。优先按独立完整段落分批 upsert，并逐次使用服务器返回的草稿版本；拟定明确的总条目数、存储和读取上限。若另做段内分块上传，须作为新增协议提供完整性校验和最终保存回执。任何上限都明确报错，不截断、不把局部传输当作完整段落。
- **数据库核对：** P1 属性值、草稿操作和修订快照使用 JSON 列，理论表示空间不应被误认为可无限写入；部署数据库 JSON 限额、事务日志、备份、单次读取/投影字节数仍需在隔离目标数据库验证。此轮未连接运行数据库，不能宣称 20,000 字已通过真实持久化。
- **头像与昵称：** 按 V5 12 使用已存在 P1 `POST /api/v1/me/avatar` 上传和 `/api/v1/me` identity 更新：输入图片限制 5 MiB；服务端会解码、缩放并产出主图/缩略图，返回尚未确认的 `avatar_ref`；identity 更新使用 `expected_version`。移除用 `avatar_ref: null` 的身份更新显式提交。昵称当前为 2–32 Unicode 字符。`PATCH /me` 会立即修改正式身份，因此 G03 只上传候选/保存私有拟用 ref、昵称或移除意图，不能顺手 PATCH；这些待确认身份选择的服务端恢复引用亦为拟新增，须绑定本人上传资源及旧 `identity_version`，G05 才明确提交。保留旧头像直到新 ref 绑定成功，失败/冲突不得伪报画像与身份均已保存。原型照片说明写 5 MB，实际端精确限制为 5 MiB，正式 UI 应显示同一口径。
- **分类/可见性：** authenticated/friends/private 逐条控制仍使用 P8 普通资料隐私规则；联系方式仍使用单独联系人投影。普通资料 confirmed 条目默认 authenticated，旧的显式范围不变。页面分类只筛选资料，不隐式更改范围。头像身份不套用普通资料逐条 visibility。

这些是接入前需定稿并实施的兼容扩展，不是建议把所有短字段一并改为 20,000。问题自由回答仍可保持短答；长文使用对应的画像段落草稿。

## 现有接口与拟新增边界

现有请求统一 `/api/v1`，使用登录用户、CSRF、严格 JSON 字段、版本检查和适用时的 `Idempotency-Key`。本表是源码签名核对，不表示 V5 前端已经接入。

| 能力 | 已有方法与请求核心 | 接入约束/差异 |
|---|---|---|
| 五阶段会话 | `POST /onboarding/sessions` `{space_id?,generation_mode?}`；`GET/PUT /onboarding/sessions/{id}`；PUT 需 `expected_version,action`。现有 actions 为 `save_materials,move,review_confirm,question_position,save_drafts,reconcile,complete`，额外字段按 action 白名单。 | 现有签名无任意 `resource_refs` 写入。不要从客户端传草稿真相或跳过服务端版本；新十步旅程需拟新增受控应用用例/接口，不直接泛化现有 action。 |
| 会话进度 | `GET /onboarding/sessions/{id}/progress`。 | 投影已保存状态；`percent` 可空，不隐式执行 AI。不能据 P2 `completed` 推断所有十步对象均已确认。 |
| 画像草稿/确认 | `POST /me/profile/drafts` `{scope,space_id?,base_profile_version?}`；`GET/PUT /me/profile/drafts/{id}`，PUT `{expected_version,fields:[operations]}`；`POST .../{id}/confirm` `{expected_version,base_revision,attribute_ids?,confirmation_intent:'confirm'}`。 | 当前 operation 最多 200，字段必须在目录且类型固定。confirm 可全量或指定 stable IDs；新增的任意长文需扩字段 schema、请求策略和投影检查。 |
| Space 画像 | `GET/PUT /me/events/{spaceId}/profile-context`（spaces 别名也存在）；写入 `{expected_version,attributes,confirmation_intent:'confirm'}`。 | 当前上下文写入口直接确认，适合已确认设置，不适合 G03 私有编辑。服务端仍须核对 Space 权限、当前选择合同。 |
| 问题/合成 | `POST /me/profile/question-batches` `{session_id,expected_version,generation_mode}`；`PUT .../question-batches/{batchId}/answers/{questionId}` `{expected_version,answer_type,selected_options,free_text}`；`POST /me/profile/syntheses` `{session_id,expected_version,expected_batch_version,generation_mode}`。 | AI 返回 202 JobDTO；规则准备问题和规则合成都返回 201 SessionDTO，问题内容再按会话引用 GET `/me/profile/question-batches/{batchId}`。当前答案 free_text 最多 1,000 字，批次引用正式画像版本。 |
| 来源/头像 | 来源 `POST /me/profile/sources`、`POST .../sources/resume` multipart；`POST /me/profile/extractions`；头像 `POST /me/avatar` multipart 后 `PATCH /me` `{expected_version,avatar_ref}`。 | 简历 5 MiB；头像 5 MiB 输入。来源、候选和媒体均为服务端本人资源；上传或导入本身不代表用户确认其公开。 |
| 隐私/预览 | `GET /me/profile/preview?perspective=owner\|authenticated\|friends&draft_id?&scope?`；`PATCH /me/profile/visibility` `{expected_version,changes,confirmation_intent:'confirm'}`；`PUT /me/profile/relation-sharing?space_id=...` `{expected_version,kind,object_id,visibility,confirmation_intent:'confirm'}`。 | 预览是只读模拟。关系写只接受当前 Space 已有关系对象，仍由关系源与真实成员/对象权限二次验证；不替代相关领域的确认和发布 API。 |

新旅程/私有 review snapshot/长文段落接口均为**拟新增**。优先由应用服务接口编排现有 P1/P2/P8 用例，所有资源引用由服务端核验所属用户、scope、Space、状态和版本；不让前端写任意内部引用。若共享一个接口，需要动作白名单和逐对象幂等回执；不要用一个“大提交”跨画像、头像、想法、活动、关系和推荐库事务。

逐对象回执不意味着拆开已经存在的事务：P2 同一工作流的 global/Space 草稿确认原子性应保留；身份、想法等独立领域才分别呈现其已有提交结果。来源 reader 的现有同步 HTTP 执行与 AI 队列也应分别适配，不能因来源有 progress 就推断可后台续传。

## AI、异步状态与恢复

P6 已有 `extract/questions/compose`，AI 请求在数据库事务外执行，并以任务 context 检查输入来源、会话、资料/草稿/题目批次是否仍 current；revoked/superseded 结果不得安装或覆盖新内容。用户可显式取消/重试，不能把刷新/普通读取当作重试。任务和原始来源只本人访问；成功后清理任务 input 的行为按 S6 既有合同保持。

现有边界包括：普通 JSON body 256 KiB；AI 输入 128 KiB、结构化输出 64 KiB；简历 5 MiB；来源原文 1 MiB、最多 2,000 个段落、单来源段落 32 KiB；问答自由文本 1,000 字。多个完整 20,000 字段落不应整份送模型。拟定 AI 对 narrative 的按需片段/摘要引用、最大字节数和覆盖范围；超额时返回明确“未处理/不支持”，不能静默截断后宣称已理解全文。AI 产物保持草稿/候选，G05 才由本人显式确认。

刷新/关闭/跨设备恢复应读取服务端会话版本、草稿与任务 progress；浏览器本地状态可作临时输入缓存，不作正式回执。网络不确定时通过幂等键和读取服务端当前对象恢复，不盲目重复创建资源。N06 旅程重新打开时按当前已授权 Space 重验，过期会话可恢复或明确要求重新开始，不能复用 revoked/superseded 任务结果。普通浏览、切活动和更改可见性均不触发导入或模型调用。

活动桥补充核对：现有 current-event 按用户与认证会话保存，并非账号跨设备共享；P1 的本人/Space 成员检查不能替代当前选择版本，P2 AI context 也尚未绑定 selection_revision/access_version。相关核验是 N05/N06 待补能力，不能把上述“恢复时重验”要求写成当前代码已满足。跨设备先解析本设备的有效选择，不从旅程旧 space_id 自动切活动；旧A任务不得在B展示或采纳，再次回到A仍核验当前权限与输入版本。

## 建议的实施与验收顺序
