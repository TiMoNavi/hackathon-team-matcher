# S5 GitHub 与简历导入实施约定

2026-11-11。本轮已实现并验收，结果见 [实现报告](16_S5实现与验证报告.md)。本轮交付 P3 GitHub 与 P4 简历两个插件，复用 P1 的来源存储、普通资料草稿和 P2 的填写流程。

## 插件边界

- P1 matcher-user-profile：本人来源、私有文本快照、段落与证据、版本、读取任务、候选采纳。
- P3 matcher-github-import：依赖 P1 与 auth-github；读取服务端已验证的 GitHub 关联，取得公开资料和有界项目，转换为结构化文本。
- P4 matcher-resume-import：依赖 P1；接收本人文件，解析 PDF/DOCX/MD/TXT，转换为同一种结构化文本。
- P2 matcher-onboarding：展示已保存来源，调用可用读取器，允许预览和逐项采纳至自己的 input_drafts.global，再进入核对和原规则流程。

业务用例与来源读取通过领域端口连接。数据库、GitHub HTTP、文档解析进程放在外层。两个新插件均可独立服务普通资料草稿，不依赖 P2。

## 共用读取端口

P1 提供 humhub\modules\matcherProfile\domain\ports\ProfileSourceReader：

- kind(): string，返回 github 或 resume。
- status(int ownerId): array，只检查本地能力/验证身份，不拉取来源。
- read(int ownerId, array input): array，返回下述结构。

P3/P4 Module 提供 getSourceReader(): ProfileSourceReader。P1 只在对应插件已启用时取得读取器；不存在时返回明确不可用结果。

读取结果包含 external_id、label、canonical_url（可为 null）、raw_text、sections、candidates、metadata。sections 为 id/label/text/locator 的有序数组，locator 为定位对象（例如 GitHub 的 {path:...} 或文档的 {format:...,page:...}）；candidates 为 id/key/value/evidence 的有序数组，evidence 引用 section id。候选必须是来源明确支持的全局资料字段，先保存为本人候选，不直接确认或公开。原文与快照存于私有数据库，不自动过期。

GitHub read 输入为空对象，目标账号只能由登录关联解析；刷新也不能通过传入用户名改读他人。简历 read 输入由上传控制器构造，包含 tmp_path、filename、mime、size，文件路径不从 JSON 客户端接收。读取器返回实际 rules 模式和零模型调用的可追溯元数据。

## 本人 API 与采纳

统一 /api/v1，使用当前登录身份、CSRF、严格请求字段与版本。所有 POST 使用 Idempotency-Key；读取与删除保持本人边界，失败读取也有任务记录。响应继续使用 data/meta 包装。

| 方法与路径 | 输入 | data 输出 |
|---|---|---|
| GET /me/profile/source-capabilities | 无 | readers.github / readers.resume，含 enabled、available、reason、imported_before；GitHub 另含 linked、current_auth、provider_user_id、configured 等本地身份状态 |
| GET /me/profile/sources | 无 | sources：最多 20 个活跃来源的概要，不带原文；每个来源都有 snapshot=null |
| POST /me/profile/sources | JSON {kind:github} | SourceDTO，201；相同已存在来源直接复用，不重新读取 |
| POST /me/profile/sources/resume | multipart file（单文件，最大 5 MiB） | SourceDTO，201；相同文件哈希直接复用 |
| GET /me/profile/sources/{id} | 无 | SourceDTO，含当前私有结构化快照 |
| POST /me/profile/sources/{id}/refresh | GitHub：JSON {expected_version}；简历：multipart file + expected_version | SourceDTO；简历重试使用同一文件，更新后的文件按新来源上传 |
| DELETE /me/profile/sources/{id} | JSON {expected_version} | deleted SourceDTO；同一删除可安全重试 |
| POST /me/profile/extractions | JSON {source_id,expected_version,draft_id,expected_draft_version,candidate_ids:[...]} | {source_id,source_version,snapshot_id,draft_id,applied:[候选ID],skipped:[{candidate_id,reason}],draft:原P1 DraftDTO,generation_mode:rules,llm_calls:0} |

SourceDTO 保存 id、owner_id、kind、version、status、label、external_id、canonical_url、latest_snapshot_id、last_job_id、created_at、updated_at、deleted_at。status 为 running/ready/failed/deleted。snapshot 为 null 或 {id,version,created_at,external_id,label,canonical_url,raw_text,sections,candidates,metadata}。last_job 为 {id,execution_status,applicability,error_code,updated_at}。失败读取返回 status=failed 的 SourceDTO，客户端展示 error_code 并提供明确重试；前置认证、版本、不可用等错误仍走标准 HTTP 错误包装。

读取任务先提交 running，再在数据库事务外执行读取，完成时按来源版本提交。晚到结果只更新任务 applicability，不恢复已删除或被新版本取代的文本。幂等记录只保存来源/快照/草稿引用及采纳 ID，不复制原文到 HTTP 回执。

采纳仅写指定本人全局草稿；同值候选跳过 same_value，已有单值字段跳过 existing_value，避免覆盖原确认资料或手填。用户可在核对页自行编辑已有单值字段。能力列表的 imported_before 包括已删除来源，只在 false 时提供首次自动读取；已删除后再次导入由本人明确发起。源码用例为 ProfileSourceService 的 capabilities/list/get/import/refresh/delete/apply，HTTP 由 P1 SourceController 提供，无 P2 依赖。

完整解析原文、段落及证据私存于数据库；上传的原始二进制不另行留存。大小边界为解析原文 1 MiB、结构化 JSON 2 MiB、段落 2000 个且每段 32 KiB、候选 200 个；段落与候选 ID 是 1–96 位安全 ASCII，候选必须符合全局 FieldCatalog。

每个来源与版本都有独立状态。失败保留可重试记录，刷新产生新快照并使旧待处理结果失效，用户删除来源时清除私有原文并撤销相应未采用结果。已由本人确认的资料按普通资料编辑规则管理。

采纳指定来源版本、候选 ID、全局草稿 ID 和 expected_draft_version，校验归属与并发，不覆盖已确认资料或抢占普通手工草稿。已有同值条目可去重；需要替换的资料留给用户核对。完成采纳后 P2 重新读取自己的会话 DTO，显示同一份 input draft。

## GitHub 身份

采用原生 auth-github 的服务端 user_auth 关联与当前认证客户端；稳定 GitHub 用户 ID 为身份依据。用户名可能变化，读取时按已验证 ID 确认当前 login，再生成 https://github.com/{login}。仅取得本人公开资料，不保存 OAuth token 到来源快照。首次填写读取、复用既有快照和本人主动刷新分别处理。

当前本地 OAuth 是否配置、是否完成真实外部登录，应在实施报告如实记录；隔离测试关联不代表真实 OAuth 回调已经验证。

## 验收

共用用例内存测试；插件真实解析与有界 HTTP 适配测试；隔离数据库迁移、权限、版本和删除测试；真实 Playwright 完成导入后原五阶段流程。用户材料、凭据不作为测试夹具，也不写进报告。冻结稿、HumHub 原版与现有已确认资料保持不变。
