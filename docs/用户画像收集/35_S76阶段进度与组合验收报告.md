## 前端现在可以获得什么

P1 0.10.0 与 P2 0.4.0 在既有返回中增加 progress，并提供三个紧凑接口。前端可以据此显示当前步骤、已答与跳过的题目、正在运行的操作、待核对结果和恢复入口。

| GET 路径 | data 的内容 |
|---|---|
| /api/v1/onboarding/sessions/{id}/progress | 会话 progress 对象，包含阶段、题目计数、任务摘要与修订 token |
| /api/v1/me/profile/ai-jobs/{id}/progress | 紧凑任务元数据与 progress |
| /api/v1/me/profile/sources/{id}/progress | 紧凑来源元数据、最后读取任务摘要与 progress |

现有 SessionDTO、JobDTO、SourceDTO 保留原字段，并各自新增 progress。响应继续使用 data/meta 信封、本人登录与 private/no-store。

| 前端展示 | 后端依据 |
|---|---|
| 第 3 / 5 阶段，补充问题 | stage=questions、stage_index=3、stage_count=5 |
| 已回答 4 题，跳过 1 题，剩余 1 题 | questions 的 answered、skipped、remaining；total=6 |
| 正在准备补充问题 | 活跃任务的 phase=preparing_questions、state=running；会话 state=processing |
| 草稿已生成，等待核对 | 会话 stage=draft、state=ready |
| 资料有变化，需要重新核对 | state=needs_attention、reasons 与 next_actions |
| 本人已确认完成 | stage=completed、state=completed |

表中的题目数字是说明用例。questions.current_index 使用零基索引；没有题目时为 null。阶段顺序仍是 materials → review → questions → draft → privacy → completed。

前端收到主动操作的响应后即可更新展示。存在当前 queued/running 任务时，poll_after_ms 提示 1000 ms；终态为 0。revision_token 在阶段、答案批次版本、相关资料版本或任务状态变化时改变，同一状态重复读取保持稳定。next_actions 是交互提示，实际操作继续走原权限、版本与确认校验。

## 进度与结果的区别

任务进度按数据库中的 execution_status、applicability 和 operation 投影。排队、提取、准备问题、组织草稿、成功、失败、取消及失效均有固定文案。percent 保持 null，因为当前模型适配器没有可靠的百分比或剩余时间。来源仍使用既有同步读取器，通过已保存状态返回 reading_source、ready 或 failed。

失效状态优先：例如本人取消后的底层记录为 execution_status=cancelled、applicability=revoked，progress.state 返回 revoked，同时保留 execution_status。任务成功后仍需本人核对和最终确认，不能直接显示为整个流程已完成。

会话摘要仅列出当前 owner 与 session 对应的任务，活跃任务优先，最多 20 条，另有 tasks_has_more。紧凑接口不携带资料正文、候选正文或内部模型上下文。读取已存状态不运行模型或来源读取器；租约过期与撤权继续执行已有失效规则。

## 数据与插件边界

P1 保存来源与任务，提供可选 ProfileAiJobSessionQuery 端口；SQL 与内存适配器实现有界任务查询，既有仓储接口保持兼容。P2 通过注入的任务读取器组合会话进度，SessionProgress 是独立于框架的纯投影。

没有新增表和迁移。完成确认时，在既有会话 resource_refs 中记录题目计数与批次版本，使完成后的计数不受原 AI 批次失效影响。旧 AI 完成会话没有该快照时，通过 P1 getProgressCounts 在本人及有效 Space 校验后还原计数和批次版本，GET 不回填，也不返回旧题正文。资料值继续由 P1 普通资料保存；全局资料与 Space 专属偏好分开。
