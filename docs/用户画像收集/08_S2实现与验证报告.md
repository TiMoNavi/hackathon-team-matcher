# S2 普通资料、联系方式与 Space 上下文实现报告

> 2026-11-11。matcher-user-profile 已升级至 0.2.0，部署到本机 HumHub 1.19.4 预览库。S1.8 与 S2 均完成，主代理独立验证 458 项通过，包含原生头像上传、裁剪和删除的真实浏览器操作。

## 本轮结果

S1 的联系方式补充和 S2 的普通资料服务已经落地。三个子代理分别负责应用用例、数据库与原生编辑、HTTP 与媒体；主代理使用独立测试库复核，并执行主预览库升级和只读页面验证。

现在能通过后端完成资料草稿、逐条增改、显式删除、分批确认、历史读取和版本冲突处理。新前端和后续引导可以调用同一组接口。普通资料与身份分开计版本，全局资料与每个 Space 的本次偏好分别保存。

## 可选字段与默认展示

新增六类全局联系方式，普通字段目录共 **27 类全局条目 + 10 类 Space 条目**。昵称、头像另由身份用例管理。

| 字段 | 内容 | 保存方式 |
|---|---|---|
| contact_wechat | 微信号 | 可选字符串 |
| contact_wechat_qr | 微信二维码与可选说明 | 本人上传图片的 file_ref，确认后引用 |
| contact_qq | QQ 号 | 可选数字字符串，保留字符串类型 |
| contact_phone | 联系电话 | 复用 profile.mobile；条目表保存确认和版本元数据 |
| contact_email | 联系邮箱 | 本人主动填写，与登录邮箱分别管理 |
| contact_other | 其他联系入口 | label、value，可添加多条 |

37 类普通字段的 required_when 均为空。用户可以只填自己愿意提供的内容；选择添加项目、经历或联系方式后，校验该条记录的必要内容与格式，例如项目标题、邮箱格式和图片归属。

新增确认条目默认 authenticated，即登录用户通过合法资料入口可见。目前已经接通同一 Space 正式成员的查看入口。已有明确展示范围保持原值；未确认草稿、原始候选和未采用的二维码仍属于本人编辑过程。逐条隐私、好友范围和更多合法访问入口在 S3 衔接。

二维码、头像支持 JPEG、PNG、WebP，限制 5 MiB、单边 8192 像素及总计 2000 万像素，并解码、重新编码为 PNG。头像生成最大边 1024 和 256 的版本；二维码生成最大边 4096 的主图及 512 缩略图。资源经登录与归属校验读取，响应采用 private, no-store。二维码条目删除后，他人读取立即失效。

## 全局资料与 Space 的划分

产品所说的“活动”对应 **HumHub Space**。Calendar 负责 Space 内赛程。

| 保存位置 | 内容 | 换一个 Space 后 |
|---|---|---|
| global | 基本信息、性格、技能、经历、兴趣、联系方式 | 继续使用同一份资料 |
| global | 长期协作偏好、沟通习惯、长期合作期待 | 保留，不随活动切换 |
| space:<id> | 本次目标、希望承担的角色、希望找到和能够提供的帮助 | 在新 Space 重新填写 |
| space:<id> | 本次投入时数、具体可用时间、现场或远程安排 | 新 Space 从空上下文开始 |
| space:<id> | 本次沟通偏好、地点及协作说明 | 只影响对应 Space |

例如，“我喜欢先写清思路再讨论”属于全局习惯；“这次周六在线、周日到现场，预计投入 12 小时”属于当前 Space。应用层验证字段所属范围，误把全局性格写入 Space 会返回 422。

验证覆盖 Space A 填写后 Space B 仍为空、两个 Space 保存不同目标、切换后全局资料与联系方式不变。读取及写入 Space 资料均验证正式成员资格，字段目录中的 event 范围和兼容的 event_id 都映射到原生 Space。

## 数据库与原生入口

原生 ProfileField 保持 **31 项**，插件核心表保持 **4 张**。S2 通过补充迁移 m261111_000002_profile_service 增加确认收据字段 confirmation_hash、confirmed_revision 和投影恢复标记 projection_pending，并扩展联系方式绑定与草稿来源约束。

当前单值继续使用原生 user/profile 列；技能、多条经历、项目和 Space 偏好使用结构化条目。每条记录有稳定 attribute_id，重复编辑保留该 ID。历史版本保存确认时的快照，当前值从其权威存储位置读取。

原生资料编辑、账户时区设置与头像入口已接统一版本用例。头像上传后立即同步页面上的身份版本，支持连续裁剪和删除。裁剪表单使用插件内的 CSP 兼容实现，支持拖动选择与键盘数值调整；HumHub 核心、第三方库和 CSP 设置保持原样。管理员修改受管资料时生成待本人采纳的建议草稿。直接保存会创建独立草稿，既有未确认内容继续保留在原草稿中。

原有 REST 或模型对受管资料的无版本直接修改会返回 409；新前端使用本报告列出的版本化接口。后续逐条隐私投影统一覆盖原生个人页、目录、搜索与 REST 等读取入口。

确认事务同时检查草稿版本与资料基础版本，锁定相应状态和草稿，更新原生值、条目及历史快照。重复提交完全相同的确认请求返回同一结果；旧版本或不同确认内容返回 409。缓存刷新在提交后进行，失败保留 projection_pending，由后续提交或 retryPendingProjections 恢复。

主预览升级前已校验私有备份。升级前后原生 user、profile、space、space_membership 的内容哈希一致，仍为 3 个用户、3 行资料、2 个 Space 和 4 条成员关系。合成测试数据全部位于隔离库。

## 已交付接口

统一前缀为 /api/v1，采用 HumHub 登录会话，写请求需要 CSRF。创建草稿、管理员建议和上传资源还需要 Idempotency-Key；本人身份由登录会话确定。

| 方法与路径 | 用途 |
|---|---|
| GET /me/profile | 本人全局资料、字段目录、版本和编辑状态 |
| POST /me/profile/drafts | 创建或恢复草稿 |
| GET /me/profile/drafts/{id} | 本人读取草稿和预览 |
| PUT /me/profile/drafts/{id} | 显式条目操作列表 |
| POST /me/profile/drafts/{id}/confirm | 全部或选定条目确认 |
| POST /me/profile/reconfirm | 重新确认已有条目 |
| GET /me/profile/revisions/{revision} | 本人历史确认资料 |
| GET、PUT /me/spaces/{spaceId}/profile-context | 读取或直接确认本次 Space 偏好 |
| GET /spaces/{spaceId}/profiles/{ownerId} | 当前 Space 合法成员查看已确认资料 |
| GET、PATCH /me | 本人昵称、头像引用与身份版本 |
| POST /me/avatar、POST /me/contact-qr | 上传候选图片 |
| GET /profile-media/{ref} | 受控读取主图或缩略图 |
| POST /admin/users/{ownerId}/profile/proposals | 管理员提出待本人采纳的资料建议 |

/me/events/{spaceId}/profile-context 作为兼容别名指向同一 Space。新接入推荐使用 spaces 路径。Space 草稿创建携带 scope=space、space_id；后续读取、更新、确认在查询参数携带 space_id。全局返回 scope=global，Space 返回 scope=space:<id> 和 space_id。

成功响应为 data + meta.request_id；错误响应包含 error.code、message、retryable、details 和 meta.request_id。普通资料修订名为 revision，草稿更新请求使用 expected_version，确认同时发送 base_revision；身份 PATCH 使用 identity_version 对应的 expected_version。

字段操作示例：

```json
{
  "expected_version": 1,
  "fields": [
    {"key": "contact_wechat", "value": "example_wechat"},
    {"key": "project", "value": {"title": "协作工具", "contribution": "负责后端接口"}}
  ]
}
```

更新已有条目时加 attribute_id；删除采用 op=delete 和 attribute_id。省略的字段保留现状。确认请求包含 expected_version、base_revision、confirmation_intent=confirm，可选 attribute_ids 表示本次选中的条目。分批确认后，其余条目继续作为可编辑草稿保存。
