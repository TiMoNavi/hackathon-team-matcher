# S6 AI 后端实施约定

2026-11-12。已实施并验收，覆盖 task.md 的 S6.1–S6.6，结果见 [S6 实现报告](23_S6实现与验证报告.md)。现有资料、规则引导、来源与隐私后端作为基础，新增 P6 matcher-onboarding-ai。正式前端后续单独接入，本轮保持现有 assets/views。

## 用户体验与确认

先从本人选定的资料提取候选和证据，展示缺失、矛盾或不确定的待核对项；本人确认后，围绕已有资料生成 3–8 个简短问题。每题有明确选项、最后的“其他，我来填写”自由回答入口，并允许跳过。回答保存后生成可编辑画像，同时给出需要本人复核的提示。

AI 对事实、个人自述与活动安排分别处理。活动仍指当前经服务端验证的 Space；长期习惯属于全局。本人的资料确认、可见性选择和联系人授权继续由普通业务流程负责。提取、提问、综合各阶段返回 review_items，供客户端展示待核对内容；这些提示不直接修改确认资料。

## 分层与依赖

P6 依赖 P1 与 P2，提供模型传输和 extract/questions/compose 三种生成能力。P1 保存本人 AI 任务、输入版本、输出与用量，并复用来源和草稿接口；P2 将 AI 问题批次和综合结果接回既有会话。模型调用在数据库事务外进行，结果落库时重新校验输入引用、版本和访问资格。

统一端口为 P1 domain/ports/ProfileAiEngine：status():array 与 generate(string operation,array input):array。generate 返回 data 和 metrics；失败抛出仅含稳定错误码和已发生用量的 ProfileAiFailure。公开状态不包含密钥或私有配置路径。

metrics 记录实际 model、llm_calls、duration_ms 与 usage；usage 含 prompt_tokens、completion_tokens、total_tokens 和 reported，供应商未报告的用量不伪造为已知消耗。模型传输只调用服务器配置的固定 HTTPS 网关，不随资料中的链接或指令切换目标。

模型确切 ID 已从用户指定网关核验为 gemini-3.8-flash。配置由主 agent 私存在 .local，运行时读取；测试子 agent 仅使用合成适配器。真实网关验收只发送本轮编造的测试资料。

## 三类结果与复核

- extract 输入为本人选中的当前来源片段和字段目录，输出候选、合法片段证据和 review_items，等待本人选择采纳。AI 候选与原始来源快照分开保存。
- questions 输入为已确认资料、当前 Space 及允许的问题字段/选项，输出与既有 BatchDTO 兼容的问题；稳定选项 code、允许范围与自由回答入口由服务器校验。
- compose 输入为当前确认资料与本批答案，输出可编辑草稿建议、相应证据和 review_items；继承相关字段的展示范围，保留本人已经编辑的内容。

review_items 包含稳定 id、kind、message、相关字段及证据引用；kind 为 missing/conflict/uncertain/unsupported。后端验证输出 schema、字段值、范围和证据引用。结构化事实、选项与性格字段按显式证据及映射校验；不符合约束时保留明确失败状态，用户可以主动改用 rules。自然语言 headline/bio 允许基于全局证据改写，合法引用不能证明每一句文案的真实性；服务器追加 server-prose-review 复核提示，并保守继承输入范围，始终由本人编辑确认。

## 任务与接口

已有 sources、drafts、question-batches、syntheses 的 rules 行为保持。AI 模式返回 HTTP 202 与 job_id，独立工作进程领取任务；GET 查询只读取状态，不触发模型。任务使用 queued/running/succeeded/failed/cancelled 与 current/superseded/revoked 两组状态。输入变化、来源删除或资格撤销后，旧结果不能继续采纳或覆盖当前资料。

任务记录幂等键、操作、所有者、Space、输入引用/版本、实际模式、模型用量和结果适用性。提取结果按用户选择进入指定草稿；问题和综合结果经会话版本校验后接回流程。取消与明确重试通过本人业务操作进行。

### 版本与存储

P1 `matcher-user-profile` 为 0.7.0，P2 `matcher-onboarding` 为 0.3.0。P1 迁移 `m261111_000006_profile_ai_jobs` 新增 `matcher_profile_ai_job`，并为 `matcher_profile_question_batch` 增加可空 `ai_metadata_json`。不修改原生已确认值；迁移可重复运行，回滚不隐式删除任务数据。

P1 `ProfileAiJobService` 通过 `ProfileAiJobRepository`、`ProfileAiWorkflow` 与 `ProfileAiEngine` 三个端口编排。内存与 SQL 仓储共用任务用例；P2 `OnboardingAiWorkflow` 接入现有会话、来源、问题和草稿。P2 只按可选能力解析 P6 `getAiEngine()`，不导入 P6 实现类。

任务的 input/context/result/metrics/receipts 均为本人私有 JSON。成功后清除 input；问题和综合结果只保存资源引用及 review_items，不另存完整问题或画像值副本。题目、答案、编辑草稿仍由原仓储保存。

### HTTP 请求

所有路径以 `/api/v1` 开头，均需原生登录与 CSRF。新建、重试和采纳提供 `Idempotency-Key`，8–128 位字符，允许字母、数字及 `._:-`。同键同载荷重放已有资源，同键不同载荷返回 `IDEMPOTENCY_CONFLICT`。

| 操作 | 路径与请求体 | 响应 |
| --- | --- | --- |
| 能力 | `GET /me/profile/ai-capabilities` | 状态和服务器限额，0 次模型调用 |
| 提取 | `POST /me/profile/extractions`，`{generation_mode:"ai",session_id,expected_version,sources:[{source_id,expected_version,section_ids?:[id]}]}` | 202 JobDTO |
| 补问 | `POST /me/profile/question-batches`，`{generation_mode:"ai",session_id,expected_version}` | 202 JobDTO |
| 综合 | `POST /me/profile/syntheses`，`{generation_mode:"ai",session_id,expected_version,expected_batch_version}` | 202 JobDTO |
| 查询 | `GET /me/profile/ai-jobs/{id}` | 200 JobDTO，0 次模型调用 |
| 取消 | `POST /me/profile/ai-jobs/{id}/cancel`，`{}` | 200 JobDTO，重复取消幂等 |
| 显式重试 | `POST /me/profile/ai-jobs/{id}/retry`，`{}` | 202 新 JobDTO，仅 current/failed 可重试 |
| 采纳提取 | `POST /me/profile/ai-jobs/{id}/apply`，`{draft_id,expected_draft_version,candidate_ids:[id]}` | 200 未确认草稿及 applied/skipped |

提取绑定会话的全局 input_drafts，限 materials/review 阶段，采纳不能转写其他草稿。补问要求已确认资料、当前为 questions 且尚未生成批次；已有批次继续使用，重建先显式 reconcile。综合要求当前批次每题已回答或跳过，结果进入 draft，仍需编辑、privacy 和 complete 确认。重新综合保守保留已有草稿条目，包括手工修改；新建议与保留条目不同时附 conflict review_item，由本人决定修改。

JobDTO 包含 `id/job_id,owner_id,space_id,operation,execution_status,applicability,error_code,attempt,retry_of,metrics,created_at,updated_at,started_at,finished_at,generation_mode,result`，不会返回模型输入或内部版本上下文。只有 succeeded/current 返回 result，其他状态返回 null。

- extract result 为 `{candidates,review_items}`。
- questions result 为 `{session_id,session_version,question_batch_id,batch_version,review_items}`。
- compose result 为 `{session_id,session_version,output_drafts:{global,space},batch_version,review_items}`。

客户端随后读取原 SessionDTO/BatchDTO，不从任务结果另建资料副本。SessionDTO 的 llm_calls 汇总已安装的 questions/compose 指标；提取的实际指标记录在对应 JobDTO。普通 rules 路径仍为 0，不因 GET 或普通浏览增加调用数。

### 模型端口准确数据

- extract 输入 `{sources:[{source_id,version,sections:[{id,text}]}],space_id}`；candidate 为 `{id,key,value,evidence:[{source_id,source_version,section_id}]}`，证据必须属于本人来源当前快照。
- questions 输入 `{profiles:{global,space},space_id}`；输出 questions 兼容已存题库 DTO。`id/template_id/target_key/scope/mode/options/allow_free_text/allow_skip` 由服务端题库限定。每题另带 `free_text_option:{code:"other",label:"其他，我来填写",position:"last",max_length:1000}`，不属于 options，也不能把 other 当普通选择代码保存。自由回答提交 `answer_type:"free_text"` 与 free_text；跳过提交 `answer_type:"skipped"`。
- compose 输入 `{profiles,space_id,questions,answers}`；输出 `{global_fields,space_fields,review_items}`。field 为 `{key,value,visibility,evidence}`，证据为 `{type:"profile",scope:"global"或"space",attribute_id}` 或 `{type:"answer",question_id}`。写入草稿时去除证据元数据，继续执行统一字段和范围校验。
- review_item 为 `{id,kind,message,field_keys:[],evidence:[]}`。extract 使用来源证据，其他阶段使用 profile/answer 证据；这些提示仅本人读取，不代表本人确认。

### 限额与失效

默认每人同时最多 2 个 queued/running、每 UTC 日最多提交 20 个任务。取消仍计当天提交数，每条显式重试链最多 3 个 attempt，不自动重试，不静默切 rules。P2 服务器模块配置 `aiTaskLimits` 可设 active_jobs（1–10）、daily_jobs（1–1000）和 attempts（1–3）；请求载荷不能覆盖。单次提取最多 5 个来源，合计 200 个片段和 64 KiB 片段文字；完整模型输入 JSON 最多 128 KiB。P6 模型输出最多 80 条候选；P1 通用候选容器的 200 条上限仍保留，当前 AI 的有效上限为较小的 80 条。HTTP 请求体上限为 192 KiB，响应上限为 512 KiB；模型调用连接超时 5 秒、总超时 90 秒、max_tokens 为 8192，每个任务最多发出一次模型请求。

领取任务和安装结果分别使用短事务，模型传输期间不持有数据库事务或资料锁。完成、GET、重放和采纳重新验证本人、Space 资格、会话版本、资料内容与 permission_version、输入/输出草稿版本及状态、批次版本、来源版本和快照。晚到任务不能覆盖当前草稿。

来源删除回调把关联任务标为 revoked，并清空 input/result/receipts，关联 queued 任务取消。本人已明确采纳的草稿和确认资料继续沿用普通资料删除与编辑流程。AI 问题批次另绑定已确认资料及可见性指纹，旧批次不能在资料或权限变化后继续展示、回答或综合。

### 工作进程和中断恢复

多个 worker 在 owner 锁与 job 锁内将 queued 变为 running，同一任务只领取一次。running 的执行租约为 120 秒；GET、提交预算检查和 worker 轮询均回收过期任务为 failed，错误码 `AI_WORKER_INTERRUPTED`。回收不重新发送模型请求，用户可显式 retry 获得新 job_id。原 worker 晚到时不得安装，也不得把任务改回成功；如已取得实际用量，只补记计量。

未能确认的中断计量为 `llm_calls:null,accounting_complete:false`，usage 的 token 值仍为 null，不记成确定 0。正常模型完成为 `accounting_complete:true`，保留实际模型、调用数、耗时与供应商报告情况。

项目根目录的本地运行示例，部署时替换为实际 PHP 配置：

```sh
backend/.runtime/php-mysql/bin/php -c backend/.runtime/php.ini backend/protected/yii matcher-onboarding/ai-worker/run --limit=20
backend/.runtime/php-mysql/bin/php -c backend/.runtime/php.ini backend/protected/yii matcher-onboarding/ai-worker/watch --limit=20 --interval=2
```

run 单次处理至指定数量，watch 为常驻进程；interval 为 1–60 秒，limit 为 1–1000，由进程管理器负责重启。空闲 watch 不重复输出 processed=0。日志仅输出 job_id、状态、适用性、调用数、计量完整性和本轮数量，不输出资料、提示词、模型正文或异常内容。隔离测试调用 P2 `getAiJobService()->work($jobId)`，并通过 P6 `setAiEngine()` 或用例构造函数注入合成 engine；普通 GET 不运行 worker。


## 验收方式

先使用内存适配器验证生成与任务用例，再用隔离 SQL/HTTP 验证完整流程、失效与事务边界。独立代理验证自由回答、权限、隐私继承、模型错误、重复提交和晚到结果。主代理单独执行指定网关的合成资料验收，记录模型和真实用量。主预览部署前备份并核对旧数据指纹，最终复核前端和冻结文档。


## S7.6 兼容进度扩展

JobDTO 新增 progress，另有 GET /api/v1/me/profile/ai-jobs/{id}/progress 返回紧凑任务摘要；P2 会话进度包含当前 owner/session 的任务。execution_status 与 applicability 保持原含义，progress 优先表示 superseded/revoked，只有 current 的 queued/running 建议继续轮询。本人取消保留 cancelled + revoked 原记录，前端通过两者理解停止原因。成功表示结果待核对，整套流程仍需本人确认。已存任务的读取不依赖 P6 engine，GET 不触发模型；详细合同见 [S7.6 进度约定](34_S76阶段进度与组合验收约定.md)。
