# S1 用户画像字段与数据库实施报告

> 2026-11-11。本报告记录 S1 首次交付的 0.1.0 基线。随后 S1.8 补充六类可选联系方式，字段目录升级为 2，当前运行模块为 0.2.0；新增确认条目默认登录用户通过合法入口可见。最新字段、Space 划分与验证见 [S2 实现与验证报告](08_S2实现与验证报告.md)。后续本专项文档继续保存在此目录。

## 1. 这份画像用于判断什么

一份填写充分、允许展示的画像，应让潜在队友看清六件事：这个人是谁、会做什么、做过什么、怎样合作、这次愿意投入什么、正在参与哪些想法和活动。

最有用的合作依据是项目中的个人职责、具体贡献、成果或作品链接，以及本次活动的目标、角色和时间安排。性格自述与沟通习惯帮助判断相处方式，MBTI 作为可选补充。本人确认和来源依据分别记录；通过进一步沟通或小范围协作，可以核对经历与配合程度。

“充分填写”是画像的表达目标。用户可以分步补充，各条资料仍由本人决定展示范围。首期提问会优先补齐与合作判断有关的信息。

## 2. S1 的交付范围

模块位置为 [matcher-user-profile](../../backend/protected/modules/matcher-user-profile/)，版本为 0.1.0，字段目录版本为 1。

| 内容 | S1 交付 | 后续使用位置 |
|---|---|---|
| 原生资料扩展 | 注册 4 个字段，复用现有单值列，调整姓名与自述校验 | 普通资料编辑、画像核对 |
| 全局普通资料 | 21 类字段的结构、范围、数量与校验 | 持续维护的个人资料 |
| 活动偏好 | 10 类字段的结构与活动作用域 | 本次活动的找队友资料 |
| 展示身份 | 昵称、头像两个独立身份定义；昵称确认读取与中性回退 | 卡片、用户名称等原生显示入口 |
| 数据库基础 | 状态、条目、版本、草稿 4 张核心表 | S2 的统一资料用例 |
| 想法与活动外联 | 2 类只读关系契约与访问上下文 | 后续业务适配器和画像关系区 |
| 编辑、逐条隐私与引导 | 使用本轮结构继续实施 | S2–S5 交付完整基础流程 |

新原生字段在 S1 暂不进入原生公开展示、搜索、注册表单和直接编辑。普通资料与逐条隐私接口接通后，再由同一服务提供编辑和展示。当前完成字段与存储基础，已有账号的个人资料内容继续保留。

## 3. 原生数据库具体增加了什么

### 3.1 新增的 4 个 profile 字段

| 物理列 | 内容 | 类型与规则 |
|---|---|---|
| matcher_nickname | 本人确认的昵称 | VARCHAR(255)，2–32 字符 |
| matcher_age_range | 本人选择的年龄段 | VARCHAR(255)，版本化选项，可选 |
| matcher_mbti | 本人自述 MBTI | VARCHAR(255)，16 种编码，可选 |
| matcher_seeking | 长期合作期待 | TEXT，字段目录校验最多 1,000 字符 |

### 3.2 复用的原生资料

| 逻辑字段 | 原生位置 | 本轮处理 |
|---|---|---|
| real_name | profile.firstname + lastname | 改为可选；各列校验放宽至 120，原生事件另验姓名合计 120 字符 |
| headline | profile.title | 标签改为一句话自述，校验上限 160 字符 |
| bio | profile.about | 保留当前值，通过字段目录提供后续编辑规则 |
| city | profile.city | 复用城市值 |
| timezone | user.time_zone | 使用用户显式保存值 |
| 主主页链接 | profile.url | 主链接复用原列，额外链接使用结构化条目 |
| avatar_ref | 原生头像资源 | 定义资源引用与身份版本；候选上传/确认用例在 S2 实现 |

原生 ProfileField 数量与逻辑画像字段数量是两种统计。迁移前原生定义为 27 项，新增后为 31 项；画像目录的 31 类普通资料由 21 类全局资料与 10 类活动资料组成，其中许多重复经历保存在扩展条目中。

## 4. 能填写的完整资料

### 4.1 基本信息与个人介绍

| 字段 | 可表达的信息 |
|---|---|
| nickname、avatar_ref | 对外识别身份 |
| real_name、age_range | 自愿提供的真实姓名与年龄段 |
| headline、bio | 一句话定位及较完整的个人介绍 |
| city、timezone、language | 常驻地、协作时差、沟通语言和本人语言水平 |
| direction、interest | 技术、业务、创业方向与兴趣 |
| seeking | 长期希望认识的人、寻求的帮助或合作方向 |

### 4.2 能力与经历

| 字段 | 结构化内容 |
|---|---|
| skill | 技能编码、名称、本人水平与补充说明，每条独立 |
| role | 可贡献角色，如开发、设计、产品、运营 |
| education | 学校、专业、学历、起止时间及说明，可多条 |
| project | 项目标题、个人角色、实际贡献、技术、成果、作品链接、起止时间，可多条 |
| work_experience | 单位、角色、工作或实习时间及说明，可多条 |
| award | 获奖名称、主办方、日期、成果描述，可多条 |
| portfolio_link | 链接、展示名称、对应项目，可多条 |

项目经历优先突出个人做了什么、交付了什么、可以看什么作品。日期保留年、年月或完整日期的精度。重复经历各有稳定 attribute_id，支持后续独立编辑和展示范围设置。

### 4.3 性格、偏好与合作方式

| 字段 | 可表达的信息 |
|---|---|
| personality | 本人选择的性格特点 traits，以及具体做事风格 self_description |
| mbti | 本人自述的可选标签 |
| collaboration_preference | 合作节奏、分工方式等选项与补充 |
| communication_preference | 同步/异步、沟通频率、讨论方式等选项与补充 |

personality 的确认值至少包含一项实际特点或有效自述。后续补问可围绕推进任务、讨论分歧、寻求帮助、接受反馈等具体情境展开，形成能指导合作的介绍。

### 4.4 本次活动的 10 类偏好

| 字段 | 合作判断用途 |
|---|---|
| event_goal | 想交付作品、探索方向、认识队友等目标 |
| event_seeking | 本次需要的角色、能力和帮助 |
| event_role | 本次愿意承担的角色，可多条 |
| event_contribution | 本次可以实际提供的技能与支持 |
| event_time_commitment | 可投入小时数区间，按天、周或整个活动表达 |
| event_availability | 可参加的具体时间段与时区，可多段 |
| event_collaboration_mode | 现场、线上或混合协作 |
| event_presence | 大致地点及参与安排 |
| event_contact_preference | 本次偏好的沟通方式 |
| event_constraint | 用户希望队友提前知道的协作条件 |

投入时间检查区间顺序，每天最多 24 小时、每周最多 168 小时。整个活动的投入总量由后续活动用例结合活动时长判断。资料通过 user_id 与服务端生成的 global / space:<id> 范围键分别保存。

## 5. 参与的想法与活动如何展示

| 关系区 | 原生可复用内容 | 后续接通工作 |
|---|---|---|
| 活动 | Space 的名称、简介、介绍和正式成员关系 | 检查活动资格、成员展示设置和本人选择，再返回获准摘要 |
| 想法讨论群 | Messenger 的会话标题、消息和参与者关系 | 想法业务保存正式标题、简介及 message_id / space_id 关联，再提供讨论入口 |

原生 Messenger 目前没有独立的群简介、想法归属或活动归属字段。后续通过显式的想法业务关系识别讨论群；摘要使用正式简介，消息正文留在会话内。

S1 的 ProfileRelationReader 约定输出 kind、id、title、summary、href、event_id、membership_role 和分页游标，并接收访问者、画像所有者与合法入口上下文。实际查询、成员权限适配和页面展示属于后续阶段。资料卡可以由此扩展出“正在参与的想法”和“参与活动”，与本人经历相互补充。

## 6. 四张表各自负责什么

| 表 | 用途 | 关键字段 |
|---|---|---|
| matcher_profile_state | 一位用户在一个范围的资料状态 | user_id、scope_key、space_id、revision、permission_version、identity_version、current_revision_id、confirmed_avatar_ref |
| matcher_profile_attribute | 当前条目及逐条策略 | attribute_id、state_id、scope_key、field_key、native_binding / value_json、visibility、confirmation、last_confirmed_at |
| matcher_profile_revision | 确认时的历史快照 | state_id、revision、snapshot_json、confirmed_at |
| matcher_profile_draft | 编辑和处理建议 | state_id、draft_kind、base_revision、base_identity_version、draft_version、fields_json、origin、initiator_id、status |

适合原生列的单值继续写在原列；条目表保存其确认与可见性元数据。多条技能、经历与活动偏好以 JSON 保存到条目表。昵称使用独立身份确认标记，只有有效身份版本和已确认展示标记同时存在时，原生显示名才使用该昵称。

约束覆盖范围唯一性、原生绑定唯一性、有效枚举、非负版本、原生条目所属全局范围、当前快照所属状态等。UUID 引用使用一致的 ASCII 字符集和二进制排序；用户与活动外键沿用实际原生整数类型。JSON 持久化通过 Yii JsonExpression 传入结构化值。

外键采用 RESTRICT。后续主动删除用例先清空当前快照引用并重置相应状态，再按依赖清理草稿、条目、快照和状态。升级通过模块迁移交付；维护模式保留模块与数据。

### 运维与恢复

迁移前数据库备份保存在本机受限目录 `backend/.runtime/backups/`，文件权限为 0600，目录为 0700；本机 `backend/.runtime/profile-s1-backup-path` 记录本次备份位置。恢复演练将该备份导入独立测试库，随后完成安装、幂等和原值保留验证。

恢复时先进入受控维护并暂停写入，校验备份清单摘要，再将备份恢复到独立库复核字段、原值和模块状态；复核通过后由运维切换连接并恢复服务。恢复前继续保留当前库备份。此方案与迁移代码的资料保留行为一致。

模块支持 enterMaintenance / leaveMaintenance 保持加载；普通 disable/remove 和破坏性 down 会被拒绝。S2 的写用例需接入维护状态验证。

在项目根目录可执行以下检查命令：

```sh
backend/.runtime/php-mysql/bin/php -c backend/.runtime/php.ini backend/deploy/profile_s1.php inspect
backend/.runtime/php-mysql/bin/php -c backend/.runtime/php.ini backend/protected/modules/matcher-user-profile/tests/unit/run.php
node backend/deploy/profile_s1_web_smoke.cjs
```

数据库测试的两个 runner 位于模块 tests/integration 目录，只接受名称以 humhub_profile_s1_test_ 开头的独立库；准备迁移前备份的克隆后分别执行 run.php 与 native_module.php。部署入口为 profile_s1.php install，它使用原生模块启用流程，并在再次执行时验证同一版本结构。

## 8. 下一步

S2 将这些结构接成实际资料用例：读取本人资料、创建和恢复草稿、编辑多条经历、校验并发版本、确认保存，以及 `/api/v1` 接口。S3 接普通资料编辑和逐条可见性；S4 接无 AI 问答与画像组织；S5 接真实简历和 GitHub 导入。基础流程稳定后再按任务接 AI。

最终个人卡片应同时给出“能力与依据”和“本次合作安排”。这样用户可以判断是否值得进一步交流，并据双方目标、能力互补和可投入时间决定是否组队。
