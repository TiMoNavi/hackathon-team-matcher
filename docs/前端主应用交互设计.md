# 前端主应用交互设计

> 状态：已批准方案的实现设计；更新日期：2026-11-10。
> 目标客户端：Next.js / React / TypeScript 响应式 Web，移动端与 PC 共用业务接口。本文设计目标应用，不改写参考工程 GameBuddy。
> 依据：[完整方案 v3](完整方案设计_v3.md)、[系统架构与领域设计](系统架构与领域设计.md)。首次录入见 [引导优化设计](首次注册与开场引导_优化设计.md)，API、字段与错误码以 [共享契约](共享数据与接口契约.md) 为准。

## 1. 交互总则与前端边界

主导航固定为 **发现 / 广场 / 消息 / 个人**，顺序在移动端与 PC 一致。活动切换器是上下文控件，不是第五个主导航。登录、引导、详情和编辑页属于辅助路由，不改变四主导航结构。

首次引导优先展示简历上传和 GitHub 资料两个主入口。GitHub 首次注册后账号已连接，页面直接显示读取状态；不要求再次输入主页或绑定。先用现有材料预填基础画像，再确认和补充缺失项，手填不作为默认长表单。详细步骤见引导设计，这两项能力属于首期必备。

发现需要当前有效活动；广场可浏览用户主动广泛发布的帖子；消息与个人中心是账号级入口。已有好友不因活动切换消失，同一个人参与多个想法也不会从发现候选中退出。

architecture-patterns 的分层落实为：页面/组件处理呈现和用户输入，前端数据适配层调用后端用例，后端拥有权限与业务事实。前端按钮禁用用于说明状态，不能替代后端鉴权。不得把完整用户表、原始简历或其他活动候选送到浏览器后再隐藏。

所有业务 API 使用 **/api/v1**。本文列出已有批准接口的交互方式，上传、确认、消息、好友接受等具体结构引用共享契约，不再另造一套路径或字段。AI、普通社交和头像入口都使用同一套业务权限，不允许模型绕过用户操作直接发消息。

## 2. 页面树与导航行为

~~~text
登录 / 首次引导
└── 主应用
    ├── 发现
    │   ├── 当前活动选择 / 通过邀请加入
    │   ├── 想法：完整分页网格、筛选、想法详情
    │   ├── 人选：完整分页网格、随机批次、人物详情
    │   ├── AI 推荐：需求、当前推荐任务、推荐卡片
    │   └── 发布新想法：独立草稿、预览、选择活动发布
    ├── 广场
    │   ├── 公开广场 / 当前活动帖子
    │   ├── 发布帖子 / 帖子详情 / 评论
    │   └── 帖子作者页 / 添加好友
    ├── 消息
    │   ├── 私聊 / 想法讨论
    │   ├── 好友申请：收到的 / 发出的
    │   └── 系统通知 / 会话资料
    └── 个人
        ├── 本人画像与三种视角预览
        ├── 资料来源、答案和逐条可见性
        ├── 我的想法 / 关注的想法 / 已加入讨论
        ├── 我的活动与活动偏好
        └── 好友、联系人、隐私与账号设置
~~~

| 行为 | 约定 |
|---|---|
| 首次完成开场 | 进入发现，保留当前活动和首轮 run；无活动进入广场并提供加入活动入口 |
| 引导中保存退出 | 进入有权访问的主应用，保留未完成进度及继续入口；不把十步完成状态当作普通业务资格 |
| 再次打开应用 | 恢复合法的最近页面；活动资格失效时说明状态，不静默切到另一活动 |
| 打开详情 | 使用可直接访问的页面状态，保留来源列表上下文；刷新后由后端重新校验来源 |
| 从详情返回 | 恢复筛选、已访问分页 cursor 和滚动位置；已撤销的数据重新读取，不复用越权快照 |
| 从列表编辑本人想法 | 编辑器独立保存；返回原页面并刷新受影响条目，不重置整个列表 |
| 从帖子打开作者 | 保留合法帖子来源，按 authenticated / friends 字段投影；可跨活动申请好友 |
| 登录失效 | 保存可保存的服务端草稿、显示重新登录；重新登录后恢复合法目标页 |
| 主导航切换 | 不丢已保存草稿，不自动调用 AI，也不切换活动 |

返回位置可以保存在会话级 UI 状态中；URL 仅携带对象标识、类型、非敏感筛选和分页位置，不写原始资料、自由输入的私密正文或联系信息。带个人叙述的 AI 需求保存在本人任务记录中。

## 3. 发现：三种浏览能力与一个创作入口

### 3.1 页面布局

发现页顶部依次显示当前活动、AI 推荐入口和“发布新想法”。下方为“想法 / 人选”切换及各自筛选区。默认进入想法的普通分页网格；首次开场已有结果时，可显示“继续查看首轮推荐”的入口，不自动弹起覆盖网格。

| 区域 | 展示内容 | 操作 |
|---|---|---|
| 当前活动 | 活动名、成员状态、活动切换 | 选择已加入活动；使用邀请加入；失效状态有说明 |
| AI 推荐入口 | 当前有无有效推荐任务、上次结果状态 | 打开推荐页；明确点击开始或重新推荐才创建新 run |
| 新想法入口 | 固定“发布新想法”按钮 | 打开空白或本人未完成草稿；无活动仍可先保存草稿 |
| 类型切换 | 想法 / 人选 | 分别保留过滤与分页状态，不把筛人条件套到想法 |
| 筛选区 | 想法按主题、阶段、需要的贡献；人选按技能、角色、活动投入偏好 | 提交或清除筛选后回到第一页；仅展示共享契约支持的条件 |
| 内容区 | 普通分页网格，或人选的随机批次 | 查看详情、收藏/关注、添加好友；各动作独立 |

没有有效活动时，发现页保留导航及“创建草稿”，内容区显示加入活动入口，不请求全平台用户或想法。多个活动不自动合并为一个列表。

### 3.2 完整分页网格

“完整”指当前活动内全部符合权限、发现状态和用户筛选的对象，并非数据库全量导出。普通浏览不调用 LLM；后端按约定的普通列表排序返回，页面显示所选排序名称，不能将普通结果标成 AI 推荐。

想法卡显示标题、活动内阶段、问题/方向短摘要、所需贡献、发起者最小身份和更新时间。人选卡显示昵称、允许展示的能力标签、活动内角色/投入说明，以及合法读取范围内的短介绍；未知字段显示未知或不展示，不自动补成优秀评分。

统一使用对齐的商品式网格。卡片的摘要和标签数量受版面约束，完整内容在详情展开；不采用不等高瀑布流破坏逐项对照。卡片点击区与“关注”“添加好友”等操作区分开，点操作不会同时打开详情。已是好友时按钮为“发消息”，申请待处理时为“申请已发送”。

使用 **GET /api/v1/events/{event_id}/discovery**。参数中的 limit 默认 **24**、最大 **48**，cursor 为后端签名值；对象类型、筛选和排序结构以共享契约为准。

PC 和移动端均提供“上一页 / 下一页”，不虚构可随机跳转的总页数。前端保留已访问页面的 cursor 栈，因此可以返回上一页；后端没有返回总数时不显示估算总数。首次页无上一页，后端未返回下一页 cursor 时无下一页。返回已访问页仍需验证当前权限，不能永远展示本地旧页。

翻页保留筛选，定位到列表标题并播报结果；详情返回则恢复原滚动位置。改变筛选、类型或活动后丢弃该上下文的 cursor 栈。cursor 失效提示“列表已更新，请重新加载”，保留筛选并从第一页重新读取，不自行解码修改签名值。

分页已经限制了同时挂载的卡片数量，首期不叠加无限滚动和虚拟列表。后续只有实测证明连续列表需要虚拟化时另行设计，不能在本期以虚拟化替代后端分页和鉴权。

### 3.3 人选随机批次

人选页可从普通列表切换到“随机看看”。该模式面向轻量探索，不读取模型来判定合适程度，不展示虚假的匹配分数或 AI 理由。

1. 用户点击随机看看或“换一批”，调用 **POST /api/v1/events/{event_id}/discovery-batches**。
2. 服务端创建当前活动内的随机批次，前端保存批次标识。
3. 使用 **GET /api/v1/discovery-batches/{id}/items**，按 limit 与签名 cursor 分页。
4. 同一批次翻页保持顺序；后端保证批次内按对象去重，每页再次检查资格和可见性。
5. 只有明确点击“换一批”才新建批次。刷新、返回详情、重新连接网络都恢复原有效批次。

不承诺不同批次永不重复。被撤回、屏蔽或不再合格的对象从后续响应排除，因此某页少于 24 条不等于错误。批次过期或活动改变时提示重新生成；客户端不能拿旧批次在新活动继续翻页。换一批与页面浏览仅记录浏览行为，不记录为感兴趣或好友同意。

### 3.4 独立 AI 推荐页

入口与普通网格、随机浏览清楚分开。推荐页显示当前活动、推荐对象类型、本人已确认画像/所选想法、可选的本次需求。用户可以围绕自己的想法找贡献者，也可以按兴趣找想法；这些选择不会修改原画像。

| 阶段 | 页面内容 | 动作 |
|---|---|---|
| 尚未开始 | 需求摘要与当前活动 | 点击开始推荐；也可返回普通发现 |
| 处理中 | 实际任务阶段和可离开提示 | 取消或离开；返回恢复 run |
| 等待补充需求 | 当前问题、已确认条件、剩余澄清机会 | 同一 run 续答，或主动改用结构化条件；刷新不重问/重新计费 |
| 完成 | 通常 3–5 张合格卡片及依据 | 略过、详情、关注想法、加好友、重新推荐 |
| 无候选 | 当前活动内暂时没有合适结果 | 修改需求、普通浏览、进入广场 |
| 失败或已失效 | 区分网络/任务失败与输入版本被取代 | 重试或新建 run；不回退全平台 |

使用 **POST /api/v1/events/{event_id}/recommendation-runs** 和 **GET /api/v1/recommendation-runs/{id}**。首次开场与主应用共用推荐组件和接口，不另外做“欢迎推荐”算法。需求变化或画像更新时明确标记旧结果，用户启动新任务后再重新计算。

澄清续答使用同一 run 的 clarification-answers，携带当前 question_id 与 expected_version；等待用户时依据 run.interaction_status，不把已结束的 AIJob 显示成永久运行。三轮仍不明确则显示普通条件表单。模型失败显示真实失败；平台预算不足明确报错，二者均可由用户主动点击“普通发现”，不能自动替换为规则卡并宣称 AI 已完成。

卡片数量不足如实显示。摘要只展示后端返回的可读字段和依据，不借模型补能力、联系方式、其他活动成员。AI 工具与模型任务边界见 [发现推荐与 Agent 工具](发现推荐与Agent工具设计.md)。

### 3.5 想法详情与新建编辑

想法详情分为“想法内容”“当前活动需求”“发起者”“讨论入口”。长期想法可关联多个活动，但当前活动详情只给该活动的成员和讨论投影；不能提供其他活动参与者名单。

“关注想法”立即保存关注关系；“申请加入讨论”按当前活动讨论空间的规则提交申请；“添加发起者为好友”进入好友申请表。三个按钮不互相代替，加入讨论后仍能继续浏览其他想法和人选。

新建页面录入原始想法、标题、问题、目标、阶段和希望的贡献。用户可先只输入原文，由本人点击“AI 帮我整理”生成草稿，或直接手动填写。AI 只整理选中想法，不能发布。编辑过程中显示保存状态、本人版本和实际 AIJob 状态。

预览页分别确认内容、是否关联当前活动、是否在该活动开放交流。发布动作前明确显示范围；“同时发一条广场帖子”如提供，只能作为额外明确动作，不默认勾选。无活动时保留草稿，不能把公开广场当作未选活动的默认发布目标。

新注册用户只要具备活动资格，就可立即发布并开放讨论，不等待注册满一天。作者从“讨论申请”待办查看和审批 incoming 请求；群管理提供归档/恢复，明确“归档只读”和“关闭新成员申请”是两个不同动作。

## 4. 广场：广泛发布与有来源的跨活动联系

### 4.1 信息流与发布

广场顶部切换“公开广场 / 当前活动”，并显示发布入口。公开广场是用户主动选择广泛发布的帖子流；当前活动页按活动资格读取。切换广场范围不改变发现的当前活动，也不会把广场内容送入跨活动 AI 找人池。

帖子包含作者最小身份、正文、发布范围标记、时间、可选的想法摘要/进展、评论与合法操作。首期按后端普通信息流排序和分页展示；全量帖子不是全量用户目录，不增加“按技能搜索全站作者”的入口。

发布表单包含正文、是否关联自己的想法/进展、发布范围、预览。用户明确选择当前活动或公开广场后再发送；正文中的本人主动公开内容也在预览里提醒。引用私密想法时只能选择并确认要公开的摘要，不让引用链接绕过想法本身权限。

“我的画像更新了”“已经成为好友”等动态必须由真实事件和明确发布动作产生，AI 不编造活动事实。发布失败保留草稿；重复发送遵循共享契约幂等规则，不产生两条帖子。帖子删除、作者不可访问或权限收回时显示内容不可用，不能继续展示缓存正文。

### 4.2 帖子详情与作者页

用户点击公开帖作者头像，进入该帖作者展示页。此入口可跨活动，页面显示 authenticated 条目；已是好友时另显示 friends 条目。private、原始来源和未选择的联系人始终不显示。

作者页可添加好友、查看合法公开内容、屏蔽和举报，不提供其活动成员列表或“推荐更多他的朋友”。发现能力仍被当前活动约束；该作者不因出现在广场就进入当前活动推荐池。

跨活动好友申请使用统一 **POST /api/v1/connection-requests**，来源 **source_type=public_post**。服务端须验证帖子可访问、接收人就是该帖作者；仅前端传“来自广场”不能成为授权证据。评论作者等未来扩展入口不能借一个无关帖子冒充作者来源，本期不增加第二套跨活动查人接口。

广场帖与人物画像是不同对象。未登录访客可以阅读服务端允许的公开帖子及公开评论，查看 authenticated 画像、发表评论或添加好友须登录。登录回跳保留帖子来源并重新验证，不能只按旧缓存打开作者页。

## 5. 消息：申请、私聊、讨论和通知

### 5.1 列表与请求处理

消息页将会话和系统待办区分，顶部可切换“私聊 / 想法讨论”，好友申请和系统通知以单独入口及未读数展示。徽标来自服务端未读状态，不用动画计数模拟新消息。

| 页面 | 展示字段 | 核心动作和状态 |
|---|---|---|
| 私聊列表 | 对方最小身份、最后一条可读消息、时间、未读 | 打开会话；已有好友不因切活动消失 |
| 想法讨论列表 | 想法标题、所属活动、群状态、未读 | 打开对应活动讨论；明确标活动，避免同想法跨活动串群 |
| 收到的好友申请 | 发起者、首条消息、来源、请求状态 | 接受/拒绝；接受绑定 expected_version |
| 发出的好友申请 | 接收人、已发送首条消息、状态 | 查看和撤回；待处理不能当成已建立会话 |
| 系统通知 | 好友通过、讨论申请处理、有关任务状态 | 打开相关对象；对象已失效时说明并保留通知事实 |
| 讨论申请 | 我的申请 / 我需审批，想法及所属活动、贡献说明、版本 | 使用 /me/discussion-requests；审批后更新真实成员状态，通知不是唯一处理入口 |

好友请求在 event_card 来源下按活动卡片验证，在 public_post 来源下按公开帖子验证。公开帖子跨活动申请不能被“双方没有共同活动”的错误拦截。请求中的首条消息在请求详情展示，未接受前不能无限追加私聊。

接受请求携带最新 expected_version；被撤回、被处理或版本不符时拉取最新状态，由用户重新判断，不自动改成另一次接受。同方向重复点击复用已有申请；相向发送返回已有 pending 申请和 requires_accept=true，提示原接收者明确接受，不提前显示好友或私聊。只有接受事务成功后才呈现唯一好友和会话。

遇到 CONTACT_CHOICES_CHANGED 时说明“对方原先选择分享的联系方式已更新，申请尚未接受”，提供“仍添加好友，暂不接收已变更项目”或返回；仅前者的实际点击提交 omit_stale_requester_contacts。自己选中的联系方式过期时重新选择，不能自动替用户确认新的版本。

### 5.2 私聊与想法讨论

首期会话支持基础文本和链接消息，展示发送中、已发送、失败及重试。发送动作由用户触发，临时消息与服务端消息确认后归并；重试不能重复发送。附件、音视频和复杂回执不作为本文默认实现内容。

登录首日即可发送合法作品和项目外链。限流等待时间以 Retry-After 为准，保持输入并展示可重试时刻；不能把普通格式错误、同一消息的幂等重试或账号年龄提示成违规。

移动端点会话进入完整聊天页，返回恢复会话列表；PC 使用列表和聊天区两栏，资料面板按需展开。进入历史消息页时保持阅读位置，向上加载不能把用户推回底部；收到新消息时若用户正在看历史，则显示未读提示，不强制滚动。

私聊顶部可打开好友资料、管理联系人共享、屏蔽或举报。普通画像按当前 visibility 动态投影，不缓存一份“成为好友当天永久可见”的快照。取消好友后 friends 字段不可再读；历史会话是否可读由后端关系政策决定，前端按返回的可读/可发送能力显示，不自行隐藏或解锁。

同一个想法在不同活动的讨论空间分别显示所属活动。讨论成员关系不产生好友关系，也不开放 friends 条目。离开讨论、移除成员或活动资格变化后，按后端结果禁用输入并移除无权继续读取的数据；不能因为此前缓存过消息继续开放访问。

新成员进入时说明“仅显示本次加入后的消息”；有权读取想法内容时提供当前目标/贡献需求入口，帮助理解讨论背景。不自动读取或总结入群前消息，退群后重新加入也不恢复旧成员期历史。

### 5.3 好友成立反馈

仅收到后端好友成立通知后展示电路接通反馈；按通知标识去重，不使用活动 event_id 去重。弹窗提供“开始聊天”和“查看好友资料”，关闭不改变好友关系。

用户在其他页面或离线时接受的申请，在通知和消息中可继续查看。弹窗不是唯一入口，不要求双方同时在线。减少动态效果时使用静态成功提示；重复订阅或断线重放不能连续弹窗。

## 6. 个人：本人信息的长期管理

| 区块 | 主要信息 | 操作与边界 |
|---|---|---|
| 我的展示页 | 昵称、头像、已确认画像 | 预览非好友登录用户、好友、本人视角 |
| 资料与画像 | 简历/GitHub 来源、预填条目、版本和处理状态 | 上传简历、连接或主动刷新 GitHub、确认补缺；已有来源自动恢复展示，不定时抓取或重跑画像 |
| 偏好与问答 | 全局默认协作偏好、已有批次答案 | 改答案、明确重新生成问题、确认新画像 |
| 可见性 | 每条 authenticated / friends / private | 批量选择后逐条调整；普通画像对所有好友统一，不做每好友授权 |
| 我的想法 | 草稿、已发布、所关联活动、当前进展 | 独立编辑、发布、关联/移除活动，不重写其他想法 |
| 关注与讨论 | 已关注想法、申请中、已加入的讨论 | 取消关注与退出讨论为独立动作 |
| 我的活动 | 已加入活动、当前活动、活动资格 | 邀请加入、切换、查看/修改该活动偏好 |
| 活动发现开关 | 当前活动是否允许成员发现我 | 本人显式开启/暂停；不自动退出活动、解除好友或停止已有讨论 |
| 好友与联系人 | 好友列表、本人联系人及共享记录 | 联系人独立选择和撤回；不把联系人当普通画像摘要公开 |
| 账号与隐私 | 登录方式、屏蔽、举报记录、数据管理 | 账号校验、删除等操作遵循后端契约，完成后清理本地数据 |

本人资料和处理记录保持私密存储，不自动到期，不通过“后台帮你更新”擅自访问外部主页或重新调用模型。只有用户进入所选模块重新编辑并启动整理时才产生相应任务；仅查看个人页、切换活动、修改可见性不调用 AI。

修改已有画像时旧确认版本继续可用，新建议先为草稿。前端展示哪些内容需要重新确认，不能因为重新抽取来源就扩大可见范围或恢复用户已删除的条目。版本、来源和适用性规则见 [Agent 用户画像与资料处理](Agent用户画像与资料处理设计.md)。

删除来源前列出受影响的已确认条目，说明删除会移除证据并暂停这些条目的对外投影。用户可之后将认可的内容转为本人自述并重新确认；不把删除来源悄悄解释为继续公开原有来源证明，也不为了删除操作调用 AI。

### 6.1 逐条可见性和联系人

下表为全局画像条目。活动条目必须额外通过所属活动的资格校验；在非好友/好友预览中均使用 visibility 条件 AND 相应活动资格，不能借全局好友关系展示另一活动的内容。

| 选择 | 非好友登录用户 | 已通过好友 | 本人 |
|---|---|---|---|
| authenticated | 合法入口可见，可跨活动 | 可见 | 可见 |
| friends | 不可见 | 可见，适用于现有及未来好友 | 可见 |
| private | 不可见 | 不可见 | 可见 |

“所有登录用户可见”只影响合法入口的字段读取，不创造全平台人物搜索。发现页详情仍绑定当前活动，而广场作者页合法跨活动；服务端需根据入口验证资格，再输出字段投影。

变更为更广范围时展示受众说明并由用户确认；收紧权限后立即更新本人预览，并使已有客户端缓存失效。不能承诺追回对方此前已经保存的信息。原始文件和内部来源不作为可切换公开的普通条目。

联系人独立于上表。成为好友不自动公开联系方式；双方各自选择要分享的联系人字段，撤回之后阻止未来读取。普通画像编辑页不会出现逐位好友勾选框，联系人管理可以按其专门契约展示已有共享对象。

## 7. 活动上下文、状态和返回恢复

### 7.1 状态归属

| 状态 | 保存位置与恢复原则 |
|---|---|
| 当前账号、成员资格、好友关系、可见性 | 以后端为准；前端缓存仅用于呈现，不能用于绕过鉴权 |
| 当前活动与列表类型 | 页面上下文中保留；进入和切换均验证有效资格 |
| 列表过滤、cursor 栈、滚动位置 | 会话级 UI 状态；按账号、活动、列表模式分别存放 |
| 随机批次 / AI run | 使用后端标识恢复；无效时按原模式重新开始，不互相替代 |
| 画像、想法、帖子和首条消息草稿 | 依共享契约保存；显示是否已落库；正文不写 URL 或分析日志 |
| 图片、文档来源与联系人 | 只由受权接口读取，不写入持久浏览器缓存或前端日志 |

活动切换先清理旧活动可见的列表与详情，再读取新活动；旧响应还须比较账号、活动和上下文版本，避免瞬时露出旧内容。订阅通知可以属于全局账号，但事件中的活动数据仍经过服务端权限裁剪。

画像 private 或 friends 内容不能因某次合法请求而被存入所有用户共享的 CDN/静态页面缓存。页面层按服务端投影渲染；缓存键与失效规则由共享契约和架构文档统一规定，不能只加一个前端显示条件。

### 7.2 AI 状态的通用呈现

AIJob 执行状态固定为 **queued / running / succeeded / failed / cancelled**，另有 **applicability=current / superseded / revoked**。执行成功不等于可采用；已更新输入产生 superseded，撤回来源或权限产生 revoked。

所有资料整理、问卷、想法整理、推荐解释组件复用这一呈现逻辑。仅 current 且校验通过的内容直接进入确认或推荐结果。superseded 的本人画像/想法建议可经独立 review 接口审阅差异，显示“仅供参考，需基于最新版本保存”；revoked 不显示历史正文。网络断线先恢复任务订阅或轮询，不擅自创建新的收费调用。

### 7.3 表单与离开页面

输入停止或失焦可以自动保存草稿，提交前等待必要保存结束。失败保留当前输入并提供重试；返回或关页前如仍有未保存内容，明确提示。多个标签修改同一对象时展示版本冲突，不能悄悄以最后一次返回覆盖另一个标签。

个人画像的更新、联系人共享、发送消息、发帖和接受好友都属于明确业务动作。所有可能产生外部效果的按钮在发送中禁用并使用共享契约的幂等机制；按钮恢复后也不能把一次成功请求重做成第二条业务记录。

## 8. 响应式与可访问性

| 场景 | 移动端 | PC |
|---|---|---|
| 主导航 | 底部四栏，避开安全区 | 左侧固定四栏 |
| 发现网格 | 通常两列，极窄屏一列 | 按可用宽度 3–4 列，宽屏限制卡片最大宽度 |
| 筛选 | 可展开面板/底部面板，显示已选条件数量 | 列表上方工具栏，必要时侧栏 |
| 详情 | 完整页面，可正常返回 | 可使用抽屉，但刷新/深链仍可独立打开 |
| AI 卡片 | 单张或小卡组，可滑动且保留按钮 | 居中卡片区，依据与动作清楚可见 |
| 消息 | 会话列表与聊天页逐层进入 | 列表＋聊天区，按需资料侧栏 |
| 编辑 | 单列字段、键盘避让、固定主要操作 | 适中表单宽度，可与预览并列 |

不维护两套不同业务流程。断点只改变布局，不改变可见性、可用功能和申请规则。页面在 320px 窄屏、常见手机、平板和桌面宽度均无关键操作溢出；缩放后不靠横向拖动才能读表单。

所有操作有文本名称与焦点状态；抽屉/面板打开后正确管理焦点，关闭回到触发按钮；Esc 可关闭非破坏性的浮层。图标按钮有可读名称，触控目标留出足够间距。状态同时用文字表达，卡片图片缺失时有占位，不制造布局跳动。

滑卡、拖动和悬停内容均有按钮或点击等价操作。装饰弹幕不被读屏连续播报；加载只在状态变化时播报。减少动态效果时取消弹幕、卡片大位移和电路动画，但保留所有信息和成功反馈。

## 9. 异常与降级矩阵

| 场景 | 前端处理 | 禁止行为 |
|---|---|---|
| 未加入当前活动 | 展示邀请加入入口，可继续广场/消息/个人 | 全站兜底发现 |
| 当前活动资格失效 | 清空该活动列表和敏感详情，说明不可访问 | 继续用旧缓存展示成员 |
| 普通列表为空 | 显示当前筛选无结果，允许清除筛选 | 编造推荐理由 |
| 随机批次无更多结果 | 显示批次结束，可明确换一批 | 为凑数请求其他活动 |
| cursor/批次失效 | 保留筛选，重新加载合法第一页或新批次 | 自行修改 cursor 或虚构页码 |
| 推荐模型失败 | 普通网格、随机浏览仍可使用 | 把服务错误说成用户不受欢迎 |
| 候选摘要失败 | 明确 AI 推荐未完成，用户可主动进入规则/普通发现 | 自动换成规则卡并宣称 AI 成功 |
| 请求超时但可能成功 | 按幂等记录/对象状态确认结果 | 自动重发两条消息或两个帖子 |
| 好友申请已被处理 | 展示最新状态，必要时重新确认 | 带旧 expected_version 自动接受 |
| 对象删除、权限撤回或被屏蔽 | 显示不可用，清理受影响缓存 | 暴露具体被谁屏蔽或继续显示私密资料 |
| 会话断线 | 标注连接状态，恢复后去重补拉消息 | 把未发送本地消息标为已送达 |
| 登录失效 | 重新认证并恢复合法页面 | 混用前一个账号的缓存和草稿 |

## 10. 组件、接口与交付分工

共享组件至少包含活动上下文栏、画像条目与可见性控件、三种视角预览、想法卡/人物卡、分页工具栏、AI 任务状态、好友申请表、联系人选择、通用草稿保存状态和成功通知。组件共享呈现，不共享越权数据；例如广场作者页与发现详情可以使用同一画像组件，但由不同的合法入口读取投影。

| 交互 | 已批准的接口/契约入口 |
|---|---|
| 普通发现 | GET /api/v1/events/{event_id}/discovery |
| 建立随机批次 | POST /api/v1/events/{event_id}/discovery-batches |
| 随机批次翻页 | GET /api/v1/discovery-batches/{id}/items |
| 创建 AI 推荐 | POST /api/v1/events/{event_id}/recommendation-runs |
| 恢复 AI 推荐 | GET /api/v1/recommendation-runs/{id} |
| 发送好友申请 | POST /api/v1/connection-requests；source_type 为 event_card 或 public_post |
| 接受申请 | 共享契约规定的接受接口；提交 expected_version |
| 画像/想法/草稿确认、帖子、会话、联系人 | 共享契约中的同名用例；本文件不新增平行 API |

前端依受权投影编写 mock，不能用一份全字段用户对象假装所有场景。领域规则、事务、讨论成员和好友生命周期详见 [社交后端业务设计](社交后端业务设计.md)；联调使用相同接口和错误结构，不把 mock 特有字段带入实现。

## 11. 移动端推送与通知触达

应用内通知统一使用 SSE；应用外触达使用 Web Push 与 Service Worker。消息持久化、未读、通知事实与系统推送分别处理，系统通知不是消息已读或必达承诺。本节只定义交互，订阅表、偏好、presence 与接口以共享契约为准。

### 11.1 启用时机与设备条件

不在首次登录后自动弹系统授权。首次发送申请或进入消息页后，显示可关闭的“有回复时通知我”；本人点击“开启通知”才请求浏览器权限、注册订阅并保存服务端偏好。拒绝、暂缓或设备不支持均不阻止使用。

先检查安全上下文、Service Worker、Notification 和 PushManager 能力，再给对应引导。iOS/iPadOS 的 Web Push 需要受支持版本中的主屏幕 Web App，并由用户实际点击触发权限请求；不能把“Safari 16.4+”写成普通网页标签里必定可推送。未满足安装条件时说明如何添加到主屏幕，同时保留站内消息入口。发布前按实际目标浏览器验证，不用 UA 字符串代替能力与安装状态检查。

依据为 [WebKit 官方说明](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)；2026-11-10 核对。该资料说明平台前提，不表示本项目已经验证推送。

### 11.2 订阅、偏好与退出

使用共享契约的 /api/v1/me/push-subscriptions、/me/notification-preferences 和 /me/presence，不在前端文档维护第二套表结构。

| 设置 | 初始行为 | 交互 |
|---|---|---|
| 系统推送总开关 | 未启用，等待本人点击及浏览器授权 | 授权和订阅成功后才显示已开启；失败说明具体状态 |
| 私聊、好友申请、讨论申请结果 | 总开关开启后默认提醒 | 可按类别关闭，不影响站内通知事实 |
| 群消息 | 总开关开启后默认提醒 | 可按群关闭；群归档、退群或失权后立即停止对应推送 |
| AI 任务提醒 | 默认关闭 | 用户可主动开启，不作为引导完成条件 |
| 免打扰 | 默认无 | 明确时区及跨午夜时段；不擅自假定服务器时区 |
| 已订阅设备 | 只显示安全摘要 | 可逐设备撤销，不展示 endpoint/keys |

退出登录和撤销会话由服务端撤销关联订阅，不能只依赖前端成功发送 DELETE。共用设备切换账号时，旧账号订阅先失效，新账号经本人操作重新绑定；不把旧订阅或未读状态沿用到另一个账号。

### 11.3 首条提醒、合并与失败

前台可见页面按共享契约上报有期限的 presence；SSE 连接本身不代表用户在看，也不替代 read_seq。所有实时页面退出后，已授权设备仍可在会话有效期间接收系统推送。

| 场景 | 触达行为 |
|---|---|
| 有未读事件且无有效可见页面 | 尝试立即推送首条，不等待离线满 5 分钟 |
| 事件发生时前台在线 | 先发站内通知；60 秒后仍未读且已离线时再补推 |
| 同会话短时间多条消息 | 首条及时提醒，随后按共享契约的 5 分钟窗口合并；不丢站内未读 |
| 暂时网络或服务故障 | outbox 有界重试，每次重新鉴权与检查偏好 |
| 端点失效或权限撤销 | 失效端点停止投递；不循环重试，不影响已保存消息 |
| 不支持/拒绝系统推送 | SSE、站内通知列表及重新打开后的未读正常使用；不反复弹授权窗 |

### 11.4 文案、跳转与隐私

首期系统通知仅用“你有一条新消息”“收到新的好友申请”等通用文案，不包含私信正文、群内容、联系方式或私有画像。是否已在应用登录不能作为在锁屏展示正文的理由。

通知点击只接受服务端生成的同源允许路由；重新验证登录、当前成员/好友、屏蔽及对象状态后才读取正文。被删内容、失效申请和已退出讨论显示不可用，不从推送载荷或本地缓存恢复正文。

### 11.5 验收要点

1. 初次登录不弹系统权限；用户点击开启后才请求，拒绝仍可完成申请和聊天。
2. 新注册用户发送合法作品链接并关闭页面，收到回复后在可用设备上触发首条提醒，无 5 分钟空窗。
3. 前台暂缓、随后关闭页面的未读事件能够经延迟复核补推；已读事件不补推。
4. 同会话通知合并、瞬时失败重试和重复 outbox 不重复产生业务消息。
5. 登出、会话撤销、换号、退群和屏蔽后旧订阅不能恢复无权内容；系统文案始终通用。
6. iOS 主屏幕前提、普通网页、拒绝权限和不支持设备分别测试，不将文档说明视作兼容测试通过。

## 12. 验收场景

1. 四主导航在手机和 PC 一致，活动切换不增加第五导航；完成开场可以进入对应页面。
2. 普通想法/人选网格使用 24 条默认分页，拒绝超过 48；上一页/下一页恢复正确，界面没有不受支持的随机跳页。
3. 进入普通发现和随机浏览均不调用 LLM；随机同批次翻页不重复乱序，刷新不自动换批次。
4. AI 推荐入口独立；同一 run 可恢复澄清，最终只显示通过校验的 0–5 张卡；0、1、2 个合格候选均如实展示，失败不伪造成功结果。
5. 无活动、无资格、切活动旧结果晚到、篡改 cursor 和随机批次来源，都不能看到其他活动成员。
6. 新想法可独立存草稿、整理和活动发布；保存不自动发广场；关注、讨论成员、好友关系互不替代。
7. 登录用户通过公开帖头像可以跨活动看 authenticated 画像并发好友申请；原本不属于当前活动的人仍不会进入发现/AI 候选。
8. friends 条目对所有已通过好友生效；private 对他人隐藏；未登录者不能读 authenticated 画像；原始资料与联系人没有随好友关系自动开放。
9. 好友申请首条消息需要用户发送；event_card 与 public_post 使用同一接口但分别校验来源；接受绑定 expected_version。
10. 好友成立通知重放只显示一次反馈；好友与私聊在切活动后保留；同想法不同活动的讨论成员及消息不会串用。
11. 页面返回、刷新、多标签冲突、网络失败、重复发送和重新登录均有明确状态，已保存草稿不丢失，未确认 AI 结果不覆盖正式版本。
12. 本人资料没有自动到期或后台周期性重编辑；个人中心只在本人启动任务时调用 AI，改可见性无需模型。
13. 键盘、读屏、减少动效、手机键盘展开及窄屏情况下，可完成浏览、发布、申请和回复。
14. 实现与验收记录汇入 [联调验收与交付路线](联调验收与交付路线.md)，不得以文档 mock 已通过代替真实联调。
