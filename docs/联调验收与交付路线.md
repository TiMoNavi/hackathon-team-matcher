# 联调验收与交付路线

> 日期：2026-11-11。本文规定应用实施阶段的验证，不表示下列应用测试已经运行。
> 产品决定见 [v3](完整方案设计_v3.md)，接口及错误码见 [共享契约](共享数据与接口契约.md)。本轮实际交付为设计文档，文档校验与应用验收分开记录。

## 1. 交付依赖与完成标准

| 阶段 | 交付内容 | 必须通过的门槛 | 后续依赖 |
|---|---|---|---|
| A 业务基础 | 身份、邀请、普通资料、规则题库、模板画像、活动上下文、想法、字段视图与接口合同 | 模型调用为 0 时完成资料输入、补问、草稿、编辑、隐私预览和确认；验证对象与活动资格 | 前端与社交 |
| B 社交闭环 | 四板块、好友申请、私聊、群讨论、论坛广场、通知和治理 | 请求并发、权限撤回、消息幂等、移动/PC 同功能 | 真实试用基础 |
| C 资料工作流 | 首屏简历/GitHub 导入、结构映射、规则补问、确认和重编辑；基础路径验收后接 AI 提取/提问/归纳 | 真实解析/读取、基础模式全程 0 次模型、AI 与规则共用资料/确认合同、权限/版本与恢复 | 首个用户可用版本及后续 AI 上下文 |
| D 有界推荐 | 普通发现/随机、规则与全文召回、有限模型精排、对话 Skill | 200→24→0–5、同一 run 预算、零 LLM 浏览、明确失败与用户主动普通入口 | 活动试点 |
| E 联调试点 | 合成规模、真实活动演练、监控、回滚和管理处理 | 权限与并发零已知高风险缺陷，业务关键路径全部通过 | 小范围发布 |

先实现可手动完成的用户闭环，再接模型。前端可以依据同一 OpenAPI 合同和假数据并行开发；假数据、假模型和演示弹幕均显式标记，不作为真实用户或推荐质量证据。

阶段 A/B 不依赖模型网关、embedding 或外部网页可用。embedding 未接通时全文与规则检索提供首版；扫描件无法解析时允许换文本或手填。

A/B 是内部工程增量，不代表只提供手填就可以交付首个用户版本。对用户试用前必须完成 C 中的简历上传/解析、GitHub 自动关联/公开导入与基础画像预填，并通过 R26 验收；不能用 mock、占位按钮或“后续接入”替代。功能必须提供，不强迫每位用户同时上传简历和连接 GitHub。

## 2. 测试分层

| 层级 | 方法 | 必须覆盖 |
|---|---|---|
| 领域与用例 | 内存仓储、固定 Clock、假模型、可控乱序任务 | 状态转移、版本、字段过滤、预算、来源归属 |
| 数据库集成 | PostgreSQL 事务、唯一约束和竞争请求 | 同用户对 pending 唯一、连接唯一、消息幂等、outbox 回滚 |
| API 合同 | 从同一接口定义验证输入/输出和负例 | 认证、owner/member、cursor、expected_version、错误码 |
| UI 端到端 | 手机和 PC 浏览器，真实接口或明确的测试替身 | 十步恢复、四板块、每条可见性、好友和聊天 |
| 规模与故障 | 合成活动、网关 spy/假响应、队列乱序、缓存旧版本 | 候选及请求上限、延迟与资源、降级、撤权传播 |

内存测试验证业务逻辑，不代替数据库竞争测试。文档本轮只做链接、围栏、JSON 示例和规则一致性检查，不声称已运行上述应用测试。

## 3. 可复现测试数据

建立活动 A、B 和 C。A/B 均有同名不同 ID 用户，部分用户双活动参加，部分仅一场；C 用于无候选和稀疏候选测试。另建无活动用户、已屏蔽对、普通好友对、已退出成员、被移除群成员及被封禁账号。

每位合成用户包含明确的 authenticated/friends/private 条目及少量已授权联系方式，混合有 GitHub、无 GitHub 但有设计/研究/硬件贡献的人。活动偏好故意不同，验证不会把 A 的投入时间写成长期事实。

想法包含草稿、活动关联、双活动关联、归档和多个同作者对象。公开帖子、活动帖子、删除帖子均有样例。原始资料全部虚构，包含正确文本、损坏文件、扫描件占位、超限内容以及提示注入语句；不使用真实简历或私信压测。

规模分别生成每场 200、2,000、20,000 名成员；另列想法数量，不能把成员数当成全部候选总数。固定随机种子、排序策略版本和字段可见性分布，让同轮结果可重放。

## 5. 规模与质量验证方法

### 5.1 测什么

用假模型记录完整请求字节数、候选数量和调用次数；用真实数据库记录检索扫描量、索引使用、CPU/内存、错误率及 P50/P95。固定推荐和自然语言推荐分别统计，不把模型等待与普通数据库分页混成一个延迟指标。

并发采用逐级 1、10、50 个请求进行初始试验，先在相同硬件和数据分布下记录基线，再决定是否启用向量索引或活动分区。并发等级为试验设置，不代表承诺支持的生产峰值。

~~~text
fixture人数 × 想法数量 × 可见性分布 × 并发等级
  → 普通分页 / 随机批次 / 固定推荐 / 自然语言推荐
  → DB耗时、候选数、序列化字节、模型次数、失败类型
  → 比较同配置与上次基线，而不是引用第三方“95%”宣传
~~~

硬验收为上限、权限、无重复副作用及零模型浏览；响应时间、推荐质量和成本先实测再设上线目标，不能凭设计文档预填“已达标”。

### 5.2 推荐质量

准备至少 30 组人工可解释的需求与期望依据，覆盖技术、产品、设计、硬件、研究、多想法和缺资料用户。评审候选是否满足硬条件、理由是否有引用、是否只偏向高项目数、是否重复曝光同一作者；记录实际结果和排序版本。

两位合适候选优于五位勉强凑数候选。没有 GitHub 不作为负面能力事实；没有时间字段标为未知，不假装满足“必须周末”硬约束。不能用接受好友率单一指标把用户或推荐质量等同于社交吸引力排名。

## 6. 可观测性、功能开关和回滚

指标包括普通接口延迟/错误、邀请失败、申请重复与接受率、消息重试、资料解析/确认率、AI输入量/调用数/用量异常、候选不足、权限剔除、队列时延和 outbox 积压。指标只记录必要标识和分类，不记录原始简历、私信、验证码或完整模型提示。

功能开关分开控制文本模型、对话 Skill、embedding、外链导入和推荐解释。关闭模型后保留资料及草稿，提供手动填写和用户主动进入普通发现的出口，不自动把AI失败当成功；不得把关闭AI实现为关闭整套发现和消息服务。
