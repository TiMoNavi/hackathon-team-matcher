# 对话、私聊与群聊插件接入规划

> 日期：2026-11-12。本文为接入设计；实际实施与验收状态以task和实施记录为准。
> 首轮仅新增规划文档；用户随后授权逐步实施，具体批次见实施记录R002起。全局设计、HumHub核心和原生mail不由本专项直接改造。
> 执行入口见 [task.md](task.md)，后续证据见 [实施记录](02_实施记录.md)。本文件为衍生设计，不替代冻结原稿。

## 1. 结论与边界

可以接入。建议新增可撤回的聊天 UI 插件和必要的服务端适配插件，复用 HumHub 身份、会话、文件与消息事实。独立指模块、页面、资源及升级边界独立，仍依赖 HumHub 与原生 mail，不承诺脱离宿主运行。

- 范围仅为现有聊天页面接入、私聊、群聊及相关接口；不接管全站导航、认证、发现、推荐、画像或活动选择。
- 原型保留在 [前端固定目录](../../frontend/对话%20群聊页面/README.md)，保留样式和交互；正式模式以服务端事实取代演示数据。
- 无需新增 LLM 调用、重建 FastAPI、平行消息库或常驻 Next 服务。前端构建工具只用于开发和产物生成。
- 接口与权限以 [共享契约及 HumHub 补充映射](../共享数据与接口契约.md)、[实施合同](../睡前全自动运行/04_HumHub实施合同.md)为依据；旧设计表名和端点不能冒充当前实现。
- 与 [全局任务](../睡前全自动运行/task.md) 的 N08/N09 协调所有权和依赖，本专项不擅自重写其状态或解除前置闸门。

### 2.1 两个创建缺口

CreateMessage 要求 message 和 recipient，且每次新建 Message；原生参与者的唯一约束只防止同会话同用户重复。现有创建路径未提供用户对唯一私聊，也未提供不发送首条正文的正式建群用例。

- **唯一私聊**：与 N08 锁定合法好友关系到原生 message_id 的唯一绑定、并发接受、重新建立关系和旧会话策略。不得按显示名称或“当前恰有两名成员”猜测私聊身份，也不新建第二套好友真相。
- **空会话**：底层 Message 可以单独持久化，不等于空会话业务已完成。须明确创建者资格、成员建立、配额、事务、通知、幂等及失败回收，禁止插入假消息使表单校验通过。
- 前端约定接受好友后建立唯一空私聊，申请附言不直接转成聊天消息；若既有接口方案冲突，在接线前记录并与 N08 对齐，不能静默复制附言。

## 3. 拟定模块与事实所有权

以下名称为提案，锁定前须检查工作区已有模块、N08/N09 产物及路由占用。若已有合适适配模块，扩展同一所有者，不再并行新建一套。

| 所有者 | 职责 | 不承担 |
|---|---|---|
| 原生 user/session、Space/membership | 身份、账号及有效活动成员事实 | 不接受前端伪造 actor/资格 |
| 原生 friendship 与 N08 适配 | 好友、申请来源、接受版本、发出历史、私聊绑定 | 聊天 UI 不持久化平行好友关系 |
| 原生 mail/file | message、user_message、message_entry、附件与基础通知 | 不复制消息正文或原生成员表 |
| matcher-chat（拟定） | 聊天用例、同源 JSON、原生适配、必要权限保护；承接明确分配的群邀请与消息元数据 | 不新增用户/current-event，不接管想法事实 |
| matcher-chat-ui（拟定） | 独立 HTML、React 资产、页面入口和 API 客户端 | 不拥有权限规则、消息或邀请事实 |
| matcher-ideas 与 N09 | 想法、活动发布、永久 Messenger 绑定、讨论资格编排 | 不把想法、Space、群聊合成同一对象 |
| matcher-recommendation | 唯一 current-event | 聊天模块只经现有接口查询，不另存选择 |

依赖方向为 UI → 聊天用例 → 端口 → HumHub/mail 适配器。业务层不依赖 React、HTTP 或具体 AR 类；控制器负责解析与响应，原生模型调用留在适配器。通过内存适配器验证规则，再用隔离环境验证真实数据库及会话。

如需扩展表，仅保存原生对象引用、邀请状态、版本、幂等键、稳定序号/历史边界和必要偏好，不复制消息正文与用户资料。表结构、外键删除行为、并发唯一约束、旧数据处理先经所有权复核。

## 4. 页面与同源接入

1. 在原前端目录增加小型构建桥，保留既有组件与原型预览；将演示数据适配器与正式 ChatApi 适配器分开。正式模式缺数据展示真实空态，不回填示例人物、聊天或定时回复。
2. matcher-chat-ui 提供独立文档和自有深链；候选页面路径为 `/matcher/chat`，须先查重。不依赖 matcher-webapp 的全站壳，不全局重定向原生首页或 mail 路由。
3. 构建产物放入插件自己的资源目录；显式 manifest、资源路径白名单与同源字体/图片。每页仅一个兼容 React 运行时，不同时套入 Bootstrap、jQuery/PJAX 壳或多个 Next 运行时。
4. 复用原生登录 session，HTTP 使用 same-origin credentials，写请求保留 Yii CSRF。bootstrap 只下发必要路径、版本和当前 CSRF 防护值；安全 JSON 编码、CSP/nonce 不放宽，不下发 REST 管理密钥。
5. 主题偏好可按原约定在浏览器记忆；登录、当前活动、联系人、消息和权限不以 localStorage 为权威。保留日夜主题、输入法保护、窄屏切换、独立滚动及减少动效。
6. 先实现已登录读取本人会话的薄片，再接发送和群规则。401、真实无会话、403、依赖未启用、加载失败分别显示，未完成按钮禁用或说明待接入。

## 5. 私聊、群聊与讨论资格

- **既有私聊**按合法关系及会话历史权限读取，不随切换当前活动消失；跨活动既有私聊不是全站查人的许可。新联系入口仍由 N08 验证 event_card 或 public_post 来源。
- **普通群聊**由用户明确创建；邀请人与受邀人资格、邀请待处理/接受/拒绝/撤回、版本冲突和终态幂等由服务端维护。受邀未接受时不得写入真实参与者、计作成员或读取消息。
- **活动讨论**绑定指定 idea_activity、Space 与独立 Messenger，会话绑定遵守 matcher-ideas 的永久唯一与 tombstone 规则。同想法跨活动不得复用成员或消息。读取、发送、邀请、分页、附件和晚到结果都重新校验对应活动资格及所需当前活动上下文。
- **历史边界**按共享契约明确入群起点、重新加入起点、退出撤权；原生仅凭当前 UserMessage 的授权不能独自表达 join_seq。规则未实现前不开放会泄露旧历史的群入口。
- **好友与群成员独立**。关注想法、加入讨论、成为好友、建立私聊各自有明确用户操作；UI 不自动发申请、拉群、发送附言或回复。
- **资料展示**仅取合法入口可见的最小成员信息；联系方式独立读取，不能从原生 REST 用户全量定义夹带资料。

基础会话列表、已有消息与发送适配可分批准备；好友申请和接受复用 N08，活动讨论依赖 N09 已锁定资格与绑定合同。已有群仅在其成员与历史边界、附件/通知及原生入口保护均已验收后开放，否则基础薄片只开放私聊，群入口等待 C07/C08。普通基础薄片通过不代表整个群聊或全局最低闭环完成。

## 6. 候选接口与数据合同

本节是待对齐清单，不是已上线 API。优先使用共享契约已有语义；实施前由单一集成人确认实际模块所有者、字段、方法、路由顺序及兼容方式。不能把原生 REST 输出或旧设计枚举直接标作已具备。旧共享契约的会话模型主要区分好友私聊与想法讨论，独立普通群的类型、成员权威和历史边界须在 C01 明确补充映射，不能把所有多人会话当作活动讨论；必要的共享文档修订交原集成人，不在本轮修改。

| 候选能力 | 拟对齐接口/合同 | 实施前决策 |
|---|---|---|
| 本人会话列表 | GET `/api/v1/conversations` | 类型、授权后的摘要、未读含义、稳定顺序与签名 cursor |
| 消息历史/增量 | GET `/api/v1/conversations/{id}/messages` | cursor 与 after_seq 互斥、初始最新页、历史边界、序号映射 |
| 发送消息 | POST 同路径，client_message_id/body | 唯一键及正文冲突、原生事务、附件关联、用户意图 |
| 已读 | PUT `/api/v1/conversations/{id}/read-state` | 单调 read_seq、不得越过可读范围；不将浏览列表标作已读 |
| 提醒偏好 | PUT `/api/v1/conversations/{id}/notification-preferences` | 真实持久偏好与版本；未实现不显示静音成功 |
| 创建群/邀请/接受/退出 | 先对齐 N09，再锁定具体端点 | 不与已有讨论邀请端点重复；受邀者真实接受才成为成员 |
| 好友申请/联系人/唯一私聊 | 消费 N08 合同 | 不在聊天模块另造申请状态、发出历史或好友关系 |
| 上传/预览/下载 | 复用原生文件能力并评估窄适配 | 上传所有权、大小/MIME、关联事务、撤权和历史边界 |

统一要求：

- actor 来自会话；原生用户/Space/Messenger ID 按真实正整数校验，不能仅因 ID 可猜测而忽略授权。
- 列表按契约默认24、最大48，并使用绑定用户/资源/查询/权限上下文的签名 cursor；会话历史不能直接照搬原生50条设置。消息排序、稳定游标与入群边界须一起设计。
- 共享契约的 seq/read_seq/client_message_id 并非原生现成字段。可评估引用 message_entry 的扩展元数据和事务分配；不能把全局 entry ID、时间戳或未读会话数冒充已满足合同。
- 发送成功须有持久 message_id；本地临时消息显示发送中/失败/结果待确认。原生无逐条送达/已读回执时，UI 不展示虚假的“已送达/对方已读”。
- 永久客户端消息唯一约束与有限期请求幂等分开；同键异正文冲突，每次重放重新授权。请求超时不自动换键再发，已存消息与通知副作用需有一致性方案。
- 返回统一 data/meta 或 error/meta；保留401、403、409、CSRF400及实际错误语义，兼容网络/非JSON失败，不以失败回退空数组或假成功。
- 内容按契约长度与安全渲染处理，不把原生富文本原样注入 DOM；附件列表与下载重新鉴权。上传失败、超限和关联失败均可恢复，不显示本地 blob 为已上传。
- 共享契约约定应用内实时通道统一 SSE。有界增量轮询或原生 live 信号触发再拉取仅为待 C01 与集成人确认的 HumHub 阶段适配候选，须记录与正式实时合同的差异，不代表 SSE/Web Push 已交付。事件只作提示，拉取仍授权；切会话、离页、撤权后清理订阅和在途结果，不在本专项擅自扩建全站通知。

## 7. 原生入口与旁路保护

新 UI 的隐藏按钮不能成为唯一防线。原生 MailController 的 search-user 使用全站可用用户查询；InviteParticipantForm 和 REST 加成员直接写入 UserMessage，均不能直接满足当前产品规则。

实施前建立覆盖矩阵：原生 HTML/JSON、REST、消息查询与编辑、成员 picker、加人/退出、文件上传/下载/预览、通知摘要、live 事件和关联详情。逐项确认合法来源、参与者、当前活动/讨论资格、历史起点和撤权。

优先使用模块 events 与 Yii `EVENT_BEFORE_ACTION` 等扩展点，在业务插件内统一限制旧入口或转接已授权用例；[HumHub Controller](../../backend/protected/humhub/components/Controller.php)沿用父级 beforeAction。钩子能覆盖哪些请求、执行顺序和 JSON/HTML失败结果须验证；不能先承诺所有核心零改动。

若某条文件或 live 路径无法通过已验证扩展点落实历史权限，先关闭对应不可安全开放的能力并记录缺口，再评估范围明确的适配；不为换 UI 扩大修改全局规则。不得凭 UI 卸载撤掉必要保护后宣称仍满足产品权限。

## 8. 撤回、卸载与数据保护

- matcher-chat-ui 提供 uiEnabled 开关：关闭时撤回新增菜单，新增页面明确不可用，保留合法原生聊天入口。UI 不拥有消息表，不负责删除会话或附件。
- UI 撤回与业务插件停用/卸载分开。已存在邀请、历史边界、唯一绑定或权限保护时，matcher-chat 不能随 UI 自动删除；依赖与存量数据处理另行审核。
- **禁止以 disable mail 回退。** [mail::disable](../../backend/protected/modules/mail/Module.php)会删除 MessageEntry，父类 disable 会执行卸载迁移；[mail uninstall](../../backend/protected/modules/mail/migrations/uninstall.php)会删除会话、成员和消息等表。
- 新插件迁移和卸载不得删除原生 mail/file/好友/Space 数据；扩展元数据保留、归档或删除策略另列且不破坏原始事实。禁用后仍受保护的功能可以明确拒绝，不能为“原生可用”放开历史消息泄露。
- 原生回退至少验证旧会话及新 UI 写入的消息在授权范围内可读写、附件仍受限、未读一致；只有真实回执才能声称“去掉还能跑”。

## 9. 实施顺序与验收边界

1. **合同与隔离准备**：核对并发工作、模块名、路由、N08/N09所有权；定义双用户/跨活动合成场景与旧入口矩阵。只读审计不算应用验收。
2. **只读薄片**：原目录构建桥、独立页面、真实session、本人会话/历史、真实空态、401/403及资源深链；不放开未完成的写入口。
3. **基础写入**：消息与附件、已读、版本和永久幂等；两用户真实读写、重复提交/断网结果确认、拉黑/退出/撤权。
4. **群与讨论**：空群创建、邀请接受/拒绝/撤回、成员历史边界、唯一私聊绑定及N09活动讨论接线；事务、并发与旧入口负例全部验证。
5. **兼容与撤回**：原生/新UI交叉读取，启停及重复升级、资源和日夜/移动交互、附件/live旁路、备份恢复；明确每个尚未实现或不可用能力。

验证按层进行：内存用例测试 → 隔离数据库与 HTTP → 双用户浏览器 → UI 撤回/升级恢复。仅构建通过、内存演示、空库安装或源码存在，不足以声明聊天闭环通过。

本轮完成标准仅为规划、任务拆分和文档链接/结构核对；未来实施状态、命令、结果、阻塞及数据影响逐批写入本专项 [实施记录](02_实施记录.md)，不得提前填成功。
