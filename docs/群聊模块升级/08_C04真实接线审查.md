## 4. 事务与持久版本专项

1. 明确唯一事实来源、锁行、锁顺序和写入者。旧入口能修改原生成员/entry；只锁新表不自动隔离旧写。
2. 一致性快照不代替撤权可见性。写前写后重验应能观察并发提交，或有共同锁协议及明确线性化点。
3. revision 不能只依赖内存、缓存、可复原 hash 或异步事件。持久指纹检测仍须处理读间 A→B→A、并发分配、撤权重入和 sender 恢复。
4. read_seq 目标、存量和合并返回值都对应当前代次下获准真实 entry/墓碑或合法 0/join 基线；拒绝未来、空洞及旧代次高位。
5. entry→seq 仅元数据，不复制正文。新增/删除/编辑与 seq/revision 一致性、故障回滚和通知时点分别验，事务成功不代表外部通知 exactly-once。
6. 重复原生成员须负例及真实并发证据；不擅自改核心唯一索引。

## 8. 新适配器首轮观察与修复

已读取首批迁移、DirectAdmission、NativeProjection 与 SqlState。发现以下需实现者解释或修复的候选缺口，尚未完成真实复现。

- synchronize 检测失效后在当前事务写 revoke，随后用例抛 404/409 会被 transaction 整体回滚。必须证明失败读取后的持久失效不会丢失，避免原生事实恢复后旧代次或 cursor 复活。
- pairEnabled 轮询 User.status；若两次请求之间停用再恢复、无持久生命周期记录，hash 仍可相同。仅 Message/Entry/UserMessage/File 钩子不足以证明用户状态失效的单调版本。
- Yii Controller.runAction 先 createAction，再 module beforeAction，最后 controller beforeAction。REST 身份替换发生在最后阶段；聚合入口不得依据旧 session actor 决定放行。提前文件拦截还须核对实际路由解析与 token，而不只匹配 URL 字符串。

上述已向后端所有者反馈；先保持隔离验证范围，不据此宣称当前生产存在漏洞。

随后只读回读 SqlReadStore：已加入外层同步/持久撤销、内层 savepoint 回滚用例失败的结构，尚待真实事务证明。正常 append 误推授权 revision 和 metadata 缺表误允许 disable 两项已静态修复：append 只推进 last_seq，旧条目编辑/删除和标题变化才升级版本；缺表时业务模块拒绝 disable。User 生命周期持久撤销已加入，bulk/raw SQL 绕 AR 的限制保留。
