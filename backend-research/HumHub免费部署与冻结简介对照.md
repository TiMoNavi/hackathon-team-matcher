# HumHub 免费部署与冻结简介对照

> 日期：2026-11-11。依据：用户指定的冻结简介及后续明确选择。
> 冻结简介只读；本文件承接解释、取舍和插件建议，不冒充原稿。用户后来明确的 Space 活动映射、Messenger 仅用于一对一、Q&A 社区和 Clean Theme 预览优先于早期候选映射。
> 部署入口见 [运行说明](../backend/deploy/README.md)，免费包版本及校验见 [模块清单](../backend/deploy/modules.lock.json)。本地原生模块预览与目标产品实现分别记录。

## 1. 这套免费组合的作用

它适合验证社交底座和模块交互：用户、Space、角色、帖子、评论、好友基础、私聊、问答、赛程、图集、链接与文件预览。Clean Theme 让原生页面适合预览；正式前端依然使用 AffectUI 与 Shadcn UI Kit，不把主题当成已经做好的产品前端。

插件可以复用现有模型、权限框架、事件和迁移系统，这条路线值得推进。不过，REST 模块有接口与我们的每个业务用例都已有可用接口，是两件需要分开核对的事。当前免费包没有实现活动上下文、个性化资料授权和 AI 队友推荐。

## 3. 个人信息字段怎么复用

以下按“产品字段如何建模”分析。默认 ProfileField 名称来自本地 v1.19.4 的 InitialData；安装后的实际定义见 [字段导出](../backend/deploy/profile-fields.json)，不含个人资料值。头像和用户名属于其他模型，不应误算为普通 ProfileField。

| 原稿字段 | 可复用基础 | 本项目建议 |
|---|---|---|
| 头像 | 核心个人头像与文件访问 | 复用上传/缩略图；与原始简历附件分开授权 |
| 昵称 | 用户显示名及用户名机制 | 明确显示昵称与登录标识的区别，不强迫昵称唯一 |
| 姓名 | firstname、lastname | 可适配中文全名；展示与登录账号分开 |
| 年龄 | birthday 字段 | 可显示计算年龄或本人确认区间，不能因此默认公开完整生日 |
| MBTI | 无本项目专用预置字段 | 可选结构化属性，不以模型推测值自动公开 |
| 方向 | 自定义字段能力 | 使用可维护标签；区分长期方向与当前活动偏好 |
| 学校 | 自定义字段能力 | 可多条教育经历，不把学校和整个经历塞进一个字段 |
| 技能 | 自定义字段能力 | 多值标签、来源和用户确认；缺乏依据时不自动给熟练度 |
| 一句话自述 | title/about 可参考 | 单独明确短简介字段，避免 title 职称含义混乱 |
| 在找 | 自定义字段能力 | 优先归到活动偏好，可随活动变化 |
| 角色 | 自定义字段能力 | 区分技术角色与 Space 管理员角色，防止混淆权限 |
| 获奖情况 | 普通文本字段只能勉强承载 | 用可重复结构化记录及稳定属性 ID |
| 学业经历 | 普通资料文本可参考 | 用可重复经历记录，可对每条配置展示范围 |
| 项目经历 | about/链接/图集可辅助 | 独立结构化经历，关联本人选择分享的链接与图片 |

不建议立刻向原生 profile 表追加全部业务字段。先设计确认版本、稳定属性 ID、可见性与全局/活动区分，再决定简单展示字段如何投影到 HumHub。否则 AI 草稿、用户已确认资料和原生资料页会形成互相覆盖的多份权威数据。

## 4. 建议如何自研插件

### 4.1 第一版先做一个项目插件

建议命名为 **team-matcher**（建议名，尚未创建），在一个插件内部按领域分目录。这样保持 HumHub 模块化单体、同库事务和统一账户，不急于分成多个服务或维护两套好友/成员数据库。

| 内部子域 | 负责规则 | 复用对象 | 不应负责 |
|---|---|---|---|
| activity | Space→活动映射、邀请码、当前活动、成员资格、发布范围 | Space、Membership、Calendar、Content | 不接管全局私聊，不把日历参与当活动成员 |
| profile | 原始资料私存、导入、AI 草稿、本人确认、逐条可见性、联系人授权 | User、File、ProfileField 的展示适配 | 不让普通登录重跑 AI，不让短代码公开草稿 |
| discovery | 同活动候选、筛选、随机、游标、推荐 run 与预算 | PeopleQuery/成员查询、已确认可展示摘要 | 不跨活动补卡，不在普通翻页调用模型 |
| idea | 想法本体、想法与活动关联、活动内讨论成员和消息、项目 Agent 用例 | Post/Comment/Q&A 可作展示或迁移适配 | 不把关注想法等同好友，不复用另一活动的讨论历史 |
| social | 好友申请版本、明确接受、私聊资格、去重与联系人关系联动 | Friendship、Messenger | 不重建第二套原生好友权威状态，不以模型声称的同意发起写操作 |

HTTP 控制器、现有模块调用、数据库和 AI 客户端放外层适配；领域与应用用例通过明确接口衔接。REST Controller 保持薄层，负责输入/输出转换，不把所有规则堆到控制器。先用内存适配器验证活动隔离与披露规则，再验证真实 HumHub 集成。

### 4.2 插件与原生代码的边界

- 优先使用 HumHub 模块配置、事件、权限、内容模型和迁移机制；没有必要先改一遍核心代码。
- 封装普通用户业务接口，补齐共享契约；原生管理员接口不能直接授权给前端或 AI。
- 现有入口也要纳入权限检查，不能只有新 API 严格而原生 URL 可以绕过。
- 邀请码加入仍调用原生添加成员机制；私聊继续使用原生会话/消息模型；必要的版本与幂等字段通过插件迁移维护。
- 给 Messenger 落实一对一约束时覆盖创建和加人，不只改按钮。本次原生预览未声称已完成这个限制。
- 需要 Python 处理简历或模型调用时，可通过任务适配器使用；用户、活动、好友和授权仍需明确唯一权威存储，不能默认 PHP/MySQL 与原计划 FastAPI/PostgreSQL 同时拥有相同数据。

### 4.3 AI 留口的位置

建议先定义应用接口，不先给模型一个全站管理员 token。资料处理从本人主动导入或重编辑开始；任务写回草稿，确认后才形成正式画像。普通浏览、登录、切活动和改可见性不启动重编辑。

推荐先在已验证活动内合并召回不超过 200 个候选，最多 24 份最小摘要送模型，最多 5 个结果；正常发现为 0 次 LLM 调用。异步返回时再次核验活动资格和资料版本。澄清、失败与预算继续服从共享契约，不自行扩大调用次数。

项目 Agent 的回答需有清楚的 AI 身份与触发来源；它不能替用户发好友申请、接受邀请或授权联系人。公开发布、普通发消息和授权仍须来自用户真实操作。

## 5. 先后顺序

1. 先验证本次免费预览：登录、Space、帖子评论、问答、日历、私聊与文件组件是否能正常打开和操作。
2. 第一条自研链路仍是邀请码加入 → 切活动 → 活动帖子评论 → 获准资料 → 普通人物发现，同时落实首期资料导入与确认模型。
3. 再实现想法记录、活动内讨论与好友私聊约束，明确原稿中多人讨论需求如何承接。
4. 最后接 AI 推荐精排与项目 Agent；数据量小也不跳过活动边界和预算规则。

阶段一不需要购买 Survey、Advanced Survey、Onboarding Tour、Job Listings 或 Professional。Q&A 能验证社区交流，但不能把它当成已经完成原稿所有多人聊天要求的证据。

## 6. 当前运行结果

安装、模块状态、页面检查及待配置项以 [部署说明](../backend/deploy/README.md) 和部署目录的核验报告为准。整个环境只供本机原生能力预览，不接真实用户资料，不对外开放，不宣称已经验证 300–400 人并发。

本次实际核验补充：

- 登录、活动、赛程、问答、Gallery、Link List、Messenger 和 PDF 原生页面可打开；队列重建任务、cron 和启停恢复已通过。
- 私有 Space 的成员访问正常，非成员的原生 URL/API 拒绝访问；这只证明原生私有容器边界，不能等同于本项目当前活动发现已实现。
- 普通用户调用 REST 管理型 User API 返回 403，说明仍需提供本人资料与获准字段的受控业务接口。
- PDF 原文件拒绝非成员/访客下载，但 PDF Viewer 弹窗在已知 GUID 时会显示文件名。正式资料导入前应补统一可读检查，不能直接把此组件接到真实简历库。

本轮不修改冻结原稿，也不把插件分析反向写进用户原文。正式业务实施时，再按用户确认更新当前衍生设计与统一契约。
