## 1. 先给决定

**建议先用免费核心组合验证，当前付费采购额为 ¥0，保留全部 ¥700。**付费表单和引导模块并非毫无价值，但它们最直观的页面能力主要服务 HumHub 原生前端。我们的前端确定重做，是否值得付钱取决于后端模型、接口和权限到底能省多少工作。

这轮重点结论：

1. Calendar 适合赛程，活动成员、邀请码和上下文仍由 Space 承担。
2. 按用户最新要求，Messenger 只承担一对一私聊；以前“想法讨论绑定 Messenger 会话”的方案停止作为当前建议。
3. Q&A 可以先承担求助、问题与回答；普通交流和想法进展也可使用核心帖子/评论，暂不买收费论坛。
4. Survey 不是免费依赖。Survey €90 + Advanced Survey €45 = **€135，参考折合 ¥1,009.81**，超过预算；仅买增强包不能用。
5. Survey 的公开 REST 说明目前是 **GET only**。即使买了表单系统，也不能直接省去新前端提交资料的接口、AI 处理和逐条可见性开发。
6. PDF Viewer 按用户要求进入首批接入清单；Social Stats 暂缓，因市场兼容标签停在 1.17。

## 2. 新的业务映射

以下表区分产品方向与实现建议；原生模块已可预览，表中项目业务约束并未随安装自动实现。

| 项目概念 | 建议承载方式 | 状态与关键边界 |
|---|---|---|
| 一场黑客松/活动 | 一个 Space | 延续此前已同意的成员、组织者、管理员、邀请码和当前活动映射 |
| 开幕、分享、组队截止、路演等赛程 | 该 Space 内的 Calendar 日程 | 对“Calendar 是赛程”的实施解释；不是用日历报名替代活动成员关系 |
| 人与人的私聊 | Messenger | 用户本轮明确限定一对一；原生多人入口需服务端约束 |
| 社区求助与经验问答 | Space 内的 Q&A | 免费候选；回答、投票、最佳答案接口待验证 |
| 想法、招募和进展 | 轻量想法记录 + 核心帖子/评论；适合问答的内容可关联 Q&A | 本次建议；不把职位申请流程整体改造成想法系统 |
| 想法讨论 | 原生帖子评论/问答先验证异步交流；独立想法讨论子域承接多人会话 | 冻结简介的多人讨论与项目 Agent 尚未实现，不复用已限定一对一的 Messenger |
| 演示图、项目截图、作品展示 | Gallery | 图片有价值，不能取代想法本体与访问控制 |
| 仓库、演示站点、学习资源 | Link List | 可分别关联活动或本人资料；仍需验证合法访问入口 |
| 广场 | 用户明确发布或分享的公开内容集合 | 不通过活动结束后搬迁所有内容来生成 |
| 个人画像 | 自有确认与可见性用例，按需适配 HumHub 资料 | Survey/Onboarding 可评估辅助录入，但不能成为权限规则的替代品 |
| 普通找人 | 服务端当前活动成员查询 + 已确认、可展示字段 | 在线状态/社交连接可以辅助，候选不足如实返回 |
| AI | 服务端受控的资料处理与推荐用例 | REST 提供部分数据访问能力；不直接赋予模型管理员或社交写权限 |

### Calendar 与 Space 为什么都需要

一次完整活动可能有十几条赛程。把每条赛程都当成独立活动，会把成员、邀请和当前上下文拆散。推荐保持“一个 Space 包含多条 Calendar 日程”。邀请码加入 Space；报名某条日程是附属动作，不能获得另一个 Space 的访问权。

本项目前台的当前活动赛程按服务端确认的 Space 筛选；Calendar 的原生全站概览不直接作为活动内人物发现入口。跨活动的历史日程查看如需要，应有单独的已授权入口。

“首批”表示项目接入优先级；当前预览安装状态另见运行说明。没有通过适配检查的插件，不能因为免费就全部启用。

## 4. Survey / Advanced Survey 能否做资料填写和 AI 回复

### 4.1 可以复用的部分

如果我们保留 HumHub 原生表单界面，Survey 能省去通用题型、答案草稿、导出和管理页面的工作；Advanced Survey 再增加模板、预填、审核状态和通知。做活动反馈、需求征集、志愿者报名一类表单，适配度更高。

它也可以作为资料录入的候选外层适配器，但不能直接把调查答案当成最终画像。其“预填当前资料字段”是把已有值带入表单，没有证明具备“AI 理解简历并预填”的能力；问卷管理员审核也不等于用户对每条画像公开范围的确认。

### 4.2 我们仍然必须补什么

| 本项目要求 | 插件现成依据 | 缺口 |
|---|---|---|
| 多种资料输入、暂存和恢复 | Survey 字段、草稿/自动保存 | 字段与项目画像模型之间的映射；独立前端写入 API |
| 简历上传、GitHub 公开来源导入 | 表单可收文件；GitHub Sign-In 可识别用户 | 资料私存、来源读取、抽取、去重和身份映射 |
| AI 根据资料追问、解释或补全 | 这些插件未声明 AI 能力 | 按需任务、模型适配器、结构化结果校验、失败恢复和预算 |
| 每条画像选择可见性 | Survey 有答案/作者层级可见设置 | 每条属性的 authenticated/friends/private；动态好友授权 |
| 第 5、8 步逐条可见性预览 | 未声明该流程 | 自建确认界面与服务器校验 |
| 只发布本人确认内容 | 表单状态/管理员审核可参考 | 不可变确认版本、expected_version、原始资料与公开画像隔离 |
| 不覆盖新版本 | 未声明本项目版本/任务语义 | AIJob 的 execution_status、applicability 和失效校验 |
| 联系方式单独授权 | 未声明 | 独立于普通画像的授权记录及读取校验 |
| AI 回复到社区 | 无明确原生能力 | 若回复公开，应先生成草稿，经用户确认再走普通发布流程 |

**关键判断：在前端完全重做的前提下，Survey + Advanced Survey 能复用的后台功能不足以直接证明值得先花 €135。**公开写接口的缺口会削弱“购买即可接前端”的预期。这里评价的是当前适配，不否认模块作为原生问卷系统的价值。

### 4.3 更适合当前预算的资料处理链路

1. 首个资料页面前置简历与 GitHub 公开来源入口，原始资料私存。GitHub 首次注册完成身份关联后读取本人公开来源；后续普通登录不重抓。
2. 应用用例接收本人导入或主动重编辑请求，通过后台任务调用 AI 适配器，得到结构化草稿与待补充问题。
3. 用新前端组件展示预填结果，允许修改、补缺、保存退出；保留十步引导以及第 5、8 步逐条可见性预览。
4. 用户确认后才形成新的正式画像版本，提交携带 expected_version。未确认草稿和原始资料不进入人物卡片、短代码或公共内容。
5. 普通资料读取根据合法入口及 authenticated/friends/private 判定；联系方式独立授权。
6. 已被取代或撤销的任务结果不覆盖新资料；浏览、切活动和修改可见性不触发重编辑或 AI。

这是待实施的流程建议。采用项目 architecture-patterns：规则由领域/应用用例维护，HumHub 模型、Survey（若以后采购）、数据库、HTTP 和 AI 都是外层适配；不在前端脚本、问卷 CSS/JS 或模型提示词里承担授权。后续先用内存适配器验证业务规则，再做 HumHub 集成测试。

## 5. Messenger、Q&A 和想法讨论的具体边界

### 一对一需要后端落实

Messenger 原生有参与者管理能力。我们限制一对一时，不能只隐藏前端“加人”按钮；创建会话、邀请参与者、REST 与原生路由都必须受同样规则约束。私聊和已建立的好友关系保持全局有效，不因切活动自动消失。

继续沿用项目的好友及私聊资格规则；不能因为 Messenger 接受某个用户 ID，就让它绕过本项目的联系人权限、请求版本和合法入口检查。

### Q&A 能做社区，但有明确语义

Q&A 很适合“求设计队友”“这个 API 怎么用”“赛程问题”等求助；投票和最佳答案可以提高实用信息的可见度。闲聊、项目进展和开放式想法讨论可先用核心帖子/评论，避免所有内容都被迫选一个“最佳答案”。

同一想法关联两个活动时，分别关联各自的帖子或问答线程；成员和讨论内容不能串用。此方案提供异步交流，不承诺实时群聊、输入状态或聊天历史权限已实现。

## 6. 发现、推荐与自动关注

Online Users、Suggested Following、Auto Follow 解决三个不同问题：展示活跃状态、依据关注关系产生建议、自动写入关注关系。**三者叠加也不会自动成为本项目的找队友系统。**

建议普通发现按下面顺序执行：

1. 服务端验证当前活动及成员资格。
2. 仅在该活动内召回选择可被发现的用户；加入后 discoverable 默认 false，不能由插件自动打开。
3. 只用用户已确认的 authenticated 字段生成发现卡片，好友也不能让这类卡片额外暴露 friends 字段。
4. 再按用户筛选、资料完整度或经同意使用的在线状态排序；先过滤、再分页，候选不足原样返回。
5. 关注图可作为以后的一项信号，但不能跨活动取人来补卡，也不能通过解释暴露第三人的受限社交关系。
6. 普通列表、筛选、随机和翻页调用 AI 次数为 0；用户主动发起 AI 推荐时才按既有最多 200/24/5 的候选预算处理。

Auto Follow 默认关闭。新人引导优先显示“建议关注活动组织者/公告账号”的卡片，由用户确认；如果以后提供自动关注选项，也须明确其行为并允许管理关系，不能把它统计为用户主动兴趣或成功匹配。关注不会自动建立好友或授权联系方式。

## 7. 活动结束、分享与全局广场

用户账号本身是全局的；结束一个 Space 不需要把用户账户“转成全局”。应该区分活动归档、成员关系变化和公开发布。

**建议默认归档活动并保留原权限，不自动向广场公开。**确需展示成果时，由作者主动发布一份获准公开的摘要或帖子，明确选择可发布的附件；其他人的评论、参与信息、私聊和原始简历不随之自动公开。

Move content 是管理员迁移工具，官方明确提示只移动内容或成员可能影响日历参与和任务指派。因此不把它挂在“活动结束”自动任务上；也不把 Space 管理员角色直接复制成全站管理权限。

Share content 可以作为主动分享的技术候选，但上线前需确认：

- 操作者有权读取源内容、有权向目标发布，且该内容允许被分享。
- 分享到新活动不让其成员间接读取源 Space 的私有详情、附件或评论。
- 原帖变私有、删除、成员退出后，分享入口、搜索结果和附件的行为一致。
- 广场作者入口只展示获准资料，不能扩张成全站人物列表或跨活动推荐。

这些是本项目规则，不是声称插件已存在安全缺陷；本轮未测试实际分享实现。

## 8. 登录、通知和独立前端的适配

### 8.1 登录组合

GitHub 和邮箱验证码是既有要求；Google 是用户本轮提出的新增候选。GitHub/Google OAuth 模块可以作为入口，账号绑定须落到同一份权威用户身份，避免按未经确认的邮箱自动合并账号。

JWT SSO 仅在另有可信身份服务时作为桥梁；没有必要因为模块免费就再建一套重复登录。官方手册提示资料字段可在每次登录写入，因此只同步必要身份字段，不把画像内容交给 JWT 登录载荷覆盖。2FA 是第二道验证，邮箱 2FA 不等于既有邮箱验证码注册/登录已经完成。

### 8.2 通知与文件

Firebase 模块可作为推送候选。FCM 服务标为免费，但新前端仍需做设备订阅、权限提示、注销/换账号后的 token 解绑、通知跳转鉴权等集成。桌面、移动端及目标用户实际网络中的到达率本轮均未验证，不能承诺全覆盖。站内通知继续作为基础通知通道。

锁屏/系统推送默认只放必要摘要，避免泄露私聊或私有资料；点击通知后重新校验对象权限。Firebase 服务账户私钥只放服务端，不进入 React 或文档。

PDF Viewer 属于首批需求，但安装 HumHub 预览模块不会自动让新的 React 页面显示 PDF。前端仍要接入获准的文件访问方式与阅读界面；私有简历不因预览需要而公开。Text editor 仅按需启用，控制附件写权限。

### 8.3 模块能力与 API 能力分开验收

| 能力 | 本轮接口证据 | 对新前端的处理 |
|---|---|---|
| 核心用户、帖子、评论、Space、文件、通知 | REST 手册列有端点 | 验证普通用户权限；不要把管理员 API key 放浏览器 |
| Calendar、Messenger | REST 手册列有模块 API | 验证活动归属/参与者限制，并固定模块版本 |
| Survey | 官方仅承诺 GET API | 如采购，提交、草稿保存和更新接口仍需补或向作者核实 |
| Onboarding | 有数据结构和原生跳转开发文档 | 未确认完整引导 REST 接口，不能直接复用页面行为 |
| Q&A、Gallery、Link List、Online Users 等 | 本轮未确认完整独立前端 API 覆盖 | 优先查公开源码；缺什么补什么，不通过管理员权限“打通” |
| Google/GitHub/JWT/2FA | 各自的认证集成 | 验证跨域、回调、会话、安全绑定和二次验证组合 |

REST 的 /api/v1 前缀相同，不代表它已满足共享契约。仍须适配普通分页默认 24/最大 48、签名 cursor、合法入口 access_ref、expected_version、写入幂等与统一错误结构。普通查询、详情、分页和异步结果都应重验当前活动或合法例外；不要保留可绕过新规则的旧路由。

REST 可服务 AI 调用后的应用用例，但 AI 本身不持有全站管理员令牌。模型读取最小获准数据；发帖、发消息、接受好友与授权仍须来自用户真实操作。

## 10. 后续实施顺序与验收要求

本节是恢复实施时的建议顺序，不是本轮已经执行的安装计划。

### 第一批：关键链路与必备资料

先接 GitHub 身份、邮箱验证码用例、REST 适配、Space 邀请与切换，再接文件/PDF 预览、首期资料导入和确认。随后验证活动内发帖评论、获准资料读取、普通人物发现；并行准备管理员 2FA。首期资料导入不能因改用插件路线被降为长期待办。

验收必须覆盖两个活动的列表/详情/分页隔离、合法广场作者例外、默认不可被发现、逐条可见性、任务失效与旧路由绕过检查。普通发现不得调用 LLM。用内存适配器验证用例后，还需真实 PHP/数据库和 HumHub 集成检查；两类结果分开报告。

### 第二批：交流与赛程

接一对一 Messenger、Calendar、Q&A；Q&A 接口未覆盖时核心帖子评论可先验证公共交流，但不宣称问答模块已经打通。检查私聊切活动不丢失、第三人不能被加进会话、同一想法跨活动的讨论不串用。

### 第三批：展示、通知、运营

按需求接 Gallery、Link List、Firebase、受控分享和同活动在线状态。Social Stats 在 1.19.4 兼容验证前保留关闭；Move content 只作经验证的运维操作，不设置活动结束后的自动搬迁。

### 采购检查点

只有当实测表明 Survey 或 Onboarding 的模型与接口能显著减少我们要写的代码，且最终结算不超 ¥700 时，再提出具体购买项。当前已有免费原生运行环境和有限检查数据，没有付费包试用；不据此声称节省了多少天开发，也不承诺 300 人并发已验证。
