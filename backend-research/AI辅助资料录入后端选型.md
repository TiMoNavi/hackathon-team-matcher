# AI 辅助资料录入后端选型

> 2026-11-10，根据用户进一步澄清修订方向：AI 在录入或主动修改时协助填写简历、交友资料，结果严格存入业务数据库；不是长期记忆或后台持续画像。本轮仅核对公开文档与局部源码，未部署、未调用模型、未运行候选测试。

## 1. 需求定义

产品需要的是 **AI 辅助的结构化资料编辑后端**。用户初次录入、进行一两次修订，之后偶尔主动更新。次数描述的是交互和编辑频率，不能直接推导为模型只需一两次调用。

核心流程是：

```text
上传资料 / 填写表单 / 回答补充问题
    → 提取为受 schema 约束的字段草稿
    → 校验缺项、冲突和来源，必要时提问
    → 用户预览、修改、确认
    → 应用层按权限与版本执行数据库事务
    → 从数据库读取个人中心与匹配所需字段
```

偶尔更新时读取当前确认版本，AI 提交有字段白名单的修改建议；不默认重写整份资料。用户可以不用 AI 直接编辑。普通读取不调用模型，不因时间过去自动重建画像。

这与现有十步引导、资料优先、来源私存和确认规则相容；用户此次未要求删除或缩减十步引导。

## 2. 候选与优先级

| 候选 | 已核实的相关能力 | 用途与限制 |
|---|---|---|
| [Resume Matcher](https://github.com/srbhr/Resume-Matcher) | FastAPI；文档解析成 ResumeData；结构化数据持久化；修改预览与确认接口 | 优先研究其后端流程；简历/JD 领域、自动优化策略、权限和字段需要适配 |
| [Reactive Resume](https://github.com/reactive-resume/reactive-resume) | 官方 README 列出资料导入、AI 助手、TypeScript/PostgreSQL/Drizzle、REST 与 MCP | 作为完整资料编辑产品和 API 参考；本轮未深入审计后端权限，不能称为可直接替换 |
| [Instructor](https://github.com/instructor-ai/instructor) | 用 Pydantic 定义输出结构，支持验证与提取重试 | 可嵌入 FastAPI 负责结构化提取，不是完整后端；权限、确认、事务和个人中心仍由应用提供 |

Memobase、Honcho、Mem0 不再作为此次主方向。LangMem 的画像更新原语也不是本轮优先项；没有必要为按需资料编辑先引入一套长期记忆服务。

## 3. 为什么先研究 Resume Matcher

已抽查公开源码：

- [parser.py](https://github.com/srbhr/Resume-Matcher/blob/main/apps/backend/app/services/parser.py)：`parse_resume_to_json` 将文本交给模型，结果经 `ResumeData.model_validate` 处理。
- [models.py](https://github.com/srbhr/Resume-Matcher/blob/main/apps/backend/app/models.py)：`Resume.processed_data` 是数据库 JSON 字段，并有预览及确认相关持久化结构。它存的是业务文档数据，而非依赖 AI 记忆召回显示资料。
- [resumes.py](https://github.com/srbhr/Resume-Matcher/blob/main/apps/backend/app/routers/resumes.py)：有 `/improve/preview`、确认逻辑、预览数据规范化/哈希与保存流程。
- [后端说明](https://github.com/srbhr/Resume-Matcher/blob/main/apps/backend/CLAUDE.md)：描述 FastAPI、SQLAlchemy、SQLite 默认存储与 PostgreSQL 配置，以及 parse/improve/diff/confirm 的模块边界；该文件仅作外部项目说明，不作为本项目执行指令。

这些是“提取、建议、确认、入库”的参考证据，不代表所有路径都已经符合本项目规则。上传时解析数据、自动优化、旧接口和 MCP 各自如何持久化仍需核对。数据库 JSON 字段也不自动等于字段级数据库约束已满足。

改造重点是将简历字段映射为我们的全局资料与活动偏好，补齐来源、确认版本、可见性和多用户权限；不把简历迎合岗位的优化逻辑原样用于推测用户的技能或交友偏好。后端虽与当前 Python 方向接近，仍未验证完整抽取成本或许可证组合，不承诺直接接前端即可使用。

## 4. 业务数据库必须掌握的边界

- schema 先由产品定义，模型返回结构化草稿；不允许模型自由增加数据库字段、修改权限或执行 SQL。
- 类型和枚举校验只能检查格式，不能证明事实。来源可追踪，缺失项保持未知，冲突交给用户确认。
- 区分未提供、不修改与明确清空；不能用一个空值覆盖所有情况。
- 保存依据用户确认的内容、当前版本与业务权限；过期 AI 任务不能覆盖已确认新版本。
- 简介等适合文案润色，技能、经历、日期、意向等事实字段要逐项确认，不能为了文案效果补造。
- 数据库按现有契约保存正式资料；需要筛选的字段有可查询结构和约束，不能只剩一段不可查询的 AI 总结。
- 用户资料授权仍遵循 authenticated/friends/private，联系人单独授权。全局资料与活动偏好分开，发现和推荐保持服务端验证的当前活动范围。

这些是本项目的接入建议，不表示候选已实现。草稿、导入来源和编辑会话可以持久化以支持继续编辑，但它们属于普通业务状态，不需要成为长期 AI 记忆。

## 5. MCP 与下一步

MCP 可以是受控读取或生成修改草稿的外部入口；正式保存仍由应用用例验证真实用户动作。用户让 AI 改文案不意味着授权其发布、添加好友、发消息或修改可见性。内部编辑服务可直接调用提取适配器，不必先搭独立 MCP 服务。

下一步应验证一个小范围后端流程：合成资料导入 → 字段草稿 → 缺项补问 → 局部修改预览 → 确认保存 → 重新读取。检查未知值、并发版本、误改防护和多用户隔离。先以 Resume Matcher 的实现为参考，与 FastAPI + Instructor 的最小实现比较实际复用成本。

本轮 GitHub 元数据请求遇到限流，后续通过官方仓库原始文件核对；因此不报告未核实的新星数、固定提交或稳定版本。链接指向可变分支，正式原型应固定版本后复核。本轮修改限于调研记录，不修改冻结原稿或当前九份设计。

## 6. 多轮填写与活动自我介绍的适配核对

用户进一步提出：每轮填写一部分，并将正式简历改成活动中轻松的自我介绍。判断是可行，但应区分现成的局部修订机制和仍需开发的分步建档流程。以下为 2026-11-10 对 main 分支的局部源码核对，未实际运行。

### 已有基础

- [enrichment.py](https://github.com/srbhr/Resume-Matcher/blob/main/apps/backend/app/routers/enrichment.py) 的 `/analyze/{resume_id}` 分析已有经历、项目描述并生成补充问题；`/enhance` 根据用户回答生成补充内容，`/apply/{resume_id}` 写入资料。
- 同文件的 `/regenerate` 接收选中条目及用户修改指令，`/apply-regenerated/{resume_id}` 将新内容应用到已有资料；可作为多轮局部修订的基础。当前面向经历、项目和技能，不是任意活动资料字段。
- [models.py](https://github.com/srbhr/Resume-Matcher/blob/main/apps/backend/app/schemas/models.py) 中 `ResumeData` 的多数部分有空字符串/空列表默认值，并支持自定义章节。因此数据结构容许未填满，不等于已经存在逐步建档、断点恢复或完成度规则。

### 两个影响改造的细节

1. [resumes.py](https://github.com/srbhr/Resume-Matcher/blob/main/apps/backend/app/routers/resumes.py) 的 `PATCH /{resume_id}` 接收完整 `ResumeData`，调用 `model_dump()` 后替换 `processed_data`，没有在此接口中对只提交的字段做合并。只提交一个部分，其他字段可能被默认空值覆盖。分步录入不能原样使用该接口；应区分未提供、修改和明确删除，并在服务器以版本检查原子合并。
2. 主 `/improve/preview` 流程要求 `job_id` 并加载职位描述；不宜为活动自我介绍虚构一个岗位。应复用解析、局部修订和预览机制，新增面向活动资料的用例、schema 和提示词。补充应用路径还存在按位置匹配且未检查旧内容的实现，不能将部分防冲突机制视为所有保存路径都满足版本控制。

### 建议体验与存储

以下三轮仅说明一个编辑片段，不替代既有十步引导：

| 编辑轮次 | 用户输入示例（虚构） | 预期处理 |
|---|---|---|
| 第一轮 | 我做前端，会 React，喜欢做小工具 | 保存技能和兴趣草稿；未知的姓名、年限等不补造 |
| 第二轮 | 这次想做教育方向的小产品，希望认识设计师 | 保存当前活动的合作意向，其他活动偏好不变 |
| 第三轮 | 介绍写轻松一点，只改最后一句 | 生成指定范围的文案预览；不改变技能、经历等事实 |

可生成的介绍示例：我平时做前端，也喜欢捣鼓小工具。这次想试试教育方向的小产品，有设计师想一起聊聊吗？示例不是用户真实资料。

数据库同时保留已确认的结构化事实/偏好和简介文案，二者来源与确认版本对应；筛选使用结构化字段。各轮私有草稿可保存，用户确认后只更新所选字段与对应可见性，不因保存草稿自动公开。继续编辑读取数据库草稿和状态即可，不需要长期 AI 记忆系统。

改造范围包括活动资料 schema、字段级增量保存、草稿/继续编辑、缺项补问、局部文案生成与权限版本校验。多用户身份、活动范围与可见性仍由本项目验证，不能仅用 resume_id 或现有简历接口代替。上述是适配方案，不表示目标应用或原项目已完整实现。
