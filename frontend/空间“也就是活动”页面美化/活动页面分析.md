# 黑客松活动页面分析

分析日期：2026-11-12。当前交付为分析与建议，尚未实现页面或完成接口联调。

## 1. 需求理解与结论

目标是一场黑客松的活动主场。用户进入后，应能看到这场活动的样子、了解大家正在做什么、找到下一项日程，并知道自己可以如何参与。顶部活动风采建立氛围，论坛承接交流，日程帮助行动。

视觉直接继承现有首页及 Signalry 原版，包括字体职责、浅色背景、紫色主操作、少量青柠强调、容器比例、留白、卡片材质与交互。活动名称、现场照片、作品演示和成员主动发布的内容承担页面的个性。

后端适合继续使用。已查到的 Space、Gallery、Post/Comment/Like/Topic、Calendar 能构成这页的基础。主要工作是重组前端呈现，再核对或补齐新界面所需的数据适配。源码中存在某项能力，不等于当前 Space 已启用该模块，也不等于新 React 页面已接通。

本次使用 shadcnuikit 与 frontend-design 两项页面设计 Skill，并按父级约定阅读 architecture-patterns 检查业务边界。组件来源仍限定为 Shadcn UI Kit 与 AffectUI，通用设计建议服从首页和 Signalry。

## 3. 旧页面为何显得像论坛

保存的旧截图与 Space 页面源码共同反映出几个问题。

1. 顶部主要是横幅、巨大头像和文章/成员/关注数，缺少能表达黑客松现场的内容。
2. 左侧模块菜单、中间动态流、右侧活跃记录形成三栏，注意力被导航和附属信息分散。
3. 日程、问答、普通帖子混排在时间流里，想找赛程需要从动态中识别。
4. “某人加入空间”等系统记录占据醒目位置，实际合作进展与活动内容不够突出。
5. 灰色背景、密集边框和偏管理界面的模块名称，使页面更像内部社区工具。

源码依据为 [Space 首页](../../backend/protected/humhub/modules/space/views/space/home.php) 与 [空间菜单](../../backend/protected/humhub/modules/space/widgets/Menu.php)。现代化应同时处理信息优先级、内容类型和布局。

## 4. 后端能力与页面对应

| 页面内容 | 已查到的能力 | 前端适配与限制 |
| --- | --- | --- |
| 活动名称、简介、介绍 | Space 模型有 name、description、about；容器有原生头像/横幅展示 | REST 的 Space 输出没有完整覆盖 about 与展示素材，需要核对取数入口 |
| 参与资格与管理权限 | Space 有加入策略、可见性、角色；Membership 有邀请、申请、正式成员状态 | 产品当前按邀请加入，不能因底层支持自由加入就自行开放报名 |
| 活动风采 | Gallery 支持空间相册、图片、说明、权限及与帖子关联 | 现有相册分页入口返回含 HTML 的 JSON，不是可直接给新 React 图库使用的结构化媒体列表 |
| 活动论坛 | Post、Comment、Like、Topic 与内容流；Content 有置顶能力 | 复用帖子与评论；论坛分类可以映射 Topic，但“公告/找队友/进展”等分类需配置，不能假定已存在 |
| 活动日程 | Calendar 有起止时间、地点、时区、参与状态、提醒和 ICS；有 REST 控制器 | 在当前 Space 范围读取，参与单项日程与加入整个活动分别处理；提醒、导出等还需单独接入验证 |
| 同场伙伴与想法 | matcher 系列已有当前活动资格、发现及想法活动关联能力 | 从既有发现入口读取获准字段；想法关联现有会话不能当作自动建群或开放讨论工作流 |

### 需要补齐或确认的事项

**活动资料。** 已检查的 Space 核心字段没有独立的整场活动起止日期、主会场、报名截止、创作/路演阶段及首页精选内容配置。Calendar 的单条赛程可以提供节点；整场活动元数据与重要节点的对应关系仍需定义。不能把 Space 的 enabled/disabled/archived 当作报名中/创作中/已结束，也不能直接拿最早、最晚日历条目推定整场活动时间。

**风采精选。** 相册存储可以复用，但“哪张是封面、哪几张在顶部展示、按什么顺序、谁可见”需要有可保存的选择。可以评估指定相册或轻量展示配置，接口契约确定后再实施。图片及其说明的可见性必须沿用源内容权限。

**新前端的数据入口。** 原生 REST 基类关闭 Session，使用已配置的 API 认证；它的分页默认是 page/limit。不能假定浏览器已有 HumHub Cookie 就能调用，也不能与产品设计中的 cursor 契约混用。应复用既有登录与权限用例，经受控适配输出页面所需数据，具体接口名称另行确定。

**普通成员入口。** 原生 REST 的 Membership 列表要求 Space 管理员身份，不适合拿来直接构建普通参会者的伙伴列表。优先复用当前活动发现的获准资料投影；自助接受邀请也应走相应成员流程。

**帖子内容结构。** 原生 Post 输出以 message 为主，没有独立标题。普通讨论卡可以直接呈现正文摘要；公告或想法有可靠标题来源时再展示标题。不能为了卡片美观，把前端临时生成的标题写成后端已有字段。

**赛事扩展。** 本次没有确认队伍报名、作品正式提交、评委评分、排行榜或奖项管理的完整实现。它们不是本轮三块核心内容的前置条件，页面也不应提前显示虚构的作品数、奖池或实时在线人数。

接口依据另见 [REST 基类](../../backend/protected/modules/rest/components/BaseController.php) 与 [成员管理接口](../../backend/protected/modules/rest/controllers/space/MembershipController.php)。

## 5. 建议的信息架构

活动页面是当前活动的详情与参与入口。进入主应用后，沿用“发现 / 广场 / 消息 / 个人”四个主导航，活动选择器作为上下文控件；活动内部单独设置“概览 / 论坛 / 日程 / 风采”。首页营销导航的外观可以复用，文案按所在场景调整。

```text
全局导航                                      当前活动 / 我的入口

活动风采首屏
  活动名称 + 一句话介绍
  日期 / 地点 / 已确认的活动阶段
  主视觉照片与精选现场内容
  按成员身份提供参与操作

活动内导航       概览        论坛        日程        风采

概览内容，宽屏约 64% / 36%
  精选现场照片与项目进展                 当前 / 下一项日程
  官方公告与近期讨论                     活动指南与组织者
  找队友、提问、分享入口                 同场伙伴发现入口

论坛     当前活动帖子 / 分类 / 发布 / 评论详情
日程     日期切换 / 按时间排列的议程 / 日程详情
风采     当前活动相册 / 图片说明 / 大图查看
```

### 顶部活动风采

首页的中心标题、光场、网格与外围浮动卡片很适合转为活动首屏。保留相同构图语言，将内容换成真实活动名称、主办方选定照片、现场合作和作品演示。标题与操作保持清楚，照片和轻动效形成氛围。

首屏操作随身份变化。未加入时按授权入口提供“通过邀请加入”；受邀者接受邀请；已加入者优先看到“找同场队友”“查看日程”；管理者另外提供活动管理入口。原型中的活动阶段、时间和照片如用示例，须清楚标注。

首次打开概览时完整显示首屏。进入论坛、日程或从内容详情返回时，可收为紧凑活动标题栏，保留活动名称和上下文，减少反复经过大首屏的成本。

### 论坛

采用头像、作者、正文摘要、可选图片、话题标签、评论与点赞的内容流。官方公告单独突出；找队友、项目进展、提问、资料分享通过活动话题组织。默认采用后端支持的时间排序，热门排序和未读统计待有可靠接口再提供。

概览只呈现少量内容预览，完整论坛在独立标签内读取和翻页。发布时明确“发布到当前活动”，公开广场继续作为另一种明确发布范围。论坛帖子用于交流，正式想法仍走既有想法用例，评论不自动创建群聊。

### 日程

默认使用日期切换加纵向议程列表，把签到、开场、组队交流、创作、导师交流、作品展示等实际赛程按时间展示。上述名称只是可采用的内容类型，不代表当前活动已经发布这些日程。

每项显示时间、标题、地点和状态，点击打开详情。桌面可增设月历切换，手机优先保留议程列表。当前进行中根据真实时间与时区计算，关闭/取消状态另行尊重后端。成员端以阅读和合法参与为主，编辑及拖拽排期只向有权限的管理者开放。

### 风采

顶部精选与完整相册共用同一来源。点击图片查看大图、说明及合法来源帖子，支持键盘关闭和前后查看。新活动尚无现场照片时可展示主办方提供的海报、场地或往届资料，但必须标明归属；没有素材时呈现真实空状态。

## 7. 状态与范围

活动是 Space，Calendar 条目是该活动内的赛程；加入活动、参加单项日程、关注想法、进入讨论和成为好友分别处理。

活动可见性与成员资格同时约束内容。私有活动不能用风采展示绕过权限；成员发现与推荐限定服务端验证的当前活动。公开广场仍按其独立规则工作。切换活动时清理旧活动列表与详情，晚到响应必须检查上下文。

原型至少覆盖受邀、已加入、无权访问、活动已归档、暂无图片、暂无帖子、暂无日程和加载失败。业务操作只有收到真实成功响应后才显示已保存或已发布；演示版本明确说明使用本地状态。

产品规则继续引用 [主应用交互设计](../../docs/前端主应用交互设计.md) 与 [共享契约](../../docs/共享数据与接口契约.md)，不在本目录复制另一套业务定义。

## 8. 建议的第一版范围

第一版围绕四项可见成果推进：活动风采首屏、概览、论坛、日程，完整相册由风采入口进入。先用明确标注的演示内容验证页面及手机体验，再按后端能力逐项接数据。

可验证的关键交互包括活动内导航、照片大图、论坛分类与帖子详情、发帖草稿、日程日期切换、日程详情、身份对应的参与入口。后端暂不支持的动作，给出明确状态或保留为后续范围。

实施时对照 1440、768、390、320px；检查实际英文及中文字体、长活动名称、内容溢出、键盘焦点、减少动态效果、返回位置、权限失效与切活动后的旧响应。当前分析未执行这些新页面验收，也未把已有首页测试记录当作活动页通过记录。

建议先确定这套内容层级，再在当前目录实现第一版可交互预览；活动元数据、媒体列表和认证适配作为后续接口核对清单。
