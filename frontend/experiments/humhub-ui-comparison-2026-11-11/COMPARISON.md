# HumHub 三条前端路线：实现效果与改造难度

> 历史技术实验：本文保留路线比较与当时的验证结果，旧页面风格不作为当前依据。核心页面按 [Signalry 原版风格与布局规范](../../design-system/team-matcher/MASTER.md) 执行。

验证日期：2026-11-11。目标是三个首页原型的可行性、实际视觉效果和接入成本；没有进行正式项目迁移。

## 结论

三条路线都已经做出可交互首页，并通过同一套浏览器检查，各 17/17 项。前两条运行在真正的独立 HumHub 实例中；第三条运行在独立 Next.js 生产预览中。就“保留 HumHub 后端，并持续使用 AffectUI 与 Shadcn UI Kit”这个目标而言，建议优先继续路线 2。

视觉效果主要取决于页面设计，并不是 React 自动比 PHP 好看。本次原生版也能实现完整的新视觉，但需要把 React 组件的结构和状态转写；路线 2、3 则实际直接使用了两套组件源码。此次没有安装整个付费站点模板，也没有证明所有模板都能无改动兼容。

## 做出了什么

共同题目为“同频 CoLab / AI 创造者周末”。三页采用同一份合成数据，展示活动概览、四位成员、角色筛选、姓名/技能搜索、成员详情、本地关注和想法卡片。桌面为侧导航与内容卡片，手机为单列与底部导航。

| 路线 | 实际页面实现 | 双库使用方式 | 看图后的观察 |
| --- | --- | --- | --- |
| 1 原生视图升级 | PHP / Yii 输出 HTML；加载 HumHub、Bootstrap、jQuery、PJAX、Clean Theme 资源 | Kit 资料卡和 AffectUI 清单作为参考，转写为 PHP / CSS / DOM 交互 | 页面完整、自然；活动横幅占据较多空间，手机第一张成员卡出现较靠后 |
| 2 独立 React 插件 | HumHub 模块路由返回完整独立 HTML，发布 Vite 构建资源 | 原样使用 Kit Card、Button、Sheet 与 AffectUI ProgressTracker | 组件视觉与主题一致；详情侧栏、清单和手机布局均正常，版面偏舒展 |
| 3 独立 Next.js | 单独 React / Next.js 项目及生产服务 | 原样使用 Kit Card 与 AffectUI ProgressTracker | 首屏更紧凑，手机第一张成员卡能完整出现；页面自由度高 |

这些布局差异可以在任意路线中重新设计，不是框架能力的硬限制。统一截图位于 evidence 下的三个路线目录，画面尺寸为桌面 1440×1000、手机 390×844。已逐张查看桌面及手机截图。

路线 1 为了隔离实验，以独立模块挂载原生 PHP layout；它验证原生技术改造的可行性，尚未打包成覆盖全站的正式主题，也未升级 Bootstrap 主版本。路线 2 虽然按 HumHub 模块安装，但页面内部已经是新 React 前端。路线 3 则仅实现了独立首页，没有执行全站重写或删除原有框架。

## 改造难度：已发生的工作与尚待验证的工作

以下难度是基于此次代码、构建和浏览器运行情况的判断，不是完整迁移的工时报价。

| 比较点 | 1 原生视图升级 | 2 React 首页插件 | 3 独立前端重写 |
| --- | --- | --- | --- |
| 做这个首页 | 中等：样式和 DOM 状态要自己转写 | 中等：页面组合直接，增加一层 PHP 模块桥接 | 较直接：独立 React 环境可组合现成组件 |
| 组件接入成本 | 高于另外两条；TSX、React state 无法直接作为 PHP 执行 | 低；本次四个组件原样使用 | 低；本次两个组件原样使用 |
| 实际遇到的框架工作 | 原生样式叠加；AppAsset 注册；PJAX 重复绑定防护 | 模块控制器；独立文档；构建 manifest 与资源路径；Vite CSS 类型声明 | Next.js 工程与生产构建；没有原生框架适配 |
| 推广到全站的主要工作 | 逐页覆盖视图和主题，兼容既有模块及交互 | 接通授权业务接口，逐页迁移，同时处理新旧导航一致性 | 完成认证、权限、数据接口、上传、消息、路由及整体迁移 |
| 运行和部署 | 使用现有 PHP 运行方式；本页无需新增前端构建依赖 | 构建时用 Node，产物由 PHP 同源提供；本页无需常驻 Node 服务 | 本次用独立 Next.js 服务；后续部署模式须另定 |
| 本次尚未证明 | 全站主题、完整 PJAX 导航、升级兼容 | 真实登录/权限/数据接入、旧业务页的视觉连续性 | 与 HumHub 的认证和全部业务对接 |

“插件”与“重做前端”是两个维度。路线 2 可以把新前端作为 HumHub 插件交付；如果未来逐页接管用户界面，插件里同样会承载大范围前端重写。真正节省的是部署与后端共存方式，不是自动省掉业务迁移。

自写代码范围不包含配置、lockfile、第三方组件、演示数据、生成产物或测试证据；各路线细项见各自 metrics.json。JSX/CSS 的换行习惯差异较大，不以物理行数给难度排名。

资源统计来自同一浏览器脚本，取 Resource Timing 中 script / link / css 发起的条目之 decodedBodySize，排除 HTML 与未被此筛选收录的字体、图片等资源。原生版含框架和主题 bundle，其他两页只含当前应用资源。它反映本次首页载入内容量，不是完整站点体积、真实传输量、速度评分或通用性能结论。尤其不要把 PHP 开发服务未压缩的字节数与其他方案的 gzip 估算直接相除。

各代理保留了约 5 分 55 秒、13 分 55 秒、13 分 26 秒的原型墙钟记录，但起点及是否计入环境等待并不相同。不能据此宣布原生路线开发效率最高，也不能推算正式全站工期。

## 统一测试与独立证据

父任务执行 [compare-browser.cjs](compare-browser.cjs)，使用本机 Microsoft Edge / Chromium。三条路线共享相同数据与测试钩子，最终共 51/51 通过。

- HTTP 200，初始四张卡片，演示数据说明。
- 前端角色筛选，Python 技能搜索，空结果，清空后恢复列表。
- 关注状态切换，成员详情内容，Escape 关闭；手机筛选和详情关闭。
- 两种视口均无页面横向溢出，无 JavaScript 异常、无所监测静态资产 HTTP 错误。
- 原生版能检测到 HumHub / jQuery / Bootstrap；React 插件与独立版没有这些原生前端对象或样式。

原生关注按钮为图标，测试通过 aria-pressed / 无障碍名称核验状态；其他版本也允许通过可见文字核验。首次公共脚本只检查文字时产生过一次误报，已修正断言并重新完整运行三条路线，没有为迎合测试改动原生按钮设计。

各代理还分别完成 PHP 语法、TypeScript、生产构建与补充交互检查。路线 2 另测了 1024、768 宽度、深色切换与 AffectUI 清单；路线 3 另测了 AffectUI 清单。本次不是完整的跨浏览器、无障碍、弱网或长期回归验收。

## 隔离环境与共同问题

本次从本地 HumHub 1.19.4 分发归档单独解压创建实例，没有把当前原项目切换成实验站点。实例位于 /tmp/humhub-ui-compare.6qn_jdwx/humhub，使用 8193 端口、新 MySQL 实例、新建演示数据库和生成的独立凭据。未复制原业务数据库；PHP/MySQL 二进制安装通过只读用途的符号链接复用。

分发包缺失若干依赖的 dist 目录，曾导致原生框架资源加载失败。本次从原安装中补齐缺失依赖文件，只写入隔离实例。这是三条路线之外的共同环境准备问题，不能算作原生页面技术路线的失败。详细记录见 [isolation.json](evidence/isolation.json)。

原生模块与 React 模块均实际通过 HumHub 模块管理启用。8193 以 localhost 打开，原有 8090 仍使用 127.0.0.1；业务数据库与应用配置分离。

## 建议下一步

如果继续做验证，选择路线 2，先接一个受真实登录和当前活动权限保护的只读成员列表，核验“登录态 → 活动权限 → 数据接口 → React 页面”的完整链条。之后再决定扩展个人页、广场、消息等页面。该步骤尚未执行，本次到三个首页效果与改造难度比较为止。

当前所有关注、匹配比例、通知和想法均为合成数据或本地交互。保留 HumHub Controller、CSRF meta 和同源路由，不等于业务权限已经通过验收。本实验不涉及付费包完整性、许可权益或远程 registry 下载权限的再次验证。
