这个流程的核心逻辑非常清晰：用“即时反馈”和“低输入成本”对抗传统填表带来的流失率，通过游戏化的角色生成机制（RPG 建卡）来替代冰冷的简历填写。

围绕你提出的流程与核心疑问，整套产品的画像设计与流程优化方案如下：

一、 用户画像（Persona）需要包含什么？
黑客松和初创团队匹配与传统职场招聘完全不同，没人关心冗长的教育背景或标准化绩点，大家只在乎“你能做什么、想做什么、能不能一起肝”。

画像应当分为四个模块，生成像 RPG 角色卡一样的轻量面板：

模块	核心字段（AI 自动提炼 + 用户微调）	作用
1. 战术角色与职能	
• 主职/副职（如：主攻前端 / 副修 UI 设计；或 算法 / 硬件胶水工）


• 硬核技能标签（3~5 个最熟练的栈，如 React, PyTorch, ESP32）


• 动手段位（快速 Demo 级 / 商业交付级 / 算法构架级）

快速确定队伍缺位匹配度
2. 参赛/创业状态	
• 当前意向：带着点子找人（发起人） / 寻找硬核队伍加入（自由人）


• 精力投入度（肝度）：志在冲奖熬夜流 / 拓展人脉重在参与 / 寻找长期创业合伙人


• 协作偏好：线下集中黑客松 / 纯线上远程协作

避免价值观与目标不一致导致退赛
3. 证明与高光（Proof of Work）	
• 一句话高光（如：“曾获天大黑客松三等奖”、“独立开发过万级用户的微信小程序”）


• 代表性开源/落地项目（AI 从 GitHub 提炼提取 1~2 个最相关的 Repo 简介）

建立第一印象与信任度
4. 隐藏/授权隐私层	• 微信号 / 手机号 / 真实姓名 / 完整简历原文 / GitHub 主页	初始完全打码，仅在双向发起申请并同意后解锁
二、 流程重构：解决“想法该放前面还是后面”的冲突
你在第 9 步提到的直觉非常敏锐：如果把想法放在最后，用户在前面感知不到利益，容易半路放弃；但如果想法放最前面，没有基础身份卡，AI 无法进行有针对性的协同对话。

建议将流程调整为 “点子钩子（Hook）→ 极简建卡（Profile）→ 点子深化（Plan Mode）→ 最终开箱（Match）”：

[首页动态演示] 
      ↓
[登录 + 弹幕氛围] (GitHub 一键优先)
      ↓
[Step 1: 抛出诱饵 (Hook)] —— 10 秒选方向或填一句想做的点子
      ↓
[即时反馈 (Tease)] —— “已检测到 8 位相关领域开发者，完成身份同步即可解锁”
      ↓
[Step 2: 懒人建卡] —— GitHub / 简历 / 个人主页导入，AI 动效解析
      ↓
[Step 3: 交互式微调] —— AI 智能补全（自适应 2~3 个选择题）
      ↓
[Step 4: 点子深化 (Plan Mode)] —— 针对 Step 1 的想法进行多轮共创，生成项目蓝图
      ↓
[Step 5: 总览确认] —— 角色卡 + 项目卡 合体展示
      ↓
[Step 6: 滑动发现与隐私互换] —— PC/移动端分端匹配展示
关键步骤细节说明：
登录页氛围（弹幕与信任）

弹幕内容采用真实感强烈的动态滚屏：“北京·全栈老哥刚刚组队成功《AI自媒体工作流》”、“寻找精通 3D 打印与硬件调测的伙伴”。

突出 “一键同步 GitHub”，文案注明：“仅读取公开公开仓库与技能分布，绝不获取敏感私有代码”。

自适应提问 Skill（减少交互疲劳）

信息充分时（授权了 GitHub 且仓库活跃）：AI 只需问 1~2 题确认偏好，例如：“检测到你主写 Rust 与 Python，这次比赛你希望担任：[主力后端] [算法预研] [什么都干]？”

信息缺失时（只填了邮箱）：AI 触发轻量选择题（上限 3 题，提供 [其它: ___] 选项），快速定性角色与技术栈。

想法共创（Plan Mode）的设计

采用类似 Cursor / Claude 的分步 Plan 界面：

AI 提问：“这个点子面向的具体痛点是什么？有对标产品吗？”

AI 提问：“技术选型上有初步倾向吗（例如是否需要特定硬件、模型或端侧落地）？”

输出格式标准化：【项目代号】+【一句话解决的问题】+【技术架构初步设想】+【急需寻找的角色】。这不仅能吸引队友，后续还能直接作为比赛报名的初始底稿。

interface AppFlowState {
  currentStep: 'landing' | 'login' | 'idea_hook' | 'profile_parse' | 'survey' | 'plan_mode' | 'review' | 'feed';
  
  // 想法临时数据
  ideaDraft: {
    rawHook: string;             // Screen 3 输入的一句话
    refinedProblem?: string;     // Screen 6 对话提炼的痛点
    techStack?: string[];        // 方案倾向的技术栈
    neededRoles?: string[];      // 急需队友角色
  };

  // 用户角色卡
  userProfile: {
    handle: string;              // 代号或 GitHub 用户名
    roleTitle: string;           // 战术角色（如：全栈黑客）
    skills: string[];            // 技能 Tag 列表
    hackathonGoal: string;       // 参赛目标/肝度
    collaborationType: string;   // 线上/线下
    proofs: string[];            // 提炼的代表作/高光
  };

  // 匹配列表与交互
  matchFeed: {
    selectedCandidateId: string; // PC 端选中的卡片 ID
    isFlipped: boolean;          // 移动端当前卡片正反面状态
    sentRequests: string[];      // 已发送申请的目标 ID 列表
  };
}
四、 快速验证交互指标（Checklist）
在前端做交互跑通时，重点核对以下 5 个验证点：

输入摩擦感：从 Screen 1 到 Screen 5，用户是否在 60 秒内、打字不超过 20 字就拿到了完整的 Persona 结果。

即时利益感知：Screen 3 填完想法后，是否有明显的“已找到潜在队友”的挂钩反馈引导继续下一步。

自适应题量控制：当提供完整 GitHub 时，问卷不得超过 2 道选择题；未提供资料时，题目上限为 3 道。

端侧视图切换：PC 端左右分栏的选中淡入动效、移动端正反翻转在视觉上是否层级明确、不误触。

隐私心智确认：在发出申请前，所有联系方式界面均明确标注为“未公开/打码”，避免用户因顾虑信息泄露而中途跳出。
