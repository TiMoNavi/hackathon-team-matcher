## 三、关键特性设计

### 3.1 人的评价规则

#### 评分维度（总分 100）
```
技术能力 (40 分)
├─ 编程语言 (15 分)
│  ├─ 自述等级 × 0.4
│  └─ GitHub 验证 × 0.6
├─ 框架/工具 (15 分)
├─ 算法/系统设计 (10 分)

软技能 (30 分)
├─ 沟通能力 (10 分) → 首次默认 5 分，互评后调整
├─ 领导力 (10 分) → 是否当过 leader
├─ 执行力 (10 分) → 项目完成率

活跃度 (20 分)
├─ GitHub 活跃度 (10 分)
│  ├─ Commits 频率
│  ├─ PR 贡献
│  └─ Star 数量
├─ 参与历史 (10 分)
│  ├─ 参加次数 × 2
│  └─ 项目完成率 × 3

信誉分 (10 分)
└─ 初始 5 分，根据互评调整
   ├─ 信息准确：+1 分/次
   ├─ 信息夸大：-2 分/次
   └─ 恶意行为：-5 分/次
```

#### 置信度标注
```
每个评分维度附带置信度：
- 高置信度 (90%+)：有客观数据验证
  例："Python 4 星" + GitHub 有 5 个 Python 项目
  
- 中置信度 (50-90%)：部分验证
  例："全栈工程师" + GitHub 有前端代码但无后端
  
- 低置信度 (<50%)：仅自述
  例："精通算法" 但无 LeetCode/竞赛记录

推荐时优先匹配高置信度用户
```

#### 动态调整机制
```python
# 伪代码
def adjust_capability_score(user_id, review_data):
    """
    根据互评调整能力评分
    """
    # 获取历史评分
    old_score = get_score(user_id, "frontend_skill")
    
    # 获取队友评价
    peer_rating = review_data["skill_accuracy"]  # 1-5
    
    # 如果评价远低于自述 → 下调
    if peer_rating <= 2 and old_score >= 4:
        new_score = old_score - 1
        confidence = max(0.3, confidence - 0.2)
    
    # 如果评价验证了自述 → 提升置信度
    elif peer_rating >= 4:
        confidence = min(0.95, confidence + 0.1)
    
    update_score(user_id, "frontend_skill", new_score, confidence)
```

### 3.2 互补性计算规则

#### 技能互补矩阵
```
理想团队配置（3-5 人）：
- 前端 × 1-2
- 后端 × 1-2  
- 设计 × 0-1
- PM/运营 × 0-1
- 算法/AI × 0-1

互补评分公式：
complementarity_score = 
    (缺失角色覆盖度 × 0.5) +
    (技能不重叠度 × 0.3) +
    (经验层次梯度 × 0.2)
```

**示例计算**：
```python
# 用户 A：前端 (React 5星, Vue 4星, 设计 2星)
# 用户 B：后端 (Node.js 5星, Python 3星)

# 1. 缺失角色覆盖度
A_missing = ["后端", "算法"]
B_coverage = ["后端"]  # B 能补上后端
coverage_score = len(B_coverage) / len(A_missing) = 0.5

# 2. 技能不重叠度
A_skills = {"React", "Vue", "CSS", "Figma"}
B_skills = {"Node.js", "Python", "SQL", "Docker"}
overlap = A_skills & B_skills = {}
non_overlap_score = 1 - len(overlap) / (len(A_skills) + len(B_skills))
                  = 1 - 0/8 = 1.0

# 3. 经验层次梯度（避免两个都是新手）
A_experience = 3  # 年
B_experience = 5  # 年
gradient_score = 1 - abs(A_experience - B_experience) / 10
               = 1 - 2/10 = 0.8

# 最终互补分
complementarity = 0.5*0.5 + 0.3*1.0 + 0.2*0.8 = 0.71 (71分)
```

### 3.3 防止资源错配的具体规则

#### 曝光配额系统
```python
def calculate_daily_quota(user):
    """
    计算用户每日最大被推荐次数
    """
    base_quota = 20
    
    # 能力越强，配额越低（反直觉但合理）
    capability_factor = 1 - (user.capability_score / 100) * 0.5
    # 例：90分用户 → factor=0.55, 50分用户 → factor=0.75
    
    # 响应率越高，配额越高（鼓励积极响应）
    response_rate = user.accepted_invitations / user.total_invitations
    response_factor = 0.5 + response_rate * 0.5
    
    # 当前组队状态
    status_factor = {
        "seeking": 1.0,      # 在找队友
        "casual": 0.5,       # 随便看看
        "teamed": 0.1,       # 已组队
    }[user.team_status]
    
    quota = base_quota * capability_factor * response_factor * status_factor
    
    return int(quota)

# 示例
# 大佬（90分，50%响应率，seeking）：20 * 0.55 * 0.75 * 1.0 = 8次/天
# 新手（50分，80%响应率，seeking）：20 * 0.75 * 0.9 * 1.0 = 13次/天
```

#### 推荐多样性保证
```python
def diversify_recommendations(candidates, top_k=5):
    """
    确保推荐列表的多样性
    """
    results = []
    
    # Top 1: 最匹配的
    results.append(candidates[0])
    
    # Top 2-3: 次优但不同类型
    for candidate in candidates[1:]:
        if is_diverse_from(candidate, results):
            results.append(candidate)
            if len(results) == 3:
                break
    
    # Top 4: 刻意降低能力要求，选互补性强的
    for candidate in candidates:
        if candidate.capability_score < 70 and \
           candidate.complementarity_score > 0.8:
            results.append(candidate)
            break
    
    # Top 5: 完全随机（探索性推荐）
    results.append(random.choice(candidates[5:15]))
    
    return results[:top_k]
```

- [ ] 找一个真实的小型黑客松（50 人以下）
- [ ] 手动收集参与者信息
- [ ] 用原型系统生成推荐
- [ ] 对比"AI 推荐"vs"自由组队"的效果
- [ ] 收集反馈

### 开发阶段（6 周）
- 如果验证通过 → 执行之前的 MVP 计划
- 如果效果不佳 → 调整算法或 pivot 方向

## 八、风险与挑战

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|----------|
| 用户不信任 AI 推荐 | 高 | 高 | 显式展示推荐理由，支持人工浏览 |
| 冷启动无数据 | 高 | 中 | 种子用户计划，合成数据 |
| 推荐质量差 | 中 | 高 | A/B 测试多种算法，持续优化 |
| 隐私泄露 | 低 | 高 | 架构隔离，权限分级，审计日志 |
| 成本过高 | 中 | 中 | 优化 Prompt，缓存结果，限流 |
| 用户流失 | 高 | 中 | 留存机制，长期价值挖掘 |
