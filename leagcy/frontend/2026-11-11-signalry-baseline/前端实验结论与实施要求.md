# 前端实验结论与实施要求

记录日期：2026-11-11。适用范围：本目录的 AffectUI、Shadcn UI Kit 资源使用，以及后续 HumHub 前端验证与实现。

本文件保存已验证的事实、后续建议和实施约束。当前完成的是三个首页原型；路线建议不代表已经批准正式全站迁移。产品规则仍以父目录的 AGENTS.md、当前设计文档和用户后续明确要求为准。

## 一、实验结论

三个独立子任务分别实现了原生首页、React 首页插件和独立 Next.js 首页。使用同一份虚拟活动与成员数据，统一浏览器检查共 51/51 通过，各路线 17/17。

| 路线 | 已验证的能力 | 改造难点 | 当前判断 |
| --- | --- | --- | --- |
| 1. 原生视图升级 | PHP / Yii / Bootstrap 可以实现新的首页视觉；真实加载 HumHub 原生资源 | React 组件需要转写成 PHP、CSS 和 DOM 交互；处理主题样式叠加与 PJAX 生命周期 | 适合保留原生生态、逐页改变外观 |
| 2. 独立 React 前端插件 | 真实 HumHub 模块路由能提供独立 React 页面，直接复用两套组件源码 | 模块入口、构建清单、资产发布、样式隔离；后续还需接通真实业务 | 优先继续验证的方向 |
| 3. 独立前端重写 | Next.js / React 可以组合两套组件，布局和页面交互实现顺畅 | 另有运行入口，认证、权限、API 与全站迁移需要完整适配 | 适合接受较大迁移范围、希望全面掌控前端的情况 |

三种技术路线都能做好看。原生版不等于只能做旧界面；React 也不会自动带来更好的设计。本次独立版手机首屏更紧凑，是布局选择的结果，其他路线也可以实现相同布局。

“插件”是安装和交付方式，“重写前端”是界面改造范围。可以将新的 React 前端作为 HumHub 插件交付；若逐步接管全站，业务接口和页面迁移工作仍然存在。

## 二、资源与组件使用要求

1. 前端组件来源采用用户已选定的 **Shadcn UI Kit 与 AffectUI**。Kit 作为页面、区块和基础组件的主要来源，AffectUI 用于适合的交互和动效；不默认引入另一套 UI 组件库。
2. 优先查询已有 [本地模板索引](TEMPLATES.md)、vendor 快照和组件文档。需要新组件时按官方 Skill / MCP 指引选择条目，确认依赖、样式和运行环境，再安装或取源码。
3. 组件、后台页面、完整网站模板分别对待。已取得某个组件或本地快照，不等于所有付费包都能下载；本次也没有验证整套付费模板的直接安装与完整兼容性。
4. 不能把 React TSX 直接当作 PHP 组件使用。原生路线要明确记录转写范围；React 路线优先通过 props、className、主题变量和外层布局适配，尽量保留第三方原文件。
5. 选取需要的源码与依赖，不把整个 vendor 快照都打包进浏览器。保留组件来源、版本与必要的适配记录。
6. 统一颜色、字号、间距、圆角和交互状态。AffectUI 自带样式仍需与 Kit / Tailwind 主题协调；模板中的模拟数据、图片和业务逻辑不能直接视为本项目的正式实现。
7. 下载凭据只放在已有私有配置或被忽略的环境文件中，不进入前端产物、文档和测试日志。

本次直接复用的组件：路线 2 使用 Kit Card、Button、Sheet 与 AffectUI ProgressTracker；路线 3 使用 Kit Card 与 AffectUI ProgressTracker。组件源码一致性及来源记录在各路线 metrics.json 中。

## 三、后续优先路线与接入要求

**建议优先继续路线 2：由 HumHub 模块承载独立 React 页面。** 本次已证明模块入口与资源隔离可行，下一步应验证真实业务连接，而不是重复制作另一套纯静态首页。

如果采用这条路线，后续实现遵循以下约束：

- **独立前端页面。** 新页面使用自己的布局、主题、导航与 React 构建资源。保持本次已验证的隔离边界，不在完整新页面中叠加 Bootstrap、Clean Theme、jQuery 或 PJAX，也不靠 iframe 假装完成融合。
- **保留后端接入机制。** 模块通过 HumHub 控制器和资产发布机制提供页面。避免引入原生样式，不等于可以绕开服务端认证、权限或 CSRF；本次独立 HTML 返回方式也不应未经业务验证就复制为生产入口。
- **明确新旧页面边界。** 新首页不会自动改变原生消息、个人资料、管理后台等页面。每次列出已迁移和未迁移的页面，并处理跨页面导航、返回、刷新与直接访问。
- **分离页面与业务。** React 负责呈现和用户交互；HTTP 适配器处理接口，业务规则放在既有服务端用例中。不让页面直接访问数据库，不把业务规则堆入 PHP 页面控制器。
- **统一业务契约。** 接口字段、错误、分页和路径遵循现有共享契约；新增接口先核对既有模块能力，避免为演示重复建立另一套模型。

本次插件在构建时使用 Node，构建后的文件由 HumHub 同源提供，运行该页不需要另启常驻 Node 服务。独立 Next.js 原型则使用单独服务；未来是否采用其他部署方式需另行验证。

## 四、视觉与交互验收要求

用户于 2026-11-11 指定 **Signalry** 为当前风格基准，具体主题、字体与页面适配见 [整体风格规范](design-system/team-matcher/MASTER.md)。此前“同频 CoLab”实验的绿色主色作为历史参考；侧导航、手机底部导航及已验证的交互经验仍可参考。选择视觉基准不代表正式页面已实现或全部设计细节已冻结。

- 至少检查桌面 1440×1000 和手机 390×844，并在中间宽度检查布局变化；页面不得横向溢出，导航、搜索和主要操作应可用。
- 成员卡、角色筛选、搜索、无结果提示、详情打开/关闭和状态切换要实际操作验证，不能只看截图。
- 弹窗支持清晰的关闭入口与 Escape；图标按钮要有无障碍名称。测试状态时兼顾可见文字和 aria 状态，不能把图标按钮没有文字误判为失效。
- 验收同时检查构建、页面运行错误和资源加载错误，保留实际截图与测试记录。页面上线前另补真实业务、权限及所需浏览器兼容测试。
- 演示入口明确标注虚拟数据。未实现的消息、关注保存或其他业务不能用成功提示冒充已经执行。

## 五、业务接入与实验边界

1. 继续实验时使用独立目录、实例与演示数据库。正式接入需有相应任务授权，本次结论不构成改动原项目或原数据库的许可。
2. 真实页面先验证登录状态及服务端认可的当前活动。发现、筛选、搜索、详情等按项目活动边界执行，不能依赖前端过滤承担权限控制。
3. 用户资料、联系方式和好友关系沿用既有可见性与业务规则。真实关注、发帖、消息等写操作必须由用户动作触发，并通过后端授权与 CSRF 检查。
4. 模拟匹配比例、通知、成员和本地关注状态均为演示数据，不得作为真实推荐或已保存业务状态继续使用。
5. 当前尚未验收真实登录、Space 权限、数据持久化、上传、消息、通知、全站迁移或长期升级兼容性。三个漂亮首页不能代替这些验证。

下一步建议为一个最小的只读业务闭环：真实登录 → 当前活动授权 → 成员读取接口 → React 列表与详情，补上未登录、无权限、空数据和读取失败状态。此项尚未实施，也不在本次文档整理任务中启动。
